**Context:** the Android wrap and P1 printer plugin both need a full rebuild-and-reinstall for any change. Everything else — UI, business logic, report queries — is pure web layer, and shouldn't need that. Capgo pushes web-layer bundles over the air on top of the existing bundled-assets model.

**Inspected and reported the plan before installing, per the task's gate.** Verified the actual package against its real `.d.ts` (npm-packed into a scratch dir and read directly — the first fetched doc page showed a self-hosted-flavored example that didn't match what "use Capgo's hosted service" needed) rather than trust a summarized doc fetch. That surfaced the exact mechanism for every requirement:
- `autoUpdate: 'atBackground'` is a named mode, not something to hand-build: *"Check and download automatically on each foreground check, then apply the update the next time the app moves to background."* That's requirement 3 verbatim — no manual `@capacitor/app` resume-listener needed, it's built into the mode.
- `updateUrl`/`channelUrl`/`statsUrl` default to `https://plugin.capgo.app/...` — Capgo's hosted service is the unset default; setting them is what self-hosting would require. Leaving them out **is** the hosted-service config.
- Rollback (requirement 4) isn't a separate flag — it's automatic whenever `notifyAppReady()` doesn't fire within `appReadyTimeout` (default 10s). The CLI itself also refuses to upload a bundle that doesn't call `notifyAppReady()` in source, unless `--no-code-check` is passed — a second safety net against shipping an unrecoverable bundle.

**Dashboard (user) vs. code (mine), as executed:** user signed up, got an API key, logged in via the CLI, and registered `com.batuexport.app` on Capgo Cloud (org "batuexport app") before this session touched anything. Deliberately did not run the guided `capgo init` wizard even though it exists — its own description says it "adds code for updates," which would have collided with the hand-written wiring below.

**A — package and config, as built:**
- `npm install @capgo/capacitor-updater` (8.51.2, Capacitor-8-compatible). Confirmed **zero new dependencies**: `npm ls @capgo/capacitor-updater` shows it as a bare leaf, and the package-lock diff is 10 lines (the one new entry, nothing else touched) — the `npm audit` count jumping from 3 to 20 findings after this install is unrelated to it (see Verification).
- `capacitor.config.ts`: added a `plugins.CapacitorUpdater: { autoUpdate: 'atBackground' }` block. No `updateUrl` override (hosted service), no `appReadyTimeout` override (10s default is generous for this bundle size — `notifyAppReady()` fires before any data loads, so it's bounded by JS parse/execute time, not network).
- `main.tsx`: `CapacitorUpdater.notifyAppReady()` called immediately after the root render, before `App`/`AuthProvider` ever gets to its Supabase session check — placement matters here, the docs explicitly warn against waiting for any network request first. Safe to call unconditionally on the web build too: the package ships an official `CapacitorUpdaterWeb` no-op implementation (confirmed by reading `web.d.ts`), so this needed no `isNativePlatform()` guard the way the app-specific P1 printer plugin does.
- `npx cap sync android` — published npm plugin, self-registers via the same mechanism as `@capacitor/preferences`; no manual Gradle or `MainActivity.java` change, confirmed by the sync output listing both plugins and a subsequent clean `assembleDebug`.

**B — bundled assets stay the fallback.** Untouched by this task: no `server.url` was ever set (Android wrap entry), and CapacitorUpdater doesn't require one — it patches the existing local `webDir` bundle, it doesn't switch the app to fetching from a remote origin. First launch and any launch with no signal still run whatever's in `dist-native`, OTA or not.

**C — update strategy: `atBackground`**, set explicitly rather than relying on the equivalent default (`true`), so a future reader doesn't have to know that boolean means this specific mode. Checks on every foreground (app start and resume both count), downloads without blocking the UI, applies only when the app next backgrounds or relaunches — never mid-session, so Ombor is never interrupted mid-scan.

**D — rollback.** Enabled by construction, not a setting: as long as `notifyAppReady()` fires (confirmed wired in `main.tsx`), a bundle that fails to boot at all — the only thing this checks — reverts automatically within the 10s default `appReadyTimeout`. `autoDeleteFailed` (default `true`, left untouched) cleans up the failed bundle afterward so it isn't retried.

**E — env vars survive an OTA push, verified directly, not assumed.** Ran `npm run build:native` and grepped the output bundle for the real `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` values from `.env` — both inlined, no leftover `import.meta.env` lookup. This is the exact same build command (and the exact same `dist-native` folder Capgo's CLI defaults `--path` to, from `capacitor.config.ts`'s `webDir`) that produces what ships in the APK — there is no separate "OTA build" path that could diverge and omit them. A bundle missing these would produce exactly the "failed to fetch" login failure the task named; this build doesn't.

**Channel setup — blocked by a live Capgo backend inconsistency, not a CLI mistake.** `channel add production com.batuexport.app --default` failed with "App … does not exist." Diagnosed from four independent angles before concluding this wasn't fixable by retrying: `app add` itself reports a duplicate-key error (the app demonstrably exists), `organization list` shows the one org has "Apps: 2," yet `app list`, `channel add`, and `app debug` all fail to find this specific app by id. Every WRITE-shaped path confirms the app exists; every READ-by-id path can't see it — consistent with a backend/caching bug on Capgo's side (their CLI even documents a "Cloudflare rollout decision cache TTL," suggesting a caching layer sits in front of at least some reads), not anything wrong with the app registration itself or with this repo's setup. Not resolved as part of this task — flagged for the user to check via the Capgo dashboard UI directly (which may not share the CLI's specific read path) or retry once resolved. Everything else in this task — the code wiring, the env-var proof, the APK build — is independently complete and doesn't depend on the channel existing yet.

**Release flow (once the channel exists):**
```bash
npm run build:native
npx @capgo/cli@latest bundle upload com.batuexport.app --channel production
```
`--path` isn't needed — the CLI defaults it to `capacitor.config.ts`'s `webDir` (`dist-native`), which is exactly what `build:native` produces. The CLI's own `--no-code-check` bypass exists but is deliberately not part of this flow — its default (checking) is the safety net described under D.

**Adding a staging channel later** (the user's ask, structured for now rather than built now): `npx @capgo/cli@latest channel add staging com.batuexport.app` (no `--default`, so it never becomes what devices get automatically), then a specific test phone can be pointed at it via a Capgo dashboard Device Override — no app rebuild, no code change. This is why `defaultChannel` was deliberately **not** set in `capacitor.config.ts`: hardcoding it there would override the cloud-side channel assignment on every device running this APK, which would make exactly this kind of single-phone staging test impossible without a rebuild. Leaving it unset keeps the channel assignment fully cloud-controlled, which is what "test on one phone before it hits all of them" needs.
