## 1. System Overview
**Company:** BATU EXPORT — dried-apricot **toll processing** & export (Uzbekistan). Client owns the goods; BATU provides washing/processing/packaging. Apricot-first; other lines (raisins/*mayiz*, prunes) added later via settings, **no code change** (§2.3).
**Platform:** 🔒 PWA, **offline-first** (§2.6).

### 1.2 Lifecycle of one serial
```
MANAGER KIRIM order → serial DDMMYY-NNN (Kutilmoqda)
  → QOROVUL stage-1 (Гружёный, loaded) → Kirdi·bo'shatilmoqda
  → QOROVUL stage-2 (Пустой, empty)     → Yakunlandi
  → STORAGE §1 confirm + namligi + Barcode #1 → Skladda turibdi
  → STORAGE §2 send to Moyka (partial allowed) → Moykaga yuborilgan
  → STORAGE §3 finished receipt per PALLET + Barcode #2 → Tayyor (per type+calibre incl. Konditirskiy)
  → MANAGER CHIQIM request (no serial) → QOROVUL stage-1 (Пустой, empty)
  → STORAGE §4 scan Barcode #2 pallets → manifest → loaded
  → QOROVUL stage-2 (Гружёный + photos + doc photo) → Olib ketildi / Yakunlandi
```
🔒 One truck-trip may run several of these lifecycles in parallel — one per type, one per serial (§2.1). The gate stages are shared (one weighing per truck); everything from STORAGE §1 onward is per-serial.

## 2. Global decisions 🔒

### 2.1 Serial format 🔒
`DDMMYY-NNN` (e.g. `120826-003`). Resets daily. 🔒 **One serial per product type, not per truck.** A KIRIM order is a *delivery envelope* (one truck, one trip); each **type line** on it is minted its own serial by `next_serial()` on manager submit. A truck carrying Subxon + Isfara produces two serials; a single-type truck is simply the N=1 case. Consequence: **a serial is always single-type** — which is what makes Barcode #1 per type-pile (§5.1), single-sample lab results (§5.5), and per-type storage stock (§8) correct rather than approximate. Shown, never typed.

### 2.2 Barcodes 🔒 (updated)
| | #1 (raw serial) | #2 (physical pallet) |
|---|---|---|
| Printed when | Storage §1 confirms raw load | Storage §3 saves a finished receipt — **one sticker per physical pallet** |
| Encodes | serial + turi + egasi + sana | sticker ID + parent seriya + **turi** + kalibr + og'irlik + egasi |
| ID format | — | ~~`PLT-<serial>-<calibre>`~~ → **`PLT-<serial>-<calibre>-<seq>`** (Konditirskiy → `…-KN-<seq>`). *Updated 2026-07-15 (Step 6): the original format collides when a serial yields multiple pallets of the same calibre — which "one sticker per physical pallet" + atomic pallets require — since `barcode2` is the PK. `<seq>` is a per-(serial,calibre) 1-based counter. See DECISIONS.md.* |
| Notes | 🔒 one #1 per serial. Since a serial is single-type (§2.1), this is inherently one per type-pile. | **Barcode #2** carries type for scan-time confirmation and dispatch matching; the parent serial already determines the type (§2.1). 🔒 **A pallet is atomic as a physical/labeled unit — never split into multiple barcode2 rows.** ~~It is loaded whole or not at all (§5.4)~~ **AMENDED v1.32, 2026-08-28: its DISPATCH can now be partial — a batch may be split across several requests via the FIFO consumption ledger (§5.4) — only the sticker/row itself stays one-per-pallet.** |

Roles have explicit write scopes. **Rahbar is read-only on ALL operational records** (orders, weighings, receipts, dispatches, lab results) and may open **any other role's screens read-only**. 🔒 **v1.22: Rahbar is now read-only everywhere, full stop** — Administration (formerly §6.4: product settings, exceptions, user management) moved to Menejer (§3.3); no write path remains for Rahbar anywhere in the app. See DECISIONS.md "Boshqaruv moved to Menejer."
Rationale: if the owner can edit an operational record, the audit trail loses meaning. Corrections happen via **append-only notes** (§2.5) or by the responsible role redoing the action — never by silent owner edits. Enforce server-side, not just by hiding buttons.

### 2.15 Technical architecture 🔒 (NEW)
**Stack:** React + Vite + TS + Tailwind (PWA) · **Netlify** (frontend, auto-deploy from GitHub) · **Supabase** (Postgres + Auth + RLS + Storage) · Dexie/IndexedDB (offline queue).

🔒 **The database is the source of truth, not the app.** Rules that must never break live in Postgres, not React — because there will eventually be multiple clients (phone, desktop, future finance module) and a rule in React can be bypassed by any of them.

🔒 **Serial generation happens in the DATABASE** (§2.1). A Postgres function (`next_serial()`) mints `DDMMYY-NNN` atomically, using the **Asia/Tashkent** timezone for the daily reset. JavaScript generation is forbidden — two phones would collide.
- *Consequence:* an **offline-created** KIRIM order receives **its serials** (one per type line, §2.1) **on sync**, not at submit. UI shows `seriya: kutilmoqda` until then.

🔒 **RLS (Row Level Security) enforces §2.12, from day one.** Enabled on **every** table. Hiding buttons in the UI is not security — the database must refuse the write.
- `rahbar` → SELECT everything only. **v1.22: no write policy of any kind remains for rahbar** — the admin-table INSERT/UPDATE grants (owners, product_categories, product_types, calibres, settings_limits) and the `admin-users` Edge Function's caller check were both moved to menejer (§3.3, DECISIONS.md "Boshqaruv moved to Menejer"). That absence *is* the enforcement, same principle as before, now with zero exceptions.
- `menejer` → writes orders/requests · INSERT/UPDATE on `owners` (§3.3, v1.21) · **v1.22: plus INSERT/UPDATE on `product_categories`/`product_types`/`calibres`/`settings_limits`, and is now the sole caller role accepted by the `admin-users` Edge Function** (§3.3 — full Boshqaruv scope, moved from Rahbar) · `qorovul` → writes weighings · `ombor` → writes storage/pallets/dispatch · `laborator` → writes lab results.
- `notes` → **INSERT only; no UPDATE/DELETE policy for anyone** — this is what makes append-only (§2.5) real rather than a convention.
- `audit_log` → INSERT only.

🔒 **Store events, derive numbers.** Never store a running balance as a mutable number (inventory drifts and starts lying). Store the *events* (received / sent to Moyka / finished / dispatched) and derive balances via **views**. Every screen (Kuzatuv, passport, client report, Rahbar oversight) reads the same view, so they can never disagree.
- *This is also what makes a future **finance module** cheap:* money attaches to events already recorded — a price table + a view produces invoices with **zero changes to inventory tables**.

🔒 **Never DELETE — void.** Status flags everywhere (see §2.13). The audit trail is the defence in a client dispute.

🔒 **Derived columns:** net weight (`gruzheny − pustoy`) is a **generated column**, so a wrong net can never be typed.

## 2.16 WEIGHT AUTHORITY & EFFECTIVE QUANTITY 🔒 (NEW, v1.10)

*Renumbered from the source revision's "§2.15" — SPEC.md already has an unrelated §2.15 ("Technical architecture," above). See DECISIONS.md for the renumbering note (the source revision's own companion doc was never actually created in this repo — every section it would have held is now written directly into this document as each is built, per v1.18).*

Three weights exist for the same material. **All three are permanently retained; none overwrites another.**

| Weight | Source | Meaning |
|---|---|---|
| **Declared** | Menejer, at order entry (`kirim_lines.declared_qty`) | What the client said they sent. Never modified by anyone, ever (existing rule, unchanged). |
| **Intake** | Ombor, at receipt (`storage_intake.actual_qty`) | Ombor's own figure. **Pre-filled with the declared quantity and usually accepted untouched** — on single-product trucks Ombor performs no independent measurement. Treat as a per-line split, **not** as a measurement. |
| **Gate net** | Qorovul, `gate_weighings` (loaded − empty) | 🔒 **The accounting truth.** This is the only figure produced by a calibrated scale and evidenced by two mandatory photos. |

### 2.16.1 Effective quantity — the derived figure everything reads

🔒 **`effective_qty` is derived, never stored**, computed per `kirim_line`:

- **Single-line truck (the norm):** `effective_qty = gate net`. The gate weighed exactly this material and nothing else.
- **Multi-line truck (rare):** `effective_qty = storage_intake.actual_qty` per line, because the gate produces one figure for the whole truck and cannot split it. Gate net remains the truck total; the sum of the lines is reconciled against it and any gap is shown as a **soft variance** (never blocks, per §3.1 philosophy). 🔒 **A multi-line truck's `effective_qty` never becomes gate net, even after gate stage 2 completes** — only whether it is *provisional* flips; the number itself stays the per-line intake figure permanently (see DECISIONS.md — this ordering, not stated explicitly in the source revision, was confirmed with the user before implementation).
- **Before gate stage 2 exists:** `effective_qty = storage_intake.actual_qty`, displayed as **provisional** (see §2.16.2).

🔒 **Every downstream calculation reads `effective_qty`, not intake or declared** — raw available to send to Moyka, process loss, yield %, client balances, all reports. One derived truth, all consumers — the same principle as availability (§5.5.3). Implemented as `src/lib/weightAuthority.ts` (pure rule) + `src/lib/effectiveQty.ts` (I/O layer)~~, mirroring the `rewash.ts`/`activeCycles.ts` split (Step 8)~~ **(AMENDED 2026-07-28: `rewash.ts`/`activeCycles.ts`/`usePendingRewash.ts` were deleted outright as part of the wash-cycle-removal migration — this citation is stale as a live pattern reference; the pure-rule/I/O split it described lives on unchanged in `weightAuthority.ts`/`effectiveQty.ts` themselves, it just no longer has that sibling pair to point to)**.

### 2.16.2 Sequencing: gate net arrives *after* intake 🔒

The KIRIM order of events is: gate weighs loaded → **Ombor receives, records intake, Barcode #1 issued** → truck unloads and departs → **gate weighs empty → net known**.

So the authoritative weight is established **after** Ombor and Menejer have already seen a quantity on screen. Therefore:

- Between intake and gate stage 2, the quantity displayed on Ombor's and Menejer's screens is **provisional**, visually marked (*"tarozi kutilmoqda"*).
- 🔒 **When gate stage 2 completes, a single-line serial's effective quantity updates automatically on both screens** to the gate net figure. This is a derived recomputation, not a stored write — it changes no records, so it does not violate the no-silent-auto-transition invariant (§2.2). Nothing is accepted, finalized, or advanced; a displayed number simply becomes final. (A multi-line serial's *value* never changes this way — see §2.16.1 — only its provisional flag does.)
- Where the gate net differs materially from the declared quantity, both are shown with the variance — Menejer needs to see when a client's declaration was wrong, and that is a commercial conversation. 🔒 Variance is always **gate-vs-declared**, never intake-vs-declared (§5.1 amend) — intake is a pre-filled split, not a measurement, so comparing it to declared would read ~0% almost everywhere and measure nothing.
- **Lab checks are unaffected.** Laborator's KIRIM queue is keyed to intake existing, and quality is independent of quantity — a serial may be tested while its weight is still provisional.

⚠️ **Edge case, implemented:** if material is sent to Moyka before gate stage 2 completes, the sent quantity was measured against a provisional figure. Flagged, never blocked — the serial shows a variance note if the gate net later lands materially different, using the existing `kam_chiqdi_pct` threshold (§5.1) as the materiality bar rather than a new one (no threshold/notification config was built this prompt — deliberately deferred, see §7).

## 2.17 PARTIYA RAQAMI (per-type arrival batch number) 🔒 (NEW)

Every `kirim_lines` row belonging to a real delivery (`kirim_orders.origin = 'delivery'`) carries a **partiya raqami** — a per-`type_id` sequential batch number, assigned **first-come-first-numbered by arrival order** and shown next to the serial everywhere a serial is displayed.

🔒 **The counter is scoped to product type, never shared.** A truck carrying two products (e.g. Subxon + Isfara) splits into two `kirim_lines` rows, each numbered against its **own** type's sequence — a mixed truck's two lines never share one number, and never collide with an unrelated type's count. A serial is single-type by construction (§2.1), so this is the only scoping that makes sense.

🔒 **Arrival ordering key:** `(kirim_orders.order_date, kirim_orders.created_at, kirim_lines.serial)` — the order's own date for the arrival itself, its `created_at` to break same-date ties between different orders, and `serial` (globally unique, itself a monotonic per-day counter) as the final tie-break between two lines of the same type on one multi-type order.

🔒 **Assigned eagerly, at `kirim_lines` INSERT time**, by a race-safe per-type counter table (`partiya_counter`) — the same atomic `insert ... on conflict (key) do update set counter = counter + 1` pattern already used for `serial_counter`/`next_serial()`, not a live `count(*) + 1` scan (which would race under two concurrent Menejer submissions for the same type). This is mathematically equivalent to "1 + count of every earlier arrival of this type" for live inserts specifically, since a fresh insert's own `order_date` is always today — never earlier than an already-numbered row's date.

🔒 **Never reassigned once written** — enforced by a dedicated immutability trigger, independent of RLS (`kirim_lines` has no UPDATE policy for any role today; this is defense in depth).

🔒 **Origin filtering applies (see CLAUDE.md "Origin filtering"): opening-stock and internal-reprocess rows never get a number.** `origin = 'opening_stock'` (seeded old stock) and `origin = 'internal_reprocess'` (Rezka/old-stock-re-wash minted serials) rows carry `partiya_no = NULL` permanently — they never arrived on a truck, so there is nothing to number. Displayed as a **blank badge** (no badge at all), never "0" or "1".

**Displayed as a small amber badge ("P{n}") next to the serial**, visually distinct from the serial's own slate/mono chip styling, across every role's view: Laborator KIRIM/CHIQIM (live + Tarix history) and their Tahlil forms, Ombor's Intake/Moyka/Tayyor/CHIQIM tabs and Hisobotlar history, Menejer's KIRIM orders list and CHIQIM raw-serial picker, Qorovul's KIRIM gate queue, the serial passport (prominently, in the header: *"Seriya: X · Partiya: Y (Tur)"*), Hisobot's results table (its own filterable, visible `Partiya` column — exact-match filter, not substring), and the Global Export client portal's Hisobot table, per-serial summary, and internal client-report view.

Backfilled once, for every pre-existing `origin = 'delivery'` row, ordered by the same arrival key above (`supabase/migrations/0093_kirim_lines_partiya_no.sql`) — idempotent by construction (`where partiya_no is null`), safe to re-run.

🔒 **AMENDED 2026-08-29 (Prompt 9) — badge format now includes a one-letter product-type prefix: `P{n}-{prefix}`**, e.g. `P1-S` (Subxon), `P1-I` (Isfara), `P1-N` (Natural), `P1-Q` (Qand), `P1-QQ` (Qand qizil — the live `product_types.name` string, lowercase "qizil"). ## 2.18 LOSS DISPLAY CONVENTION 🔒 (NEW)

Every screen that renders the signed wash-process loss figure (`sent − received`, per §5.2's "Moyka loss becomes live" — positive = real loss, negative = surplus/overage) does so through **one shared helper, `formatLossKg`/`formatLossPct`** (`src/lib/formatLoss.ts`), never inline sign-handling.

🔒 **Display rule — the sign shown is the INVERSE of the underlying signed number's own sign:**
- Real loss (`signedKg > 0`, the expected/neutral case) → rendered **bare**, no sign: `"50 kg"`.
- Surplus (`signedKg < 0`, the noteworthy case) → rendered with an **explicit `+` prefix** on the absolute value: `"+50 kg"`.
- Exactly zero → `"0 kg"`.

*Rationale:* a naive `.toLocaleString()` on the raw signed number would mark the common case (loss) with nothing and the noteworthy case (surplus) with a bare negative sign that reads as bad news — the opposite of what it means. Inverting which side gets the `+` makes the good news visually distinct.

Applies wherever loss renders: serial passport (per-cycle `Yo'qotish`), Hosildorlik/Yield table + totals, Mijoz hisoboti (`processLoss`), Rahbar dashboard (Ledger B `Yo'qotish` row + bar-chart label), the Global Export client portal (`Убыток`, Cyrillic `кг` unit via the helper's optional `unit` parameter), and Menejer's Diqqat talab exceptions list. **Does not apply** to storage write-off figures (`storageLossKg`, always ≥0 by construction — a different, structurally-unsigned concept) or to Excel export cells (numeric cells keep their own native negative-number convention, a deliberate scope decision — see DECISIONS.md).

🔒 **AMENDED 2026-08-29 (Prompt 10, Yakunlash — see DECISIONS.md "Serial close-out (Yakunlash) + realized-vs-unrealized loss").** The signed `sent − received` gap this helper formats is no longer one thing at all times — it now reads as one of two different things depending on `wash_cycles.closed_at`:
- **Open** (`closed_at IS NULL`): the gap is **Moykada** — still-in-process, unrealized, nothing booked. `formatLossKg`/`formatLossPct` are never called on it; screens render it as a plain floored kg figure (never signed, never a `+`) alongside a **dash** (`—`) where the loss figure would go, signalling "not yet known" rather than "zero."
- **Closed** (`closed_at IS NOT NULL`): the gap is **Yo'qotish** — realized, booked. This is the exact figure `formatLossKg`/`formatLossPct` above describes; the split changes *which serials* reach this formatting, not the formatting rule itself.

One canonical TS-side splitter, `computeLossDisplay(sent, received, closedAt)` (`src/lib/formatLoss.ts`), returning `{ moykadaKg, yoqotishKg, isRealized }` — used directly wherever a screen already holds raw `sent`/`received`/`closedAt` client-side (Ombor Tayyor's own live screens, via `useMoykaOutput`). Every SQL-sourced payload (passport, Hisobot, Yield, client report, Rahbar) carries the identical split computed server-side (the same `closed_at`-gated branching, expressed in SQL once `wash_cycles` is joined) — those screens render pre-split fields, they do not re-derive anything. Yield/Hisobot's `high_loss` exceptions and the Yield table itself only ever see **closed** (realized) serials in the first place (§5.3 below) — see that section for why an open serial doesn't reach a "loss" figure to format at all.

One canonical function now answers that for both truck types — **`chiqim_departed_at(request_id)`**: gate stage 2's `completed_at` for a regular truck, **`ombor_finished_at`** for a fura. Every one of those ten call sites goes through it (`kirim_line_state`, `report_chiqim_rows`, `report_moyka_output_rows`, `stock_on_hand_rows`, `wip_rows`, `old_stock_closeout_lines`, `close_out_old_stock`, `get_serial_passport`, `get_client_report`, `rahbar_dashboard_ledger`); none re-derives the branch. Without this a fura's pallets would sit `band_qilingan` forever, count zero against `olib_ketilgan`, never reach a client report, and stay in Diqqat talab as *Jo'natish kechikdi* permanently.
  - 🔒 **Completing event = Ombor's `Yuklashni yakunlash` click.** No new button and no Menejer action: a `before update` trigger on `chiqim_requests` flips `status → olib_ketildi` in the same statement that sets `ombor_finished_at`, mirroring what `complete_chiqim_stage2` does for a regular truck at gate stage 2. **This does not weaken the "CHIQIM per-role finalization" invariant (§5 intro)** — that invariant forbids `status` standing in for *Ombor is done loading*; here, for a truck the gate never touches, Ombor's finish click **is** the departure, so the two facts genuinely coincide rather than one being overloaded for the other. Regular trucks keep all three independent finish events, unchanged.
  - 🔒 **Undo window (documented explicitly).** Ombor's undo of a consumption row is gated by the existing `ombor_deletes` RLS policy (`status IN ('kutilmoqda','qabul_qilindi')`), untouched by this change. Regular: closes at gate stage 2, as before. **Fura: closes at Ombor's finish click**, because that is when the status flips — a consequence of reusing the same status, not a second mechanism. The Menejer-side void window closes at the same moment for both (`menejer_updates` already requires `ombor_finished_at IS NULL`). Ombor's own screen states this before and at the confirm step, since for a fura it is the last reversible moment there is.
  - FIFO attribution at the finish click is **unchanged** — per line, exactly as for a regular truck. Only the truck-level weighing is skipped.
  - 🔒 **Qorovul's gate photos (NEW v1.42, 2026-08-30) — the one thing a fura does NOT skip at the gate.** The guard captures a **moshina rasmi** at entry (`Kirdi`) and a **nakladnoy rasmi** at exit (`Chiqdi`), both required, in Qorovul's own Window 1 (§4). They are an independent record: they gate nothing, they do not create a departure, and they neither block nor are blocked by Ombor's finish click — the two flows run physically in parallel. Everything this section says above about accounting weight, the departure event and the undo window is unchanged by them. Shown as thumbnails (tap to enlarge) on the serial passport and the internal Mijoz hisoboti (§3.2.7) for fura dispatches only; a regular dispatch shows no photo section there, its gate evidence being the weighing's own four photos. 🔒 **Deliberately NOT surfaced in the Global Export client portal (§3.6)** — nakladnoy photo links were dropped from that screen the day it shipped, and the storage bucket's read policy excludes the `client` role outright rather than relying on the UI not to render them.
