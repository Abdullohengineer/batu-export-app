## 2026-07-25 — Camera scanner in the Android WebView: diagnosis and instrumented fix

**Context:** the BarcodeDetector-plus-ponyfill replacement (earlier DECISIONS entry, "Camera scanner") was already confirmed working on a real phone's *browser*. In the Capacitor Android WebView specifically, the camera opens (permission granted, live video shows) but never decodes — manual entry, untouched, still works. No device is available this session, so this is code/build-artifact investigation only, no runtime device test — that's deferred, see below.

**Investigated and reported before fixing, per the task's gate.** `barcode-detector` was already at `^3.2.1` in `package.json` (confirmed, no install needed — matches what's actually resolved: `zxing-wasm@3.1.1` underneath).

**1 — does `BarcodeDetector` exist in Android System WebView?** Genuinely unverifiable without a device, and said so rather than guessing either way: MDN's browser-compat-data lists `webview_android` as `"mirror"` for the `BarcodeDetector` interface, which is BCD's own shorthand for *"inferred from Chrome for Android's version (83+), not independently verified"* — not a confirmation. Real-world Shape Detection API availability inside a WebView **embedded in a third-party app** (this app's own process, not the standalone Chrome app) has been reported as inconsistent elsewhere, plausibly because the underlying Play Services ML Kit barcode model's on-device availability isn't guaranteed to match the host Chrome app's. `createDetector()` already picks native when present via `'BarcodeDetector' in window`-equivalent (`window.BarcodeDetector ?? PonyfillBarcodeDetector`) — deliberately left this selection logic alone rather than force the ponyfill preemptively on native Android, since that would trade away native's real speed/accuracy advantage on a guess. Instead, added a one-line log (`[BarcodeCameraScanner] detector path -> …`) so the very first device test gives a definitive, permanent answer to this exact question instead of another guess.

**2 — does the ponyfill's wasm actually load, and is it bundled/reachable in `dist-native`?** Checked concretely, not assumed:
- The wasm **is** correctly emitted into `dist-native/assets/zxing_reader-<hash>.wasm` by `build:native`, and **is** correctly copied to `android/app/src/main/assets/public/assets/` by `cap sync android` — confirmed by rebuilding fresh and finding the file in both locations. "Not bundled for the native context" is not what's happening.
- The built JS resolves the wasm via a root-relative URL (`/assets/zxing_reader-<hash>.wasm`, extracted directly from the minified output), which is the same URL shape every other bundled asset (`index.js`, `index.css`) already uses successfully in this app — nothing wasm-specific about the path construction.
- Read the actual installed `zxing-wasm` package source (not just its docs) to check for the well-documented Capacitor class of bug where a WebView serves `.wasm` with the wrong `Content-Type`, breaking `WebAssembly.instantiateStreaming()` (real, longstanding, multiply-reported on `ionic-team/capacitor`'s own issue tracker). `zxing-wasm`'s Emscripten-generated loader already wraps `instantiateStreaming` in a try/catch with a fallback to `fetch().then(r => r.arrayBuffer())` + non-streaming `WebAssembly.instantiate()`, which does not care about `Content-Type` at all — so this specific, well-known Capacitor gotcha should not actually break this library, even if it's present in this environment (it wasn't possible to confirm the WebView's actual header behavior without a device).
- Given this, "the wasm isn't bundled" (the literal claim in the task's own hypothesis) is not what's happening — it's correctly bundled and referenced. What's still open is purely a runtime question — does the `fetch()` actually succeed at that URL inside Capacitor's local WebView server — which needs the device test to answer. Added a log of the resolved wasm URL (`[BarcodeCameraScanner] zxing wasm locateFile -> …`) so a failed fetch shows up as an explicit mismatch against this logged URL rather than nothing at all.

**3 — do camera frames reach the decoder the same way as in the browser?** No evidence either way was found in code — `getUserMedia`'s constraints and the `readyState >= HAVE_CURRENT_DATA` gate are unchanged from the browser-proven version, nothing native-specific there. Added a one-time log of the first ready frame's `readyState`/dimensions so this is confirmed (or ruled out) on the same device test rather than left as a silent assumption.

**The actual code bug, found regardless of which of #1/#2/#3 turns out to be the device's real cause:** the scan loop's `catch {}` around `detector.detect()` was fully silent, on purpose, to treat "no barcode in this frame" as expected per-frame noise (correct — an empty `results` array is the normal no-match case and does not throw). But it also silently swallowed genuine failures — a wasm init rejection, a native API throw — making a **permanently broken decoder indistinguishable from normal scanning** with zero signal anywhere, which is exactly this bug's symptom. This is the one thing fixable with certainty without a device: it was always wrong, independent of which underlying cause turns out to be real.

**Fix (`BarcodeCameraScanner.tsx`), diagnostic-first as instructed:**
- `detector.detect()` failures are now caught, logged once per distinct error message (not every ~100ms, so a persistent failure doesn't flood logcat), and the loop continues exactly as before — no behavior change for the normal "no code in frame" case, only for the previously-invisible real-failure case.
- Three new one-time logs: which detector path was chosen, which wasm URL is in effect, and confirmation the first camera frame reached `HAVE_CURRENT_DATA`. Not temporary debug code to be reverted — this is the requirement 1 deliverable itself, meant to persist and answer the open questions above the next time this runs anywhere, not just once on a phone that's about to get looked at.
- Deliberately did not change `createDetector()`'s native-vs-ponyfill selection, add a runtime native→ponyfill fallback, or touch `vite.config.ts`/`capacitor.config.ts`/`AndroidManifest.xml` — nothing examined there needed changing, and guessing a behavior change on an unconfirmed cause would risk trading away a real capability (native's speed) for no proven benefit.
