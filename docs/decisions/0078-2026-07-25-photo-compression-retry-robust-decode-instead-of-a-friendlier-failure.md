## 2026-07-25 — Photo compression retry: robust decode instead of a friendlier failure

**Context:** the decode fallback from the earlier "Qorovul photo upload silent failure" arc (`createImageBitmap` → `<img>`+blob URL) turned a silent, invisible failure into a shown error, but didn't eliminate the underlying failure — certain real-phone photos still needed the user to reselect the same file two or three times before one attempt succeeded. `imageCompress.ts`'s `compressImage()` is shared by every `PhotoField.tsx` consumer (Qorovul's `GateStageForm`, Ombor's `IntakeAcceptForm`, both Laborator Tahlil forms) and Menejer's `KirimForm.tsx` (its own independent call to the same function) — one fix in the shared function reaches all of them.

**Investigated per the task's three candidate causes:**
- **HEIC/format rejection** — unlikely to explain the reported pattern. A format the decoder genuinely can't handle would fail the same way on every retry of the identical file; the reported symptom (succeeds after 2-3 *reselects of the same photo*) is inconsistent with a hard, deterministic per-file rejection.
- **Oversized dimensions exceeding a hard canvas/decoder limit** — same reasoning, would also be deterministic per file, not retry-sensitive.
- **A memory ceiling during full-resolution decode — the one consistent with "succeeds on retry."** Real phone camera captures run 4000-8000px on the longest edge; decoded to raw RGBA pixels before any resizing happens, a single image can be 100+ MB in memory. Both existing decode paths (`createImageBitmap` and `<img>`+`decode()`) decode at full source resolution — the resize to 1600px longest-edge only happens afterward, on canvas. A transient memory-pressure failure that clears by the next attempt matches the reported pattern exactly; a hard rejection does not. No device was available to confirm this directly (reasoned from the code and the reported pattern, as the task allowed), so the fix doesn't bet everything on this one diagnosis — see below.

**Fix (`imageCompress.ts`), addressing all three candidates at once rather than guessing which is real:**
- **Downscale before decode, for the leading (memory) hypothesis.** `decodeViaBitmap` now passes `createImageBitmap` a `resizeHeight` hint for files over 2MB (a zero-cost, size-based proxy for "likely a full-resolution capture," chosen specifically to avoid needing to decode first to check actual pixel dimensions). **Deliberately `resizeHeight` alone, never `resizeWidth` and `resizeHeight` together** — per spec, `createImageBitmap` only preserves aspect ratio when exactly one resize dimension is given; passing both stretches the image to fit that exact box whenever the source ratio doesn't already match, which would ship a visibly distorted audit-trail photo. Height, not width, because these are gate/intake/lab photos taken holding the phone normally (portrait) — height is already the longer edge there, so this directly bounds the true longest edge; for a landscape photo it still shrinks both dimensions together, just not to an exact bound. Gated behind the size threshold so a smaller image is never upscaled by the hint.
- **A third decode path, for the format/mechanism hypothesis.** `decodeViaDataUri` — same `<img>`/`decode()` pipeline as the existing fallback, but loaded via a `FileReader`-produced base64 data: URI instead of a `blob:` URL. A genuinely different loading mechanism, not a repeat of the existing fallback: if a failure is specific to how a given browser/WebView resolves a `blob:` URL rather than the image codec itself, a data: URI sidesteps that by handing the browser the complete file inline.
- **Automatic retry, for the transient-failure hypothesis directly.** All three paths are tried in order; if every path fails, the whole sequence repeats up to 3 times with a short pause between rounds, before finally propagating the error. This targets the *reported symptom* head-on — automates exactly the "reselect the same file two or three times" workaround the user was doing manually, so it resolves itself instead of costing a manual retry each time.
- **Logged, not silent, per path and round** (`console.warn('[imageCompress] <path> failed (round N/3):', err)`) — requirement 1's "add enough logging to identify it." If a real device still hits the fully-unrecoverable case after this fix, the logs show exactly which paths were tried, how many times, and what each threw — not just the final error `PhotoField`'s catch already logs.
- **The final resize/encode step (1600px longest edge, JPEG q=0.7, ~300KB target) is untouched** — same canvas/`toBlob` code as before, unreached by any of the above; requirement 3 is satisfied by not touching it, not by re-verifying it.

**Verified live in a real browser, not just reasoned — specifically the riskiest assumption (does a single-dimension resize hint actually preserve aspect ratio, or could it distort).** Generated real random-noise JPEGs (flat-color synthetic images compress far too efficiently to cross the 2MB threshold and don't exercise this path at all — caught that on the first attempt) at 3000×4000 and 4000×3000 through `createImageBitmap` directly: `resizeHeight: 2400` on the portrait file produced 1801×2400 (expected ratio 0.7500, actual 0.7504 — a 0.05% difference from integer pixel rounding, not distortion); on the landscape file it produced 3200×2400, exactly matching the source's 4:3 ratio. Confirmed the full `compressImage()` pipeline end to end on a normal-size synthetic image too. `PhotoField.tsx` itself is unchanged — same `compressImage()` call signature, same success/error handling — so this integration contract was never at risk.
