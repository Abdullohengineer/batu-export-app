## 2026-07-30 — Correcting mistaken entries: date/plate/driver editable from KIRIM/CHIQIM second windows

**Context:** A wrong date (the driving example) or plate/driver entered on a KIRIM order or CHIQIM request previously had no fix short of living with it — neither table has a delete mechanism, and CHIQIM's only existing mutation was void (kill the whole request). Added a scoped edit action to both second windows (`KirimOrdersList.tsx`, `FinishedChiqimList.tsx`), limited to fields nothing downstream reads for math.

**Investigation before coding, per the task's own gate.** Live schema/RLS checked directly (not the migration history, which is stale in places — `kirim_orders.serial` from 0003 was superseded by `order_id` in 0009/0011). Found `kirim_orders`/`kirim_lines`/`chiqim_lines`/`chiqim_line_pallets` had **zero UPDATE policy at all** — editing was impossible, not just unbuilt. `chiqim_requests` already had one (`menejer_voids`, 0033): `my_role()='menejer' AND ombor_finished_at IS NULL`, row-level, currently exercised only by the void handler. `kirim_orders.status` flips to `qabul_qilindi` only via a trigger on `gate_weighings.completed_at` (gate stage 2, `complete_kirim_stage2()`, 0013) — stage 1 alone leaves status at `kutilmoqda` even though dated/plated gate photos already exist by then.

**Field buckets, reported and confirmed with the user before writing any SQL:**
- Freely editable: `order_date`/`plate`/`driver` (KIRIM), `request_date`/`plate`/`driver` (CHIQIM) — nothing downstream reads these for a number.
- **Locked, user's explicit call:** `owner_id` on both. Feeds client report/stock-on-hand/yield grouping everywhere on KIRIM; on CHIQIM it additionally scopes the pallet picker — changing it after pallets are reserved would leave reservations pointing at the wrong client's stock. Not included in "freely editable" despite reading as a client-facing field.
- **Locked, not built this pass (flagged, not assumed):** `kirim_lines.declared_qty` (feeds `effective_qty` pre-intake and the Kam chiqdi check), `target_moisture_pct`/`target_so2_mg_kg` (feed lab-overdue exceptions and client-report target-vs-actual), `type_id`; `chiqim_lines.type_id/calibre_id/qty_kg`; `chiqim_line_pallets` reservations. None of these have any UPDATE policy — staying unwritable is what keeps them locked, no new grant touches them.
- Never editable: `serial`/`id` (PK), `status`, `declared_total`, `ombor_finished_at/by`, `voided_at/by`, `created_by/at`.

**Lock boundary, user's explicit call on KIRIM specifically.** CHIQIM reuses the existing void boundary exactly (`ombor_finished_at IS NULL`) — same UI condition, same RLS predicate, per the task's own "same logic as the whitelist" instruction. KIRIM had no precedent to reuse (confirmed: "kirim_orders/gate_weighings have no void mechanism regardless, same standing gap," 2026-07-28 entry). Two options presented: lock once `status` flips to `qabul_qilindi` (matches the literal enum, permits editing through all of stage 1), or lock the moment ANY `gate_weighings` row exists for the order (stricter — the instant Qorovul touches the order at the gate at all). **User chose the stricter option** — dated/plated gate photos already exist the moment stage 1 happens, and letting plate/date drift after that creates a paper-trail mismatch even though it corrupts no number.

**RLS applied** (`supabase/migrations/0038_kirim_chiqim_second_window_edits.sql`):
```sql
create policy menejer_edits on kirim_orders for update to public
  using (my_role() = 'menejer' and not exists (
    select 1 from gate_weighings g where g.order_id = kirim_orders.order_id and g.dir = 'kirim'))
  with check (my_role() = 'menejer' and not exists (
    select 1 from gate_weighings g where g.order_id = kirim_orders.order_id and g.dir = 'kirim'));

drop policy menejer_voids on chiqim_requests;
create policy menejer_updates on chiqim_requests for update to public
  using (my_role() = 'menejer' and ombor_finished_at is null)
  with check (my_role() = 'menejer' and ombor_finished_at is null);
```
`menejer_voids` renamed rather than left alongside a second, functionally-identical UPDATE policy — voiding was never its only real purpose, `handleVoid` and the new `saveEdit` both now go through `menejer_updates`. Both policies are **row-level, not column-restricted** — same acknowledged limitation as the existing `owners`/master-data grants (2026-07-21 entry): the UI is what limits the update payload to date/plate/driver, not the database. Documented explicitly rather than left unstated, matching this codebase's own established practice for every prior row-level grant.

**Audit trail — `audit_log` had existed since Phase 0, unused by any code path until now.** Every successful edit writes one row (`table_name`, `row_id`, `actor`, `action:'edit'`, `before`/`after` — only the fields that actually changed, not a full snapshot) using the table's existing schema and RLS (any signed-in INSERT, rahbar-only SELECT) — no new grant needed. Also auto-posts a human-readable note via the existing append-only `notes`/Qaydlar mechanism (`EntityNotes`'s backing table, already reused elsewhere) so the correction is visible to anyone looking at the order/request in-app, not just queryable by Rahbar. No history-viewer UI was built — that's queryable infrastructure now, a viewer screen is a natural follow-up if wanted, out of scope here.

**UI:** inline edit, same pattern `ClientsSection.tsx` already established (click Tahrirlash → fields become inputs in place → Saqlash/Bekor qilish), placed at the bottom of each row's existing expand panel. The Tahrirlash control simply doesn't render once the lock condition is met — mirrors `FinishedChiqimList.tsx`'s own pre-existing void-button visibility pattern exactly, not a new UI idiom.

**Verification.** `npx tsc -b --noEmit` and `npm run lint` clean (same one pre-existing unrelated `AuthProvider.tsx` warning), unit suite 78/78 unchanged. Live-browser-verified end to end, both directions: created a fresh KIRIM order, corrected its date from the second window, confirmed the DB row/`audit_log`/`notes` all updated correctly, confirmed the `Miqdori`/`effective_qty` display was untouched by the edit. Inserted a `gate_weighings` row for that order directly, reloaded, confirmed Tahrirlash no longer renders — **and separately confirmed the RLS itself refuses a direct `.update()` call from the browser's own `window.supabase` client** (`data: []`, no error — the same "blocked write returns zero rows" signature `chiqim-undo-scan.spec.ts` already established), not just a UI-level absence. Repeated the identical sequence for a CHIQIM request (correct date → verify → set `ombor_finished_at` → confirm both Tahrirlash and Bekor qilish disappear together → confirm RLS refusal directly). One incidental finding, not a bug: `useFinishedChiqimRequests.ts` filters out any request whose `plate` starts with `TEST-` by design (2026-07-25 "TEST- prefix hygiene") — a test request created with a `TEST-`-prefixed plate correctly never appeared in the CHIQIM second window at all; renamed the plate to verify the edit UI, unrelated to this task's own change. All test fixtures (KIRIM order, CHIQIM request, the inserted `gate_weighings` row, and their `audit_log`/`notes` rows) deleted afterward via direct SQL — neither table has an in-app delete path. **Out of scope, not touched (per the task):** the cutting line, opening stock, deleting/voiding requests (pre-existing), editing anything past its lock boundary, a history-viewer UI for `audit_log`.
