## 2026-08-02 — Opening stock, Stage 3 (the mint mechanism and re-washing)

**Context.** The last of the three opening-stock stages, and the one Rezka inherits: re-washing old washed stock requires consuming finished pallets and minting a new serial, which is structurally identical to Rezka source 2. Designed generic from day one. `supabase/migrations/0053_pallet_status_consumed.sql`, `0054_serial_mint_sources.sql`, `0055_mint_serial_rpc.sql`, `0056_get_serial_passport_mint_origin.sql`.

**The mint mechanism, split in two on purpose.** `mint_serial_from_sources(...)` is generic and knows nothing about Moyka — validate sources, mark pallets `consumed`, mint `kirim_orders`/`kirim_lines` with `origin='internal_reprocess'`, write `serial_mint_sources`, return the serial. Rezka calls it unchanged and sends its serial to cutting instead. `send_old_stock_to_moyka(...)` is a thin old-stock wrapper that calls it and then does the `wash_cycles` upsert, the `moyka_sends` insert and the origin note — **all in one transaction**, so a failure can never strand consumed pallets with no send behind them. Both are `security definer` because `kirim_orders`/`kirim_lines` are menejer-insert-only under RLS and Ombor is the actor; both therefore carry an explicit `my_role()` gate, since definer bypasses RLS entirely.

**Both source shapes built; only the pallet path wired.** `serial_mint_sources` carries an explicit `source_kind` discriminator with a check constraint enforcing exactly one populated shape. `old_kn_pools`' balance was generalized *today* to `opening_kg − Σold_kn_collections − Σserial_mint_sources(weight_kg)` in both `stock_on_hand_rows` and the RPC's own guard — the third term is always zero until Rezka calls it, but getting it right now is the difference between Rezka working and Rezka silently under-counting a pool. A partial unique index (`source_barcode2 where source_kind='pallet'`) is the real guarantee a pallet can be consumed once and only once; the RPC's `for update` pre-check just turns that race into a readable error instead of a 23505.

**🚩 Deviation from the sketched spec, taken deliberately: `source_pool_id`, not `source_pool_type_id`.** Pools are unique per *(owner, type)*, so matching a weight draw on type alone would over-subtract from every owner holding that type the moment a second client has KN. Pointing at `old_kn_pools(id)` is unambiguous and mirrors `old_kn_collections.pool_id`. Flagged before building and approved.

**`declared_qty` = the WEIGHED figure, not the book figure.** This is the load-bearing modelling choice. It keeps `yield_rows`' `raw_received == raw_consumed`, so wash loss is pure processing loss and no false `capped_serials` alarm fires when the scale happens to read over book. Storage loss stays derivable and never stored: `Σ(book weights via serial_mint_sources → finished_pallets) − moyka_sends.qty_kg`. Verified live at 60 kg on the test mint.

**Re-wash output gets `is_old_stock = false`** — contradicting a line written in Stage 1, deliberately. `true` would be wrong twice: the qoldig'i toggle is exclusive, so freshly produced sellable stock would vanish from *Joriy zaxira*, and its date would read "Eski zaxira 2025-2026" when it was produced today. Lineage lives in `serial_mint_sources`, the notes and the passport instead. Confirmed live: the new pallet reads `is_old_stock=false / bucket=available`.

**🔑 The rule that resolved a real contradiction in this stage's own design: `finished_pallets.status` is a CURRENT-LOCATION field, not a did-this-happen field.** It was initially flagged as a bug that `useMoykaOutput` keeps counting consumed pallets in a serial's `received`, while simultaneously arguing `yield_rows` should keep counting them so a finalized serial's loss never moves retroactively. Those conflict; the user caught it. Resolution — both keep counting, and the split is by *question asked*:

- "Where is this pallet **now**?" → must filter status: `stock_on_hand_rows`, `useAvailableFinishedStock`, `chiqimScan.resolveScan`, `get_client_report.client_pallets`, and `report_chiqim_rows` — which is precisely why that last one **was** a real bug and is fixed here: a consumed pallet fell through its `CASE` to `'omborda'`, a location claim that is false. New `'ishlatilgan'` branch added, plus the matching `PalletStatusFilter` value and Hisobot filter option.
- "What did this serial **produce**?" → must ignore status: `yield_rows.output` and `useMoykaOutput.received`. The pallet was genuinely produced; consumption is a later event in a *different* serial's life, and subtracting it rewrites history. Concretely, excluding it would also break on-screen arithmetic, since a finalized serial's `lossPct` is the **locked** `wash_cycles.final_loss_pct` — "sent 3,500 · received 2,900 · loss 17.1%" would silently become "received 2,400 · loss 17.1%".

`bekor_qilindi` is the exception that proves the rule: `useMoykaOutput` skips voided pallets because voiding *retracts the production event itself* ("this was mis-recorded"). Consuming asserts the opposite. Different meanings, different treatment.

**The timestamp-leak audit — every consumer traced, verified live on a real end-to-end mint.** Four earlier leaks (`yield_rows`, `rahbar_monthly_trends`, `wip_rows`, `get_client_report`) all came from Stage 1's *backdated* seed timestamps. A minted serial's timestamps are **real** (today), which is exactly why the correct treatment inverts: `opening_stock` must not count as processing, `internal_reprocess` must. Test mint `020826-040`: 2 Qand K6 pallets, book 1,040 kg, weighed **980**, output 890.

Loss reads **9.2%** from the weighed 980, not the 14.4% the book 1,040 would have produced — the test figures were chosen so the two are distinguishable. qoldig'i old-washed fell 52,210 → 51,170 kg (−1,040 book) and 79 → 77 pallets. `wip_rows` stays silent because `raw_not_sent` needs a `storage_intake` row (the mint deliberately creates none) and `provisional_weight` needs `provisional` (false without intake); `moyka_not_returned`/`awaiting_lab` would fire on a genuinely delayed re-wash, which is correct and wanted.

**Notes wiring.** Neither `LaboratorChiqimTab` nor the passport rendered notes at all before. Both now read the same generic `entity_type='moyka'` key the mint writes to, so there is one note, not three mechanisms. Verified live: the lab's Window-1 card shows *"Eski zaxiradan qayta yuvish: 2 ta eski pallet ishlatildi, kitob bo'yicha ~1040 kg, tarozida 980 kg yuborildi."* The finished-output lineage note is written at receipt in `OmborTayyorTab` against the serial (naming the barcode2 in the body) rather than a new per-pallet `entity_type` — deliberately, so it is readable in three existing surfaces immediately instead of being an orphan nobody displays. The passport renders notes read-only (it is a record, not a workspace); adding stays where the work happens.

**Passport.** New "Kelib chiqishi — qayta ishlangan" section, rendered FIRST for a minted serial because it *is* that serial's beginning and the Buyurtma/Darvoza sections below are near-empty for it by design. Shows source pallet count, book total, weighed sent, the explicit storage-difference line, and a per-pallet table (barcode2 · calibre · source serial · book kg). Omitted entirely for ordinary delivered serials, matching the passport's existing "missing shows nothing" rule.

**🐛 KNOWN DEFECT, logged not fixed — consuming a pallet retroactively alters closed-period client reports.** `get_client_report.client_pallets` filters `fp.status = 'in_stock'` with no as-of-date, so a pallet consumed (or voided) today silently drops out of *last month's* finished opening/closing figures too. This is pre-existing behaviour that voided pallets already exhibit, but Stage 3 makes it reachable routinely, and it lands on a **client-facing document**. A correct fix needs `client_pallets` to reconstruct status as-of `p_to` from event dates rather than reading the current flag. Out of scope here; recorded so it does not get lost.

**🚩 One real regression, caught by the suite and fixed in source.** The old-stock button was first rendered in its own wrapper div between the "1 · Yuborishga tayyor" heading and the serial list. `full-chain.spec.ts` locates that window's rows via `heading → following-sibling::div[1]`, so the new div silently displaced the list to `div[2]` and the spec stopped finding any row. Fixed by moving the button *inside* the existing list container (also better: one consistent `space-y-2` rhythm), not by editing the test. **Verified it was genuinely mine and genuinely fixed** by re-running: the failure moved from line 262 to line 318 — and line 318 then failed *identically on a clean `main` checkout*, proving that second failure is the long-standing pre-existing one this log has recorded at the same step across three prior task runs, not Stage 3 fallout.
