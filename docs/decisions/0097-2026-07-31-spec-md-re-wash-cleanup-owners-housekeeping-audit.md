### Part 2 — owners audit and delete

**FK picture, confirmed by two independent sweeps (`information_schema` join + `pg_constraint`/OID lookup):** exactly two foreign keys anywhere in the public schema reference `owners` — `kirim_orders.owner_id` and `chiqim_requests.owner_id`, both `NO ACTION`. No other table blocks a delete.

**Critical finding beyond the literal ask:** `public.owners` has row-level security enabled with no DELETE policy at all (`menejer_owners_insert`/`menejer_owners_update`/`read_all` only, confirmed live via `pg_policies`/`pg_class.relrowsecurity`). A DELETE issued as a normal authenticated app role affects zero rows regardless of FK state — owner deletion was deliberately removed from the app's RLS surface at some point, deactivate-only by design (per `tests/e2e/helpers/fixtures.ts`'s own comment). Only a service-role/superuser connection (this session's Supabase MCP access) can actually delete a row, and only after any referencing `kirim_orders`/`chiqim_requests` rows are cleared first.
