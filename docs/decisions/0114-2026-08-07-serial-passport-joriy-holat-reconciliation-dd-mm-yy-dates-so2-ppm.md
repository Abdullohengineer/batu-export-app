## 2026-08-07 — Serial passport "Joriy holat" reconciliation, DD-MM-YY dates, SO₂ → ppm

**Context.** Three-part task: (1) the passport was missing dispatch data after CHIQIM submission and had no current-state summary; (2) dates were inconsistent (13 `toLocaleString` calls, 6 hand-rolled formatters, raw ISO passthroughs) across the whole app; (3) the sulfur unit label needed to read "ppm" instead of "mg/kg" everywhere it's a display string.

**Part 1 investigation, reported and confirmed before building anything:**
1. **Dispatch data missing is a legitimate gap, not a query bug.** `get_serial_passport`'s dispatch section (`0056_get_serial_passport_mint_origin.sql`) was already correctly gated on `dispatch_manifest` existing — it never required gate-stage-2 completion. A request that has reserved this serial's material (`chiqim_line_pallets`/`chiqim_line_raw_serials`) but hasn't produced the completed event yet has nothing to show, which is correct, but the passport gave zero indication anything was pending — unlike the CHIQIM screen, which reads `chiqim_requests` directly. Fixed by adding a `pendingDispatches` section rather than touching the existing (correct) gate.
2. **The passport was an event log, never a balance.** It has `effectiveQty` (received) and `sends_total` (sent) as separate, never-netted fields, and never joined `old_stock_closeouts`, `old_kn_collections`, or `old_kn_pools.closed_at` at all (those postdate the passport's last edit, 0056, by up to 9 migrations). Old-KN collection is genuinely not applicable to a per-serial view (old-KN material has no serial — it only touches a serial via `mintOrigin`, already covered). Storage-loss close-out was the one real gap: exact per serial for `old_washed` (`finished_pallets.status`), a derived per-serial share for `old_raw` (the close-out itself only books a lump per owner+type).
3. **Why qoldig'i (`stock_on_hand_rows`) updates live and the passport didn't: not staleness — a genuinely missing calculation.** `stock_on_hand_rows` is a plain view, re-executed every read, independently joining the same tables the passport was missing.

**`joriyHolat`: two independent balances (raw, finished), each reconciling exactly, reusing not reimplementing.** `stillInStorageKg` on both sides is read directly from `stock_on_hand_rows` (`select ... where serial = p_serial`), not recomputed — raw balance already has two independent implementations (`stock_on_hand_rows` and `useMoykaSerials.ts`, see the "Old-stock reconciliation" entry above), and this must not become a third.
```
raw:      receivedKg = sentToMoykaKg + collectedRawKg + storageLossKg + stillInStorageKg
finished: returnedKg = dispatchedKg + storageLossKg + consumedKg + voidedKg + stillInStorageKg
```
Deliberately two equations, not one — raw-sent-to-Moyka vs. finished-returned has a real gap (wash yield loss, `yield_rows`' own domain). `consumedKg`/`voidedKg` are rare mint-consumption/void exits, included so the equation has no silent residual even for an edge-case serial. `currentPosition` (finished-goods-by-calibre) is folded into `joriyHolat.finished` rather than kept as a second, differently-scoped "Joriy holat" section — a side effect of reuse also fixed a real gap in the old version, which silently omitted any pallet awaiting a lab verdict or flagged for rewash from all three of its columns (`stock_on_hand_rows`' bucket split covers it for free).

**🚩 New sync hazard, same class as the raw-balance one, recorded per direct instruction.** `joriyHolat.finished.dispatchedKg` needed the genuine-dispatch predicate (`dispatch_manifest` + `gate_weighings.dir='chiqim'` + `completed_at is not null`) computed as a historical SUM, which `stock_on_hand_rows` (a current-balance view) doesn't expose — so it's copied verbatim a **third** time here, alongside `stock_on_hand_rows`' `pallet_rows` and `get_client_report`'s `client_pallets`. All three must be kept in sync by hand if this predicate ever changes. `supabase/migrations/0067_serial_passport_joriy_holat.sql`.

**Bug caught during this task, not in the SQL: a pre-existing frontend display bug, found via live fixture testing.** `SerialPassportModal.tsx`'s Moyka pallet-status column had a 3-way ternary (`omborda`/`band_qilingan`/else-"Jo'natilgan") that predates both `consumed` (`0053`) and `storage_loss` (`0064`) — a storage-loss or consumed pallet was silently mislabeled "Jo'natilgan" (dispatched), directly contradicting the new, accurate `joriyHolat` summary rendered right above it in the same modal. Not part of the original task's scope, but fixed here since it undermines the very accuracy this task is about — `PassportCyclePallet.palletStatus`'s type was also missing both values.

**Verification — a fresh disposable fixture (owner "TEST — Joriy holat verification (safe to delete)", serial `070826-001`) built to exercise every term, including the ones no real data has yet.** Checked first: no real (non-`TEST-`) serial in the live database has a `consumed` or `bekor_qilindi` finished pallet at all — the fixture built one of each deliberately, per direct instruction, rather than reporting a trivial `0=0`.

Excel exports (`reportExport.ts`, `clientReportExport.ts`, `yieldExport.ts`) now write real `Date` values with `numFmt='dd-mm-yy'` on every per-row date cell — sortable, not text. Three period-range header labels (single text cell, not a per-row column) left as text by design. Native `type="date"` inputs and the `YYYY-MM-DD` helpers feeding them untouched.
