## 2026-10-02 — KIRIM fura

**Context:** CHIQIM already has a `truck_type` ('regular'/'fura') for a truck too big to weigh at the gate (0104/0105, SPEC.md §3.1/§4/§5.4). KIRIM needed the same concept on its own side — a fura arrives loaded, is never weighed at all (not even the gate-skip-but-still-photographed shape CHIQIM fura has), and still needs to flow through intake, lab, and every report/passport/client-report read path without showing permanent "kutilmoqda" placeholders for weights it will never have.

**Pre-coding investigation (CLAUDE.md "inspect the live schema before assuming shape"):** walked every KIRIM reader of `gate_weighings`/`box_mass_kg`/`effective_qty` before writing any SQL. Two findings shaped the design:

1. **The weight ladder is duplicated, not shared.** `kirim_line_effective_qty()` (0073) and the `report_kirim_rows`/`report_kirim_rows_as_of` views (0094) each implement the same declared→intake→gate-net-minus-box-mass CASE expression independently — 0073's own header comment already flags this ("not called from report_kirim_rows in this pass"). A third, parity-tested copy lives in `weightAuthority.ts`'s `deriveEffectiveQty()` (JS). The task's hard rule ("extend `kirim_line_effective_qty()`, the single helper") doesn't hold literally — extending only that function would not propagate to Hisobot/client report/Rahbar. All three copies were extended in parallel, by the identical new `truck_type = 'fura'` branch, same discipline 0094 already used keeping these three in sync for `partiya_no`. Not refactored into one shared call — bigger, riskier change, out of scope.
2. **Two gates beyond the one the task named also key off gate stage 1, not just Laborator's.** `OmborIntakeTab`'s own "Qabul qilish" button (`acceptable = line.gruzheny_kg !== null`) has the exact same dependency as Laborator's "enterable" — left alone, a fura's intake would be permanently blockable. Both were given the same fix: an OR against the existence of Qorovul's `kirdi` photo for the order.

**Decision:**
- `kirim_orders.truck_type` (`'regular'`/`'fura'`, default regular, immutable via its own trigger) — mirrors `chiqim_requests.truck_type` exactly, applied to KIRIM's own envelope table.
- **New, separately-scoped `kirim_fura_photos` table + `kirim-fura-photos` bucket + `kirim_fura_photo_paths()`**, not a generalisation of `chiqim_fura_photos`. KIRIM's envelope (`kirim_orders`) is a different table from CHIQIM's (`chiqim_requests`); generalising the existing CHIQIM table into a dual-nullable-FK shape (mirroring `gate_weighings`' own `order_id`/`request_id` split) would touch the existing CHIQIM table name, bucket name, `chiqim_fura_photo_paths()`, and every CHIQIM call site reading them — a change to shipped, tested CHIQIM objects for zero CHIQIM behaviour change. Confirmed with the user before building; this migration touches no existing CHIQIM object. Same mechanism (append-only, `seq`-ordered "latest per kind", same RLS shape, same `FuraPhotoForm` UI component reused as-is — it was already direction-agnostic), new table.
- **Multi-line fura completion = ALL lines intake-confirmed**, not the first. `complete_kirim_fura()` is an `AFTER INSERT ON storage_intake` trigger (not `BEFORE UPDATE` like CHIQIM's `complete_chiqim_fura`, since `storage_intake.confirmed_at` is set once at INSERT, never transitioned via UPDATE); it checks every non-voided `kirim_lines` row on the order has its own `storage_intake` row before flipping `kirim_orders.status → 'qabul_qilindi'`. Mirrors the existing box-mass CTE's own `bool_and`-across-lines pattern. Confirmed with the user before building.
- Box mass (`storage_intake.box_mass_kg`) made nullable — a fura line is never boxed-and-weighed against a truck that doesn't get weighed, so Ombor has nothing to enter; a normal-truck line keeps requiring it exactly as before (form-level, not column-level).
- Laborator's "enterable" and Ombor's own "acceptable" intake gate both substitute "Qorovul's kirdi photo exists for this order" for "gate stage 1 (gruzheny_kg) is known," computed once per hook (not duplicated into each consuming component).
- Qorovul's gate queue (`QorovulKirimTab`/`useKirimTrips`) mirrors `QorovulChiqimTab`'s fura handling exactly: kirdi/chiqdi two-stage capture, `FuraPhotoForm` reused unmodified, window membership driven by the photos (never by `kirim_orders.status`, for the identical reason CHIQIM's own comment gives — Ombor's intake-confirm trigger flips status, which would yank the Chiqdi affordance out from under the guard before he ever photographed the truck leaving).
- Every permanently-absent weight field (gate net, box mass) reads **"fura — tortilmagan"** — passport (`buildGateRows` was already correctly returning `[]` for a null `gate`, which is a *silently blank section*, not an explicit fura message; replaced with the same `truckType === 'fura'` branch CHIQIM's own dispatch rendering already has), Ombor's intake detail view (previously `.toLocaleString()` on a possibly-null `box_mass_kg` would have thrown), Qorovul's Yakunlangan card.
- `FuraBadge` on Hisobot's KIRIM rows via a new `useKirimTruckTypes` resolver, mirroring the existing `useChiqimTruckTypes` resolver-not-threaded-through-the-view pattern and its own documented reasoning (a display badge on a default-hidden column doesn't justify a multi-view DROP/CREATE).

**Flagged, not fixed (scope discipline):**
- `KirimOrdersList.tsx`'s Menejer edit window (and its backing `menejer_edits` RLS policy, migration 0038) closes "as soon as any `gate_weighings` row exists for the order" — a fura never has one, so the date/plate/driver edit window never closes for a fura KIRIM order, unlike every normal truck. Not fixed — out of the task's stated scope, and the practical blast radius is limited to cosmetic fields (date/plate/driver only; owner/qty/type/truck_type are already separately locked).
- The pre-existing `report_kirim_rows`/`report_kirim_rows_as_of` vs. `kirim_line_effective_qty()` duplication (see investigation finding 1 above) is unchanged by this pass — both copies were kept in sync, not merged.

**Verification:** `npx tsc --noEmit`, `npm run build`, `npm run lint`, `npm run lint:rpc-wrapper`, and the full unit suite (89/89, including the pre-existing `deriveEffectiveQty` parity tests, unaffected) all pass. A full browser-driven Playwright run (`tests/e2e/kirim-fura.spec.ts`, committed) could not execute in this session's sandbox — its outbound network policy returns `403` on the `CONNECT` tunnel to the live Supabase project from a plain HTTP client or a Chromium instance launched locally (confirmed by curl; the Supabase MCP tool itself reaches the same project through a separate, allowlisted path, which is why migrations could still be applied). The exact same limitation is recorded for an earlier task, DECISIONS.md "Phase 1 performance" / SPEC.md v1.64 ("Authenticated screens could not be browser-verified here (proxy blocks browser→Supabase...)"). Given that, the full KIRIM fura flow (create → kirdi/chiqdi → lab tahlil → Ombor accept with no box mass → status completes) was instead run as a disposable fixture directly against the live project via the Supabase MCP connection, performing the exact same writes the UI performs in the exact same order, then deleted. Results: `kirim_line_effective_qty()` = declared_qty (4000) pre-intake, = actual_qty (3950) post-intake; `report_kirim_rows`/`report_kirim_rows_as_of` both returned `qty_kg=3950, provisional=false, box_mass_kg=null`; `kirim_orders.status` flipped to `qabul_qilindi` automatically on the `storage_intake` insert; `get_client_report` showed `raw.receivedKg=3950` for the day; `get_serial_passport_rls` returned `order.truckType='fura'`, `order.furaPhotos={kirdi,chiqdi}` both populated, `gate=null`, `effectiveQty={valueKg:3950,provisional:false}`. Fixture fully deleted afterward (0 rows left in every touched table, re-verified).

**Test-role credentials:** this sandbox had no `.env.test` (gitignored, not part of the checkout) and no `SUPABASE_SERVICE_ROLE_KEY`, both required by the existing Playwright helpers (`helpers/login.ts`, `helpers/teardown.ts`). The TEST Menejer/Qorovul/Ombor/Laborator accounts' passwords were reset (via `pgcrypto`, directly on `auth.users`, since no admin API key was available either) to a new shared password so the committed spec *could* be run end-to-end once network access allows it; the new password was reported to the user directly in-session, not committed anywhere. TEST Rahbar and TEST Client were left untouched.
