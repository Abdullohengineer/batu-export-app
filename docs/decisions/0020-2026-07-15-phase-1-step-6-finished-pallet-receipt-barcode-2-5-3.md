No `active` wash_cycles row is created before Tugallash — absence of a `final` row means still-active, which is enough. `wash_cycle` = 1 throughout (re-wash §2.13 is a later step).
**🚩 Spec gap found and resolved (SPEC §2.2 updated inline, not silently): Barcode #2 format needed a per-pallet uniquifier.** §2.2's `PLT-<serial>-<calibre>` collides when a serial yields multiple pallets of the same calibre — which "one sticker per physical pallet" + atomic pallets explicitly allow, and which "partial receipts across multiple saves" (the test plan) requires — because `finished_pallets.barcode2` is the PK. Resolved to **`PLT-<serial>-<calibre>-<seq>`** (`<seq>` = 1-based per serial+calibre; Konditirskiy → `…-KN-<seq>`). Marked/struck the old text in §2.2 and logged here per CLAUDE.md ("if a build reveals the spec text is wrong/superseded, update SPEC.md inline… never contradict silently"). `<seq>` is computed client-side from the already-loaded pallets; the `barcode2` PK is the concurrency backstop (single ombor manager, one-pallet-per-save → collision risk is low; a collision errors and the manager retries). Verified on local Postgres: two K4 pallets → `-04-1`, `-04-2` (no collision), Konditirskiy → `-KN-1`, and re-using a barcode2 fails the PK.
**🚩 `calibres` table is EMPTY on the real project — flagged, not silently seeded.** The receipt form's Kalibr dropdown reads `calibres` (filtered to the serial's category), but the table was never seeded (Administration §6.4 isn't built). Not seeding it in a migration: master data is Administration's domain and the project precedent (Step 1 owners/product_types) is user-seeds-via-SQL. Ready-to-run seed SQL is in the PR. **Reuse (CLAUDE.md).** `barcodeLabel.ts` refactored to a generic `renderLabel(code, fields)` with thin `renderBarcode1Label`/`renderBarcode2Label` wrappers; `Barcode2Display` mirrors `Barcode1Display`'s share/download. **Refactoring the label renderer surfaced a real bug:** Barcode #2's longer `PLT-…` code was being downscaled (nearest-neighbour) to fit 50×30mm, which destroyed the thin bars and made it **fail to decode**. At very large per-serial+calibre pallet counts the seq could lengthen the code further and re-tighten the bars — flagged for if it's ever hit.
