# 150926-003 — full reversal of Moyka send

## What this is

A requested, one-off reversal: undo the entire Moyka send that minted serial
`150926-003` (2,900 kg, sent 2026-09-15), restoring the consumed source
stock to where it came from. Nothing downstream had happened yet — no
`finished_pallets`, no lab verdict — so this is a clean rollback, not a
correction of a serial with real processing history.

## Reversal

Applied directly to the live project (`qohoqbapevrcjqxbstxi`) via
`supabase/migrations/0128_reverse_moyka_send_150926_003.sql`, in FK-safe
order inside one `DO $$ … $$` block (atomic — a single statement):

1. Re-checked the zero-downstream guards at apply time (not just at
   investigation time) — aborts rather than partially reversing if
   `finished_pallets`, `lab_results`, or `rezka_sends` now exist.
2. Captured a full pre-reversal JSON snapshot for the audit trail.
3. Deleted the `moyka_sends` row.
4. Deleted the `wash_cycles` active row (re-guarded: only if still
   `closed_at is null` and carries no lab data).
5. Restored the 5 source pallets to `status='in_stock'` (book weights and
   any pre-existing consumption rows untouched).
6. Deleted the 5 `serial_mint_sources` rows.
7. Deleted the `kirim_lines` row, then its now-empty dedicated
   `kirim_orders` row.
8. Wrote one `audit_log` entry (`table_name='kirim_lines'`,
   `row_id='150926-003'`, `action='manual_reversal'`) carrying the full
   before-snapshot and a plain-language reason.

No changes to `send_old_stock_to_moyka` or `mint_serial_from_sources`
themselves — this is a one-off data reversal, not a generalized "undo
mint" feature.

**Deliberately not touched:** the auto-generated `notes` row
(`entity_type='moyka'`, `entity_id='150926-003'`, id `d0502abe-…`) that
`send_old_stock_to_moyka` wrote at send time. It isn't FK-enforced and
isn't part of this reversal's required steps — flagged rather than
silently deleted; it is now an orphaned historical note pointing at a
serial that no longer exists.
