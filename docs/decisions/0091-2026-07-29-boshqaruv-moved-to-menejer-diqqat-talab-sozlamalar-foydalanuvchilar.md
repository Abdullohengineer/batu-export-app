## 2026-07-29 — Boshqaruv moved to Menejer: Diqqat talab, Sozlamalar, Foydalanuvchilar

**Context:** Rahbar's only write surface (§6.4 Boshqaruv: product-settings master data + threshold admin) plus its Diqqat talab exceptions view (§6.2) moved to Menejer wholesale — nav/routes removed from Rahbar, added to Menejer, content of all three screens unchanged. Explicitly framed by the user as a move, not a duplication: after this task Rahbar has no access to any of the three, and Menejer has full access.

**Investigation before touching anything, per the task's own explicit gate.** Diqqat talab turned out to need no RLS change at all: `rahbar_exceptions()` and the three other dashboard RPCs it and RahbarHome share were already `grant execute to authenticated` (0030) — role-named, not role-restricted, so Menejer could already call them; only the route stood in the way. Sozlamalar's four non-owners tables (`product_categories`/`product_types`/`calibres`/`settings_limits`) were genuinely rahbar-only via RLS — moving the screen without a policy change would have rendered it for Menejer with every save failing silently against RLS, exactly the risk the task called out. `owners` already had a Menejer grant from the original §3.3 build (`menejer_owners_insert`/`update`), unchanged by this task. Foydalanuvchilar turned out not to be an RLS case at all: `UsersAdminPage.tsx` never writes to `profiles` from the browser — it calls the `admin-users` Edge Function, which uses the `service_role` key (bypasses RLS entirely) and enforces its own hardcoded `callerProfile.role !== 'rahbar'` check. The real gate to move was Edge Function code, not a Postgres policy — stated precisely to the user rather than loosely calling it "RLS" throughout.

**Two things confirmed with the user before any write, both explicitly framed as open questions rather than assumed:**
1. **Does Rahbar keep the underlying write grants as an unreachable-via-UI safety net, or lose them entirely?** Surfaced the real stakes first: Rahbar has zero write policy on any operational table already (§2.12) — write access existed only inside Administration. Revoking the Administration grants too, not just the routes, makes Rahbar **fully read-only app-wide**, a real architectural shift worth deciding consciously, not as a side effect of a nav reshuffle. **User chose: revoke entirely.** Rahbar now has 6 remaining nav destinations, all read-only reporting/oversight screens.
2. **Should Menejer's Foydalanuvchilar access be full parity with Rahbar's today, or restricted from touching rahbar-role accounts?** Flagged a real, non-obvious security implication first: the Edge Function's authorization is all-or-nothing per **caller** role, with no concept of scoping by **target** role — an unrestricted grant lets Menejer `create-user` a brand-new rahbar account (role is a field the caller sends, checked only against the 5-role allow-list) and `reset-password` on any account including a real Rahbar's, unscoped. **User chose: full parity, no restriction** — accepted the tradeoff explicitly rather than having it default in silently.

**RLS applied** (`supabase/migrations/0037_menejer_admin_move.sql`, applied live and captured to a local migration file in the same session): dropped `rahbar_admin_{product_categories,product_types,calibres}_{insert,update}`, `rahbar_admin_settings_limits_update`, `rahbar_admin_owners_{insert,update}`; created the `menejer_admin_*` equivalents on the first four (settings_limits keeps its existing insert-policy-free shape — thresholds are still seeded by migration only, never created via UI). `owners` needed no new Menejer policy (already existed); just the Rahbar one dropped. **`rahbar_admin_profiles` (FOR ALL) dropped with no Menejer replacement** — confirmed via grep that no browser code writes to `profiles` directly (`useProfile.ts`/`useProfileNames.ts` are read-only), so nothing exercises it; a broad FOR ALL grant here would additionally let Menejer self-promote via a raw `profiles.role` update, a real privilege-escalation path nothing in this task required opening. Verified live before and after via direct `pg_policies` query, not assumed from the migration text.

**Edge Function changed and redeployed:** `admin-users/index.ts`'s caller check (`callerProfile.role !== 'rahbar'`) swapped to `'menejer'`, error message and doc comment updated to match, deployed via the Supabase MCP directly (this session's environment can reach the platform API, unlike the sandboxed CLI environment noted in the original 2026-07-13 entries — confirmed live, version bumped 13→14, status ACTIVE). `ALLOWED_ROLES` (the target-role allow-list for `create-user`) intentionally left untouched — full parity was the confirmed decision.

**Route gating confirmed genuine, not just hidden nav.** All three routes lived inside `/rahbar`'s single `RoleRoute allow={['rahbar']}`-guarded block in `App.tsx`; removing their nested `<Route>` entries removes the paths outright (they fall through to the catch-all role-home redirect), not just their nav links. Re-added under `/menejer`'s own `RoleRoute allow={['menejer']}` block, same gating pattern every other role already uses. Grepped `tests/` and the rest of `src/` for all three screens first — zero e2e coverage, nothing else in the codebase assumed Rahbar-only — so the move carried no hidden blast radius.

**Files relocated, not just re-routed** — `git mv`, so history follows: `src/pages/rahbar/RahbarExceptionsTab.tsx` → `src/pages/menejer/MenejerExceptionsTab.tsx`, `RahbarSettingsTab.tsx` → `MenejerSettingsTab.tsx` (both renamed to match), `ProductCategoriesSection.tsx`/`ProductTypesSection.tsx`/`CalibresSection.tsx`/`ThresholdsSection.tsx` (same names, new folder). Kept at the same `pages/<role>/` depth deliberately — same relative-import shape, zero import-path edits needed inside them, and consistent with this codebase's own convention that `components/` is reserved for pieces reused by *multiple* consumers (like `ClientsSection.tsx`, shared by Mijozlar and Sozlamalar) while single-consumer admin sections live under their owning role's `pages/` folder — these four are single-consumer (`MenejerSettingsTab.tsx` alone) both before and after the move, just under a different role. `UsersAdminPage.tsx` needed no move — already lived at the role-neutral `src/pages/admin/`. Stale "Rahbar-only" comments inside the moved files corrected to avoid misleading a future reader; historical mockup/rationale comments otherwise left intact.

**One accepted overlap, left alone rather than silently redesigned, since the task scoped out screen content changes:** Menejer now has both `/menejer/mijozlar` (existing, no-deactivate clients-only screen) and `/menejer/sozlamalar` → `ClientsSection allowDeactivate` (moved as-is, deactivate included) — two client-management surfaces with different permissions for the same role. This is a direct consequence of moving Sozlamalar unmodified while Mijozlar already existed independently, not something introduced by redesigning either screen; noted for awareness rather than fixed, since "only where they live and who can reach them" was the explicit scope.
