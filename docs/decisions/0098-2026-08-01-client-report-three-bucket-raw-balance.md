## 2026-08-01 — Client report three-bucket raw balance

**Context.** The client report and Ombor qoldig'i subtracted raw at different moments — qoldig'i at Moyka *send*, the client report at wash *completion* — so a serial mid-processing showed different raw figures on the two screens; a client reading their statement mid-processing saw more raw than physically existed. This exact gap had already been found and explicitly deferred as out-of-scope during the raw-dispatch task (2026-07-31 entry above, "Found and reported, not glossed over" — 1050 vs. 650 kg on the same fixture shape). Fix: three buckets instead of two — Xom (omborda), Moykada (in Moyka, not yet packed), Tayyor (finished) — both screens now subtract raw at send, so they agree, and material in transit is visible instead of vanishing.

**Approach — verified before applying, not a quick patch.** Per the task's own instruction (this function has one documented shipped loss-calculation bug, cited in its own migration header, and was rewritten twice already this session for Laborator-v2 and raw dispatch) and ultracode being on, the first SQL draft went through an independent verification workflow (schema review + reconciliation stress test, two parallel agents) *before* being shown to the user. Caught 3 blocking bugs and 4 minor issues in the draft — see below — none of which had reached the database.

**Bugs found and fixed pre-apply:**
1. `raw_closing_total`/`_by_type` and the new `moykada_total`/`_by_type` summed over every `client_lines` row unfiltered by period end — missing the `arrival_date <= p_to` bound `raw_opening_total`/`raw_received_total` already had. Fixed.
2. `stock_on_hand_rows` (qoldig'i) INNER JOINs `storage_intake` — a serial that's arrived but not yet formally accepted into raw storage is invisible in qoldig'i entirely. The draft had no equivalent gate, so a declared-but-not-yet-accepted line would count toward the client report's Xom but never appear in qoldig'i — closing one disagreement while opening a new one. Fixed: `client_lines` gained a `has_intake` flag (`storage_intake` existence), and Xom/Moykada/the new reconciliation object are all gated on it, matching qoldig'i's own join exactly. `receivedKg` deliberately stays *un*-gated — it answers "did the client's goods arrive," not "is it in tracked raw storage," a different question.
3. Exact equality with qoldig'i is architecturally scoped to `p_to = today`: qoldig'i is an unconditional live snapshot with no period concept at all; the client report is period-bounded. For a genuinely historical `p_to` the two answer different questions by design (balance as of that past date vs. balance right now) and will diverge if anything moved since — not a defect, and "fixing" it would mean making qoldig'i period-aware, which was explicitly out of scope. The user's own worked example is inherently a same-day scenario, so this covers the stated requirement.
4. (Minor, ruled out rather than fixed.) A theoretical divergence if a serial could be split across multiple `client_lines` rows — confirmed impossible in this schema: `kirim_lines.serial` is that table's own primary key, so `client_lines` (one row per `kirim_lines` row) always has exactly one row per serial.
5. (Minor, addressed via a new field rather than a UI patch.) An oversent serial (sent to Moyka beyond what it ever received) would floor Xom at 0 while Moykada stays unfloored, a display-level gap a client could notice by subtracting the shown figures themselves. Rather than a new warning banner, the new `reconciliation.balancesKg` field (below) surfaces this automatically — any oversend anomaly makes it go non-zero, extending the existing `capped_serials` mechanism's coverage to before Tugallash fires, for free.
6. (Minor, defensive.) Moykada's finalization gate now checks `wash_cycle_status = 'final' and finalized_at is not null` together, not `finalized_at` alone — confirmed the app's own Tugallash handler (`OmborTayyorTab.tsx:176-190`) already writes both atomically in one upsert, so this is belt-and-suspenders, not a behavior change.
7. (Minor, unchanged deliberately.) The `(finalized_at at time zone 'utc')::date <= p_to` cast carries the same Tashkent/UTC boundary edge case already present elsewhere in this codebase (`report_kirim_rows`' `gw.completed_at`) — left as-is, matching existing convention rather than introducing a one-off fix in only this function.

**New self-check, not just a one-time hand-verify.** Given the bug history, `get_client_report` now returns a `raw.reconciliation` object on every call: `totalReceivedKg`, `xomKg`, `moykadaKg`, `cumulativeOutputKg`, `cumulativeLossKg`, `cumulativeRawDispatchedKg`, and `balancesKg` (their difference — 0 when everything reconciles, non-zero flags a real anomaly). All five terms are cumulative-as-of-`p_to` and `has_intake`-gated identically, so they're apples-to-apples rather than mixing period-scoped and all-time figures. The reconciliation identity needed **five** terms, not three — an early draft check missed that raw dispatch is a distinct third exit path alongside Moyka processing and direct loss, and would show a false imbalance without it.

**Display/export (requirement 5).** `ClientReportRaw`/`ClientReportRawByType` gained `sentToMoykaKg`/`moykadaKg` (plus the new `ClientReportReconciliation` type). `ClientReportTab.tsx`: the raw balance chain now reads opening → +received → −sentToMoyka → −rawDispatched → =closing (Xom), followed by a bold Moykada line; the old processed/loss breakdown moved below as an informational block (still period-scoped by wash-completion date, unchanged), no longer part of the subtraction chain. byType table gained sentToMoyka/closing/moykada columns. Uz/Ru labels added (`sentToMoyka`, `moykada`); `dateBasisRaw` extended with a clause for the closing balance's new send-date basis. Excel export mirrors the UI restructure exactly, byType columns included. Reconciliation is not surfaced in the UI — it's an internal self-check field, not a user-facing requirement.

**Hand-verification against live seeded data.** Built directly via SQL under Nukus Agro Eksport (the owner already named in this log, and reconfirmed above, as the dedicated hand-computed-client-report-balance fixture) — non-`TEST-`-prefixed plates (`QA-3BUCKET-0801-A`/`-B`), since `report_kirim_rows` filters `TEST-%`. Two serials, `p_from = p_to = 2026-08-01` (today, matching the equality scope in point 3): serial A = 10,000 kg, 5,000 sent to Moyka, washing incomplete — the user's own exact worked numbers; serial B = 8,000 kg, 3,000 sent to Moyka *and* 2,000 raw-dispatched, exercising the mixed-exit-path case.
- Before Tugallash: `stock_on_hand_rows` → A: 5,000 kg, B: 3,000 kg. `get_client_report` → Xom A: 5,000, Xom B: 3,000 — **exact match**. Moykada A: 5,000, B: 3,000 (nothing packed yet). `reconciliation`: `totalReceivedKg=18000`, `xomKg=8000`, `moykadaKg=8000`, `cumulativeRawDispatchedKg=2000`, `balancesKg=0`.
- Tugallash fired on serial A: 4,500 kg packed, `final_loss_pct=10`. Re-queried: Xom **unchanged** at 5,000/8,000 (never touched by Tugallash, as designed); Moykada A dropped to 0, combined moykada 8,000→3,000 (exactly B's untouched amount); `processedBreakdown.lossKg=500`/`lossPct=10`/`calibreKg=4500`; `reconciliation.cumulativeOutputKg=4500`, `cumulativeLossKg=500`, `balancesKg=0` — the 5,000 kg cleanly resolved into 4,500 Tayyor + 500 loss, exactly the "loss comes out of the Moykada→Tayyor transition, not out of raw" requirement.
- `stock_on_hand_rows` re-checked post-Tugallash: still 5,000/3,000 raw_not_washed — confirms Tugallash never perturbs Xom on either screen.
- Fixture deleted afterward via direct SQL (same no-void-mechanism precedent as the raw-dispatch fixture) — all seven touched tables re-checked at 0 rows remaining.
