## 2026-07-25 — Camera scanner: aiming frame + on-screen scan feedback restored

**Context:** Android WebView camera scanning shows a full-screen live feed with no overlay — no aiming target, no visible confirmation of a scan's outcome. The browser version (before this session's earlier decoder rewrite) showed both. Decoder/camera-selection itself is confirmed working (separate, prior task) — this is purely the scanning UI.

**Item 1, confirmed via the actual removal commit, not assumed.** `git show 755746c` (this session, "Replace html5-qrcode with BarcodeDetector") shows the old `Html5Qrcode.start()` call passed `qrbox: { width: 280, height: 120 }` — html5-qrcode's own library code drew that as a dimmed-overlay-with-cutout directly into the DOM container it managed. The commit removed html5-qrcode entirely (confirmed necessary at the time: it never decoded a real printed CODE_128 label on hardware) and replaced it with a bare `<video>` element — taking the overlay-drawing with it. Nothing filled the gap; not tied to the WebView specifically, the same commit affects the web build too.

**Item 3, confirmed the feedback data path was never actually broken by that commit — a placement problem, not a missing-code problem.** `processBarcode` (`OmborChiqimTab.tsx`, untouched by 755746c — a different file) still sets `scanError` on every failure reason (duplicate/not-found/not-in-stock-covers-voided/not-lab-passed/claimed/wrong-line) and still updates `scannedByRequest` on success, driving the per-line progress bars and the running pallet count — all fully reactive before this task. The real problem: that feedback renders below the camera view and manual-entry form, off the operator's focus while aiming a phone. Combined with no aiming guide, a scan rarely lands cleanly, so correctly-wired feedback is rarely seen to fire — both symptoms share item 1's root cause.

**Implementation, `BarcodeCameraScanner.tsx`:**
- Video wrapped in a `position: relative` container (same `max-w-xs`/centering it already had, moved from the video element to the wrapper so overlay children align to its exact rendered box regardless of the video's own intrinsic aspect ratio).
- Aiming frame: centered rectangle, same 280:120 ratio as the old `qrbox` — a deliberate callback to the one dimension the previous, real UI already got right, not an arbitrary new proportion. Built with a `shadow-[0_0_0_9999px_rgba(0,0,0,0.35)]` spread-shadow trick (dims everything outside the rectangle) instead of clip-path/SVG — simpler, no extra DOM, well-supported. `pointer-events-none`, purely decorative.
- **Deliberately not cropping frames to that region for the decoder**, despite the task allowing it "if practical" — the native `BarcodeDetector`/ponyfill `detect()` call has no region-of-interest parameter; doing this for real would mean an extra canvas draw every ~100ms in the scan loop, which is the file's own explicitly off-limits territory (decoder logic, confirmed working). Recording the judgment call rather than silently skipping it.
- New `ScanFeedback` prop (`{ tone: 'ok' | 'problem'; message: string }`, exported type) renders as a banner pinned to the bottom of the video. Deliberately NOT reusing `toneStyles`' own bg/text pair for this — those are subtle/light colors meant to sit on a white card, and would be close to illegible overlaid on an arbitrary live camera feed. Uses solid, high-opacity colors instead (`bg-emerald-600/95`/`bg-red-600/95`, white text).

**Implementation, `OmborChiqimTab.tsx`:** new `scanFeedback` state (single flat state, not per-request — same reasoning as the adjacent, pre-existing `scanError`: only one request row is expanded/scannable at a time, per that state's own comment). A `showScanFeedback()` helper sets it and auto-clears after 2.5s (ref-tracked timeout, cleared on unmount too) so it doesn't sit stale once the operator moves on. Called from the exact two outcome points `scanError`/`scannedByRequest` already update inside `processBarcode` — reusing the identical message strings for failures, a new success message (`✓ Qo'shildi — {weight} kg`) that echoes the actual pallet weight just counted. Zero changes to `resolveScan`/any resolution logic — purely an additional presentation call alongside each existing one. The pre-existing below-camera `scanError` note is left exactly as-is (not removed) — a persistent record for anyone glancing back, complementary to the new fleeting on-camera banner, not a duplicate to eliminate.

**Verified live — camera hardware unavailable in this sandboxed Browser pane (confirmed: `getUserMedia` is blocked, same standing limitation as every camera task this session), so verification used a different, still-real method: logged in as `test-ombor`, opened Skladdan CHIQIM, expanded a real in-progress request, clicked "Kamerani yoqish."** The `cameraError` fallback path rendered correctly with zero crash, proving the new overlay markup survives the no-camera case. Then inspected the actual computed DOM/CSS directly (not assumed from the source): wrapper 320×150, aiming-frame box 256×110 — 256/320 = 80% exactly, 256×(120/280) ≈ 110 exactly, confirming the aspect-ratio CSS computes correctly; `box-shadow` and `border` matched the intended mask/border values. Resized to mobile (375×812): frame box 239×103, still 80%-of-wrapper and still aspect-correct — requirement 4 holds at phone width. Feedback banner verified for both outcomes via the manual-entry path (which calls the identical `processBarcode`/`showScanFeedback` as the camera path): an invalid code produced `bannerFound: true, text: "Bunday barcode topilmadi.", bg: red/95%, color: white`; a real, available Isfara/Kalibr-7 pallet (`PLT-210726-011-07-1`, queried live via SQL, verification-only — never finalized, removed via the existing undo button before moving on) produced `text: "✓ Qo'shildi — 2,400 kg", bg: emerald/95%`, and the page's own progress bar/pallet-count/running-total all updated in lockstep (`2,400 / 2,400 ✓`).
