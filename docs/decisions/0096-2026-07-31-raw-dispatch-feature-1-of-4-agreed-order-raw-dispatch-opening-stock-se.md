## 2026-07-31 — Raw dispatch (feature 1 of 4, agreed order: raw dispatch → opening-stock seed → Rezka → KN origin)

**Context.** A client can collect raw (unwashed) material directly on a CHIQIM request — e.g. half a load washed, half taken raw. Washing-path raw only; raw KN destined for cutting (Rezka) is explicitly out of scope, per the earlier inspect-and-plan report on Rezka/raw-dispatch/KN-origin. Built against the confirmed design from that report's own point 3, with two schema/SQL checkpoints reviewed and confirmed by the user before applying (raw-balance approach + `calibre_id` handling; then `report_rows`/`get_client_report`), per this task's own "show all SQL and wait for confirmation" instruction.

**A — Generalized raw-balance arithmetic, built once.** New sibling table `raw_dispatch_lines` (id, chiqim_line_id, serial, weight_kg, box_mass_kg, `net_kg` generated as weight−box_mass, loaded_at, created_by) — shaped like `moyka_sends`, not a generic `raw_exits` table with a destination enum: the two exits share almost no columns (raw dispatch needs box mass + a line link `moyka_sends` has no use for), and this codebase already keeps `dispatch_manifest`/`chiqim_line_pallets` as separate purpose-shaped tables rather than one polymorphic reservation table. `useMoykaSerials.ts` — the ONE hook every consumer already reads — gained a third fetch and `available = max(0, inputKg − sent − rawDispatched)`; both the Moyka send screen and the new CHIQIM raw picker (`ChiqimForm.tsx`) read this same hook, so they can never compute two different numbers for the same serial's balance. Two view-level fixes found while tracing every existing "Σ moyka_sends" consumer, not in the literal ask, flagged before touching: `stock_on_hand_rows`' `raw_not_washed` bucket and `wip_rows`' `raw_not_sent` CTE both needed the identical `− raw_dispatch_lines` term, or they'd silently overstate raw stock/WIP once any of it had been raw-dispatched instead of sent to Moyka. `yield_rows.raw_consumed_kg` deliberately left at `Σ moyka_sends` only — yield measures process loss for material that actually went through Moyka; raw collected directly bypasses washing and correctly never enters that calculation.

**B — `calibre_id` handling.** `chiqim_lines.calibre_id` made nullable; new `raw_serial text references kirim_lines(serial)`; check constraint enforcing exactly one of the two is set (`chiqim_lines_calibre_xor_raw`) — not a separate line-kind column, since `raw_serial is not null` already unambiguously means "raw line" and doubles as the pointer to its source serial, mirroring how a finished line's own identity lives in what it points to (`chiqim_line_pallets`), not a redundant tag. `qty_kg` stays required for both kinds — for a raw line it's Menejer's planned figure, never overwritten once Ombor loads; the actual collected amount lives in `raw_dispatch_lines`, read separately. Ripple: 8 files actually touched `chiqim_lines.calibre_id` or its derived TS types (`ChiqimForm.tsx`, `OmborChiqimTab.tsx`, `FinishedChiqimList.tsx`, `useOmborChiqimRequests.ts`, `useFinishedChiqimRequests.ts`, `useChiqimTrips.ts`, `chiqimScan.ts`, `chiqimScan.test.ts`) — every other calibre_id/calibreId match in the initial 38-file grep was `finished_pallets.calibre_id` (always non-null, no ripple).

**C — Ombor's raw entry, and the confirmed decision on when it's written.** Weight + box-mass inputs, no scan zone, no `dispatch_manifest` row — a genuinely distinct render branch inside `OmborChiqimTab.tsx`'s existing request card, not a forced-generic line renderer. **Confirmed with the user before building:** entries are held client-side (`rawDraftByRequest`, same shape as the existing `scannedByRequest` scan list — editable/removable via a Tozalash ✕ button) and only batch-inserted into `raw_dispatch_lines` at `Yuklashni yakunlash`, the same commit point `dispatch_manifest` already uses. This is *why* `raw_dispatch_lines` is safely append-only with no update/delete policy — a typo is corrected by clearing the draft pre-commit, not by editing a written row; an immediate-write design would have made a typo permanently corrupt that serial's balance. Ombor's entered net is **authoritative immediately** — a second explicit decision, confirmed via `AskUserQuestion` over the alternative (gate-net-derived, provisional-then-final, cloning `weightAuthority.ts`'s KIRIM shape) — because CHIQIM's real gate weighing already treats gate net as a reconciliation check on the manifest total for pallets, never a value source (SPEC §5.4); making raw symmetric with that existing rule avoided a second weight-authority-shaped system for a benefit (gate-verified raw figures) the original task text only mentioned once, in passing.

**Over-collection warning (2026-07-31 feedback).** Nothing stopped Ombor entering more raw than a serial had left — `max(0, ...)` floors the balance and the excess would vanish with no record. Fixed with a non-blocking warning (same `useMoykaSerials` hook, so it can never disagree with the picker/balance shown elsewhere): a persistent "Bu seriyada qolgan: X kg" caption plus a `StatusNote` when the entered net exceeds it. Never blocks, matching this app's warn-never-block convention everywhere else (Kam chiqdi, Tugallash warnings, CHIQIM shortfall).

**D — Lab gate.** Confirmed true by construction, no RLS change needed: raw dispatch never touches `finished_pallets`/`wash_cycles`, and the hard gate (`ombor_writes` INSERT policy on `finished_pallets`) only guards Barcode #2 assignment — raw never reaches that table at all.

**E — Reporting.** New `report_rows` kind `chiqim_raw` (one row per `raw_dispatch_lines` entry, same granularity convention as the other two kinds), unioned via a new `report_raw_dispatch_rows` view; reuses the existing `'jonatilgan'` pallet-status vocabulary rather than inventing a raw-only status, so the Hisobot status filter picks it up for free. `get_client_report` gained a third closing-balance term (`closingKg = opening + received − processed − rawDispatched`, both total and per-type) and a new `raw.dispatches` array — deliberately a **sibling** to the existing (pallet-based) top-level `dispatches`, never merged, so raw-taken and washed-and-collected stay visually distinct per the task's own requirement. Passport gained a parallel `rawDispatches` array, same headline+FieldTable pattern, its own section under Jo'natishlar (omitted entirely when empty, matching every other "missing shows nothing" section on that screen).

**`total_kg_tara` split, not left ambiguous (2026-07-31 feedback).** `report_totals`' single `total_kg_tara` summed KIRIM tara (boxes in) and raw-dispatch tara (boxes out) — unrelated quantities that happen to share a column, correct on a direction-filtered view but meaningless summed together on "both." Split into `total_kg_tara_in`/`total_kg_tara_out`; `TotalsStrip.tsx` now shows both labeled figures instead of one merged "Tara," and the Excel export gained a second tara row.

**🐛 Real bug found and fixed during hand-verification, not by inspection.** `report_filtered_rows`' direction predicate was `p_direction = 'both' or r.kind = p_direction` — selecting the CHIQIM direction specifically (one of only three Hisobot options) requires `r.kind = 'chiqim'` exactly, which `'chiqim_raw'` never satisfies. Confirmed live against seeded fixture data: `report_totals('chiqim', ...)` returned `total_count=0` against rows `report_totals('both', ...)` correctly counted — raw dispatch rows would have silently vanished from Hisobot the instant anyone filtered to CHIQIM specifically, the single most likely filter choice, not an edge case. Fixed (`0045_raw_dispatch_direction_filter_fix.sql`): `r.kind = p_direction or (p_direction = 'chiqim' and r.kind = 'chiqim_raw')`. Re-verified: `report_totals('chiqim', ...)` now returns the correct `total_count=2`/`total_kg_out=550`/`total_kg_tara_out=40` for the same fixture.

**🚩 Flagged for the future, per the user's own instruction.** `raw_dispatch_lines.serial` FKs to `kirim_lines(serial)` — the same constraint the Rezka inspection report identified as needing to move to a serial-identity anchor table once Rezka source-2 (cutting-batch-minted serials with no `kirim_lines` row) lands. Fine today — every serial that can raw-dispatch arrived by a real truck — flagged here so the re-pointing isn't a surprise when Rezka is built.

**Hand-verification against seeded data (before cleanup).** Built a live fixture directly via SQL under the codebase's existing dedicated QA owner ("Sinov Mijozi QA") — a **non**-`TEST-`-prefixed plate (`QA-RAWDISPATCH-0731`) deliberately, since `report_kirim_rows`/`stock_on_hand_rows`/`report_raw_dispatch_rows`/`get_client_report` (via its join to `report_kirim_rows`) all filter `TEST-%` plates, which would have made the fixture invisible to exactly the arithmetic being checked. One KIRIM order, two lines/serials (1000 kg and 600 kg, both non-provisional — gate + box mass both known), a partial Moyka send (400 kg on the first serial only, deliberately matching the task's own "partial Moyka send plus partial raw dispatch on one serial" scenario), and one CHIQIM request mixing two raw lines (one per serial: 300 kg / 250 kg planned, entered as 320−20 and 270−20 kg to also exercise the box-mass subtraction) — directly testing "a truck taking from two serials leaves the right remainder on each."
- `stock_on_hand_rows`: serial 1 → 300 kg (1000−400−300 ✓), serial 2 → 350 kg (600−0−250 ✓) — each serial's own remainder correct.
- `get_client_report`: `receivedKg=1600`, `rawDispatchedKg=550`, `closingKg=1050` — `0+1600−0−550=1050` exactly; the formula itself is correct.
- **Found and reported, not glossed over:** `get_client_report`'s `raw.closingKg` and `stock_on_hand_rows`' raw bucket do **not** agree in this exact scenario (1050 vs. 650 combined) — and this is pre-existing, not something raw dispatch introduced. `get_client_report`'s `processed` term only fires once a wash cycle's `completed_date` lands (i.e., once washing *finishes*), so the 400 kg already sent to Moyka but not yet washed-complete still counts as "raw" in the client report's balance; `stock_on_hand_rows` instead subtracts the moment material is *sent* to Moyka, since from then on it's a different WIP state (`wip_rows.moyka_not_returned`), not "in raw storage." Confirmed pre-existing by checking the identical gap exists with the raw-dispatch terms removed entirely — the two views have always measured different things ("not yet turned into output" vs. "not yet sent anywhere"). Raw dispatch's own new term is symmetric and correct in both models; it neither introduces nor fixes this gap, and fixing it is out of scope for this task.
- `report_raw_dispatch_rows`/passport/`report_totals`: all matched expected values exactly (see the bug entry above for the one real miss, now fixed).
Fixture deleted afterward via direct SQL (not voided) — `kirim_orders`/`kirim_lines`/`storage_intake`/`moyka_sends`/`chiqim_requests`/`chiqim_lines`/`raw_dispatch_lines` all have no void mechanism (a gap this codebase has flagged before, 2026-07-17 entry), and this was one-off verification scaffolding created and deleted within the same turn, not a regression fixture meant to persist — flagged here rather than silently deleted without a trace in this log.
