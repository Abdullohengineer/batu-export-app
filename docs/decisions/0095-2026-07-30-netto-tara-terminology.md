## 2026-07-30 — Netto/Tara terminology

**Context:** Box mass (tara) was already captured per-serial at intake (`storage_intake.box_mass_kg`, since v1.10's §2.16 amendment) and already used internally in the net-weight calc, but was never displayed on its own anywhere — report tables and the serial passport both only ever showed a single net-ish figure, with no visibility into what was subtracted to get there.

**Part 1 determination, checked before writing anything.** `storage_intake` is already joined in `report_kirim_rows` (as `si`) for the existing order-level `total_box_mass_kg` truck-variance CTE — but that's a different, order-level aggregate (summed across every line of a multi-line truck), not this serial's own tara. `si.box_mass_kg` was sitting right there, unselected. `get_serial_passport`'s `intake_row` already does `select * from storage_intake`, so `ir.box_mass_kg` was likewise already available, just not surfaced in the `intake` jsonb object. Confirmed both before writing the migration — purely additive, no new joins needed anywhere.

**A real mislabelling found and fixed before writing any passport code, not assumed from the task text.** The task's literal wording ("rename net/aniq labels to Netto") would have meant renaming the passport's existing "Net" row (`gate_weighings.net_kg`) straight to "Netto." Checked the schema first: `net_kg` is a **generated column**, `gruzheny_kg - pustoy_kg` (loaded minus empty) — it never subtracts box mass. Calling that "Netto" once a real Netto (net of tara) row existed one line below it would have been actively misleading, not just imprecise. Raised this via `AskUserQuestion` rather than guessing or silently deviating from the literal instruction. **User's ruling, verbatim:** *"if it's loaded - emptry, add it as 'Brutto'. if it's loaded- emptry - box mass, then it's netto"* — adopted exactly as the terminology for both the passport and (for consistency) one piece of pre-existing prose in the Buyurtma section that used the word "netto" to describe the same raw gate figure (`"ko'p turdagi reys, darvoza netto hech qachon qabul qilinmaydi"` → corrected to `"darvoza brutto"`).

**Design decisions:**
- **Report tables (Hisobot + Ombor qoldig'i, both Menejer and Rahbar):** "Miqdor, kg" → **NETTO** is a header-only rename (the underlying value, `effective_qty`, was already net — §2.16 — nothing about the number changes). New **TARA** column reads `report_rows.box_mass_kg` (added to `report_kirim_rows`; hardcoded `null` in `report_chiqim_rows`, since a finished pallet's own weight has already had its serial's box mass deducted upstream at the raw stage — it has no tara of its own to show). `—` for any row with no box mass on file (not yet accepted by Ombor, or CHIQIM). Same treatment applied to `stock_on_hand_rows` and the Excel export (`reportExport.ts`) for consistency with the on-screen table, since it exports the same rows — a judgment call, not explicitly asked, flagged as such when reporting back.
- **Totals strip:** user explicitly confirmed adding a **Tara** total (*"Yes, add a Tara total"*) alongside the existing Kirim/Chiqim/Neto figures. `report_totals`'s return shape gained a 4th column (`total_kg_tara`), which required an explicit `DROP FUNCTION` before recreating it — Postgres refuses `CREATE OR REPLACE` when a function's `RETURNS TABLE` shape changes (`42P13`). Confirmed the whole multi-statement migration rolled back atomically on the first failed attempt (re-queried `information_schema.columns` and found zero partial changes) before reapplying with the fix.
- **Serial passport — KIRIM Darvoza section only** gains the three-row breakdown (Brutto → Tara → Netto, in that reading order, loaded/empty rows first) — deliberately **not** added to the dispatch gate blocks in Jo'natishlar, since a dispatched pallet's weight has no box mass left to subtract (already gone at the raw stage) and adding an always-empty Tara/Netto pair there would just be noise. `buildGateRows` took an optional 5th `taraKg` param for this reason: omitted entirely (`undefined`) at the Jo'natishlar call site → Brutto rename only; passed (`intake?.boxMassKg ?? null`) at the Darvoza call site → full three-row breakdown, with `—`/"kutilmoqda" fallbacks for a serial whose gate data exists but whose intake hasn't happened yet (gate happens before intake in the KIRIM flow, so this is a real, not hypothetical, ordering).
- **Qabul qilish:** "Aniq (Ombor)" → **Netto (Ombor)** (confirmed correct, not just assumed, by reading `IntakeAcceptForm.tsx`'s own pre-existing code comment: *"§2.16 box mass (KIRIM only): net product = darvoza netto − quti massasi"* — `actual_qty` already represented a net-of-product reading conceptually). New **Tara** row added directly below it, same `box_mass_kg` value the Darvoza section's Tara row shows (same serial, same source column — deliberately the same number in both places, not two independent reads).
- **Deliberately out of scope:** `OmborHisobotlar.tsx`/`IntakeDetailView.tsx` (Ombor's own separate operational history/detail screens, not named in the task — only "Ombor qoldig'i", "Menejer/Rahbar reports", and "serial passport" were), and `ReportRowCard.tsx` (the phone-width card view of the same Hisobot data) — it has no literal "Miqdor" header text to rename (the qty renders inline in a compact one-line summary), and the task's own testing checklist didn't call out mobile cards. Flagged, not silently dropped.

**Verification.** `npx tsc -b --noEmit` and `npm run lint` clean (same one pre-existing unrelated `AuthProvider.tsx` warning). Unit suite 80/80 (78 pre-existing + 2 new: `boxMassKg` mapping for KIRIM rows with and without a box-mass value, and the CHIQIM-always-null case) — also had to backfill `box_mass_kg: null` into the two `ReportDbRow` test fixture builders in `reportQuery.test.ts` once the field became non-optional on the type.
