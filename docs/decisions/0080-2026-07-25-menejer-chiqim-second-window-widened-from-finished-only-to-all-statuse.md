## 2026-07-25 — Menejer CHIQIM second window: widened from finished-only to all statuses

**Context:** Menejer's CHIQIM tab second window (`FinishedChiqimList.tsx`) only ever showed `status='olib_ketildi'` requests. Task asked to widen it to show new/pending and in-progress requests too, newest-first, matching the universal second-window pattern — but explicitly gated coding on confirming whether the exclusion was deliberate first.

**Inspected and reported before coding, per the task's gate — the exclusion was deliberate, not an oversight, confirmed from the code itself before asking.** `useFinishedChiqimRequests.ts`'s own header comment already asserted the single-status filter was "complete, not partial." Tracing further back, two separate DECISIONS.md entries confirm it was a considered design choice, not a gap: **2026-07-17 "Step 7 prompt 1"** — *"No requests-list was built for the CHIQIM tab: re-reading §5.4, 'Dashboard Window 1: requests ready to load' belongs to Ombor's own screen, not Menejer's"* — and **2026-07-18 "Step 7 prompt 4"** (closing Step 7) — the finished-only hook was built exactly as designed, same single-equality-filter reasoning. Stopped and reported this history rather than assuming it was safe to widen; user confirmed proceeding after review.

**A second, related finding surfaced during inspection: `order_status` has 4 values, but `chiqim_requests` only ever carries two in practice.** The only status transition ever applied is `kutilmoqda → olib_ketildi` (the stage-2 gate trigger, `complete_chiqim_stage2`, 0020) — `qabul_qilindi`/`yakunlandi` belong to KIRIM's lifecycle and are never written here. So "in-progress" (Ombor actively scanning/loading) isn't a distinct `status` value — that phase lives in `dispatch_manifest`/`ombor_finished_at`, not this column. Reported this rather than silently building a 3-state pill that the schema can't actually produce; proceeded with a 2-state pill (Kutilmoqda/Olib ketildi), matching how `KirimOrdersList.tsx` — Menejer's own sibling second window for KIRIM, using the same enum — already handles it (2 real values mapped, same shape).

**Implementation — `KirimOrdersList.tsx` used as the direct template throughout, not a new pattern invented:**
