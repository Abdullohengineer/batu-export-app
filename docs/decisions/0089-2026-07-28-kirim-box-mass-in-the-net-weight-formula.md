## 2026-07-28 — KIRIM box mass in the net-weight formula

§2.16's net formula was product + boxes, not true product: `effective_qty` (single-line, final) read straight off `gate_weighings.net_kg` (`gruzheny_kg − pustoy_kg`), which is whatever the scale weighed — boxes included, since the gate weighs the whole physical load at once. Real formula: `net product = gate loaded − gate empty − Σ(box mass across the truck's lines)`. KIRIM only, by design — CHIQIM ships finished pallets whose weight is already atomic and fixed (§5.4); there is no box-mass concept on the dispatch side, and nothing here touches `chiqim_requests`, CHIQIM gate stage 2, or dispatch net.

**Where box mass lives.** `storage_intake.box_mass_kg`, mandatory, `check (box_mass_kg >= 0)` — `storage_intake` already *is* "the intake/line record" (PK = serial), and box mass is entered by Ombor at the same accept-time moment as `actual_qty`, so "line accepted" and "line's box mass known" are the same event. Table was empty at migration time (this session's own clean-slate wipe, above), so `NOT NULL` needed no backfill.

**`gate_weighings.net_kg` is untouched** — still the generated `gruzheny_kg − pustoy_kg`, still what Qorovul's own gate screens (`GateStageForm.tsx`, `useGateHistory.ts`, `useKirimTrips.ts`) show, still directly evidenced by the two mandatory scale photos. Box mass is subtracted one layer up, only in the weight-authority derivation, producing a **true net** = `gate_weighings.net_kg − Σ box_mass_kg` that replaces raw `net_kg` everywhere it was being read as the truck's product total: the single-line final `effective_qty`, `truckVariance` (declared vs. gate — was silently biased by the box weight every time, since `declared_qty` is a product-only client claim and raw `net_kg` isn't), the multi-line `lineReconciliation` (sum-of-lines vs. truck total — same bias), and `provisionalVarianceFlag`. No double-counting: `declared_qty`/`actual_qty` were never box-inclusive to begin with (Ombor splits/estimates, doesn't weigh), so box mass is subtracted exactly once, only where raw `net_kg` is read as a truck product total. Multi-line per-line `effective_qty` stays `storage_intake.actual_qty` — unchanged §2.16.1 rule, box mass never leaks into it, only corrects the truck total it's reconciled against.

**Two independent pending inputs.** `deriveEffectiveQty` (`weightAuthority.ts`) gains `totalBoxMassKg: number | null` — `null` until *every* line on the order has been accepted (mandatory field makes "accepted" and "this line's box mass known" the same event; the order-level total isn't complete until every sibling line clears that bar too). Finalization now requires `gateStage2Done && totalBoxMassKg !== null`; either can arrive first. Result gains `pendingOn: { gate, boxMass }`, surfaced through a new shared `pendingLabel()` helper (same file) so `OmborIntakeTab.tsx` and `KirimOrdersList.tsx` — the two live screens reading the TS layer directly — show "tarozi kutilmoqda", "quti massasi kutilmoqda", or both, instead of the old one-size-fits-all text. The six reporting-engine-driven screens (`SerialPassportModal`, `ReportTableRow`, `ReportRowCard`, `KirimRowDetail`, `reportExport.ts`, `OmborMoykaTab.tsx`) deliberately keep the coarser "provisional" text — extending them means growing `report_kirim_rows`' column shape for a UI nuance, scoped out and flagged to the user before coding rather than done silently.

**The SQL twin.** `report_kirim_rows` (a Postgres view) is a second, independent implementation of the same `effective_qty` rule — see `report-effective-qty-parity.spec.ts`'s own header, which exists specifically to catch the two drifting. Migration `0034_kirim_box_mass.sql` adds a `box_mass` CTE (`bool_and(si.serial is not null)` gates the sum to `null` unless every line is accepted, mirroring the TS side's own aggregation) and threads `gw.net_kg - bm.total_box_mass_kg` through every branch that used to read raw `gw.net_kg`. `stock_on_hand_rows`' raw-stock figure reads `report_kirim_rows.qty_kg` directly, so it inherits the fix with no migration of its own.

**Parity test extended, not just patched.** `report-effective-qty-parity.spec.ts`'s `seedOrder` fixture inserted `storage_intake` without `box_mass_kg` — would have broken outright once the column went `NOT NULL`. Every scenario's seed now carries a `boxMassKg`, and scenario E's is deliberately nonzero (a zero box mass couldn't have caught a dropped subtraction). Added **Scenario F**, the one branch that didn't exist before box mass: a multi-line truck where gate stage 2 completes before every line is accepted — the accepted line must show provisional/pending-on-box-mass (not pending-on-gate), the unaccepted sibling stays `declared_pre_intake` regardless. `pendingOn` itself isn't asserted in this test — `report_kirim_rows` doesn't expose that granularity, only `qty_kg`/`provisional` do, so there's nothing on the SQL side for it to drift against; the `pendingOn` combinations (including "both pending," which has no natural single-scenario home in the parity test) are unit-tested directly in `weightAuthority.test.ts` instead.

**Verified live, real end-to-end**, not just via the suite: created a real single-line KIRIM order (1,000 kg declared) through the actual UI, seeded gate stage 1 (1,150 kg) and, once the mandatory box-mass field's presence was confirmed on `IntakeAcceptForm.tsx` (submission with it empty was silently blocked — no `storage_intake` row inserted, confirming "cannot be completed without it"), seeded intake (1,000 kg, box mass 55 kg) and gate stage 2 (100 kg empty) directly via SQL — the same seed-via-SQL pattern the e2e suite itself uses, since this browser environment has no file-upload capability for the two mandatory scale/pile photos. Result, cross-checked in three independent places: Ombor's own list (`Netto 995 kg`), Menejer's `KirimOrdersList` (`995 kg`, truck variance `-5 kg / -0.5%`), and `report_kirim_rows` directly via SQL (`qty_kg: 995`, `truck_variance_diff_kg: -5`) — all agree, and match `1150 − 100 − 55 = 995` by hand. Before this fix, the same inputs would have shown `+50 kg / +5.0%` (raw `net_kg` 1050 vs. declared 1000) — a spurious over-delivery reading caused entirely by the unsubtracted box weight, not an actual commercial variance. Test order deleted after verification (not `TEST-`-prefixed — a real-looking plate, per this suite's own `uniqueRealLookingPlate()` convention — so it needed manual cleanup rather than relying on any `TEST-` filter).
