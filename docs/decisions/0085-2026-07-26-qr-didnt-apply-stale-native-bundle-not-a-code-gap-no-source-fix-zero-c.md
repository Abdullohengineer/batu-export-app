## 2026-07-26 — QR "didn't apply": stale native bundle, not a code gap — no source fix, zero-code entry

**Context:** real hardware confirmed the printer outputs a clean QR, but the on-screen Barcode #2 display still showed 1D and the printed QR failed to scan on both web and native, while 1D-on-screen still scanned. Read as "the QR change applied to print only" — asked to check `barcodeLabel.ts`, `BarcodeCameraScanner.tsx`, and the native path independently before touching anything.

**All three checked directly against `main` (PR #66 confirmed merged, `cac22dc`, nothing landed since) — none were out of sync in source.** `barcodeLabel.ts`: `renderQr`/`QRCode.toCanvas` present, `stripBarcode2Prefix` present, exactly as built. `BarcodeCameraScanner.tsx`: `createDetector()` reads `formats: ['code_128', 'qr_code']`, line 99, unchanged since the prior task. `Barcode2Display.tsx`: `QRCode.toCanvas(barcodeRef.current, stripBarcode2Prefix(data.barcode2), ...)`, also unchanged. Re-read all three fresh rather than trust memory of writing them — this is a real hardware report, not a hypothetical.

**Root cause found, not guessed: the Android WebView's bundled JS was stale, independent of the freshly-compiled Java.** `android/app/src/main/assets/public/assets/` (the directory `npx cap sync android` populates from `dist-native`, and the only JS the WebView ever actually loads) carried a modification timestamp from before this session's QR migration. Confirmed definitively by content, not just timestamp — grepped the actual bundled file for the precise array construction `createDetector()` emits: found the literal `formats:[\`code_128\`]`, a single-element array — the pre-migration config — and zero trace of the `qrcode` package's own markers (`toCanvas`+`errorCorrectionLevel` both absent). This is not a partial migration; it's the entire JS bundle never having been refreshed, while `P1PrinterPlugin.java` — compiled straight from source by Gradle, with no dependency on the `cap sync`-populated asset directory — picked up the native change immediately. Explains every symptom as one mechanism: on-screen display stale (old `JsBarcode` still bundled) and scanner stale (`code_128`-only, can't recognize `qr_code`) are the *same* staleness, not two separate misses — which is also exactly why 1D-on-screen kept scanning: both halves of that pairing were consistently on the old system together.

**Fixed by running the correct build step (`npm run cap:sync`), not by touching any source file — confirmed with the same grep, now clean.** Freshly-synced bundle (`index-CC00n31p.js`, new content hash) now contains `formats:[\`code_128\`,\`qr_code\`]` and both `qrcode`-package markers. `android/app/src/main/assets/public/` is git-ignored (confirmed via `git status` showing nothing there) — this was never a shippable/committable gap, purely a local build-artifact one. Most likely explanation for how the tested APK ended up here: a Java-only rebuild (e.g. `gradlew installDebug` run directly) skips the web-asset copy step entirely if `npm run build:native && npx cap sync android` isn't run first — an easy trap precisely *because* the prior task's own change touched both Java and JS in the same PR, so "I only need to recompile the plugin" is a natural but incomplete assumption. The web deploy (Netlify, `netlify.toml` confirms `npm run build` / publish `dist`) is a separate, independently-stale artifact with the same underlying explanation — a fresh deploy off current `main` was needed and evidently hadn't run; not independently verifiable from this environment, flagged for the user to confirm via Netlify's own deploy log.

**End-to-end value chain confirmed against the actual physical label, not a synthetic one.** Queried `finished_pallets` for the label's real printed value (`PLT-210726-014-KN-1`) — exists, `status='in_stock'`, 100kg. Live round-trip in a real browser: stripped the value the same way `stripBarcode2Prefix`/the native plugin do (`210726-014-KN-1`), encoded it through the app's own `qrcode`/`QRCode.toCanvas`, decoded it through a detector built with the app's own `formats: ['code_128', 'qr_code']`, then applied `processBarcode`'s own re-prepend normalization (confirmed present and unchanged, `OmborChiqimTab.tsx` line 135) — result matched the original label value exactly (`matchesRealLabelValue: true`). This is a direct answer to the task's own ask: once the correct bundle is actually running, this specific printed label decodes and resolves correctly; the round trip was never the problem.

**No commit, no branch, no PR for this entry — genuinely zero source changes.** Every file was already correct; the only action taken was running `npm run cap:sync` locally (gitignored output, nothing to commit) and this investigation. Recording it anyway because the finding is real, reproducible, and will bite the next native-only-seeming change too if undocumented.
