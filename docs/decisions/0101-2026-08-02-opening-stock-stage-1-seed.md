## 2026-08-02 — Opening stock, Stage 1 (seed)

**Context.** The factory has pre-existing inventory predating the app — old washed pallets, old Konditirskiy (a weight pool with no pallets), old raw — that needs to be seeded, made collectible, and (later) re-washable, without ever being counted as a delivery in arrival/throughput reporting. Full design in an inspect-and-plan pass first (no code), confirmed with four additions before building: confirm old raw already flows through the normal Moyka send window; a qoldig'i old-stock filter that doesn't leak into event reports; the consume-and-mint mechanism generalized to accept a weight draw (not just pallets) so Rezka can reuse it later without redesign; and Menejer/Rahbar visibility confirmed end-to-end. `supabase/migrations/0048_opening_stock_stage1_seed.sql`, `0049_opening_stock_yield_rows_exclusion.sql`.

**The three kinds, as modelled.** Old washed = real `finished_pallets` rows (`is_old_stock`/`weight_is_estimate` booleans, independent — a later re-washed old-stock pallet is old-derived but not an estimate), anchored to one minted `kirim_orders`/`kirim_lines` serial per product type (5 total) rather than per pallet — mirrors how one real serial already produces multiple calibres. Old Konditirskiy = a genuinely new shape, `old_kn_pools` (owner_id, type_id, opening_kg) — no serial, no `kirim_lines` involvement at all, since KN opening stock was never individually tracked; balance is derived (`old_kn_collections`, the draw-down table, is Stage 2 scope — nothing collects against it yet, so the pool's balance is simply `opening_kg` for now). Old raw = zero new tables — a normal seeded `kirim_lines`/`storage_intake` row, flowing through the *existing* raw-dispatch machinery unchanged.

**The `origin` discriminator — the load-bearing addition.** `kirim_orders.origin` (`'delivery' | 'opening_stock' | 'internal_reprocess'`, default `'delivery'`) is what lets opening stock be visible as stock without being counted as a delivery. `report_kirim_rows` itself stays unfiltered (the qoldig'i/client-report *balance* paths need to keep seeing it) and just gains the column; the filter (`origin = 'delivery'`, a positive allowlist so a future Stage 3 re-wash's own `'internal_reprocess'` orders are automatically covered too, no second exclusion value needed later) is applied only at genuine **arrival** consumers, traced by reading each one's live definition rather than assumed: `report_rows` (Hisobot), and — confirmed via `pg_get_functiondef` that each reads `report_kirim_rows` directly, not through `report_rows`, so fixing `report_rows` alone would have missed all three — `rahbar_monthly_trends`, `rahbar_client_ranking`, `rahbar_product_mix`. `get_client_report`'s `raw_received_total`/`raw_received_by_type` (a period arrival aggregate, same category) get the identical treatment; `raw_opening_total`/`raw_closing_total`/`moykada_total` and the reconciliation object are balance figures and are deliberately left untouched, so the client report's own opening stock stays fully visible in the client's raw balance. The **departure/dispatch side stays unfiltered everywhere** — a real truck leaving with old-stock-derived material is a real event and should count in `volume_out`/`dispatched_kg`.

**`rahbar_exceptions()`'s `ageing_stock` branch** also excludes `is_old_stock` (2026-08-02 feedback) — it would flag permanently, forever, with no remediation possible, and a persistent unactionable entry devalues the whole exceptions list. `lab_overdue`/`high_loss`/`high_rewash` untouched.

**`stock_on_hand_rows`** gains `is_old_stock`/`weight_is_estimate` on the existing pallet/raw buckets, plus a new `old_kn` bucket (reads `old_kn_pools.opening_kg` directly — gets a small follow-up edit in Stage 2 once `old_kn_collections` exists to subtract from it). No toggle UI yet — that and the shared "Eski zaxira 2025-2026" date-label helper are the immediate code follow-up now that this migration is confirmed, not a second SQL gate.

**🐛 Real bug found during hand-verification, not by inspection — `yield_rows` had no origin awareness at all.** The seed mints a `'final'` `wash_cycles` row per old-washed serial (necessary: without a passing lab verdict, `chiqimScan.ts`'s hard gate hides the pallets entirely, and the task's own requirement was "immediately collectible"). But `yield_rows` treats any `'final'`-status wash cycle as a completed processing run — with `raw_consumed_kg` always 0 for these (no `moyka_sends` ever happened, they were seeded directly as pallets), it produced a phantom "0 kg in, 52,210 kg out" entry that `rahbar_monthly_trends()` then surfaced as a real January 2025 row: `output_kg: 52210`, a populated `calibre_mix`, `yield_serial_count: 5` — exactly the kind of Rahbar-facing distortion this whole task exists to prevent, just via a call site (`yield_rows`, not `report_kirim_rows`) the original plan hadn't traced. Fixed with the same `origin` column, but a *narrower* filter than everywhere else: `origin != 'opening_stock'` specifically, **not** `= 'delivery'` — a future Stage 3 re-wash mints an `'internal_reprocess'`-origin serial with a *real* wash cycle (real weighed `moyka_sends`, real output) that must keep counting normally in yield/loss/re-wash trends, per the already-confirmed "re-washing old stock is real processing" design point; blanket-filtering on `origin = 'delivery'` would have wrongly excluded that too.

**Hand-verified live, all three areas the confirmation asked for, via direct SQL (before the UI pieces exist):**
- **Qoldig'i**: `stock_on_hand_rows where is_old_stock` returns exactly three groups — `available` (finished pallets): 79 rows, 52,210 kg; `old_kn`: 4 rows, 103,936 kg; `raw_not_washed`: 1 row, 2,880 kg — all three kinds present, correctly flagged, summing to the full seed.
- **Hisobot**: `report_totals('kirim', '2025-01-01', '2025-01-01', ...)` → `(0,0,0,0,0)` — the minted arrivals contribute nothing.
- **Rahbar**: `rahbar_monthly_trends()` has *no row at all* for January 2025 after the `yield_rows` fix (confirming both the arrival side and the output/yield side are clean); `rahbar_client_ranking`/`rahbar_product_mix` for the seed-day period both return empty; `rahbar_exceptions()` returns no rows.
- **Global Export's client report**: period `2025-01-01`–`2025-01-01` (the seed day itself) → `openingKg=0, receivedKg=0`. Isolated further by type: Qand's `byType` entry for a period ending `2024-12-31` (before the seed) → `opening/closing/received` all `0`; for `2025-01-02` (the day *after* seeding) → `opening=closing=2880, received=0` — the old-raw contribution enters the balance immediately and is never counted as a period arrival, exactly bracketing the required behavior.

**Verification.** Both migrations applied directly (Supabase MCP, no branch — this project's own documented limitation). Every hand-verification query above re-run after the `yield_rows` fix landed, all clean.

**Out of scope, not touched (Stage 1):** `pallet_status`+`'consumed'`, `chiqim_lines.line_kind` widening, `old_kn_collections`, `serial_mint_sources`, the mint RPC — Stage 3. The qoldig'i toggle UI and per-kind rendering — Stage 2. Rezka, KN origin/state, the notes feature, the dehydration-reconciliation UI, per the original task's own scope.
