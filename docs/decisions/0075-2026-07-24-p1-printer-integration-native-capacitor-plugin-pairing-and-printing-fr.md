## 2026-07-24 — P1 printer integration: native Capacitor plugin, pairing, and printing from both barcode screens

**Context:** the Capacitor Android wrap (previous entry) deliberately left the P1 printer as a future step. This is that step — a native plugin wrapping DothanTech's LPAPI SDK (`vendor/printer-sdk/`), printer pairing persisted across sessions, and label printing wired into both `Barcode1Display.tsx` and `Barcode2Display.tsx`.

**Inspected and reported before coding, per the task's gate.** The PDF documentation and the demo disagreed in one place — the callback method is `onStateChange`, not `onStateChanged` as the PDF prose has it — resolved by decompiling the real jar (`javap` against `android/app/libs/LPAPI-2026-01-08-R.jar`) rather than trusting either source blindly. The same jar-level check also surfaced that `discovery()`/`stopDiscovery()` are real, callable methods entirely absent from the PDF's own method chapters (only the demo uses them), and gave the exact `PrintFailReason` enum names (`No_Paper`, `CoverOpened`, `TphOpened`, `VolTooLow`, `Disconnected`, …) needed for requirement E's specific-message mapping. No other divergence from the reported plan — proceeded as approved.

**A — the plugin interface, as built** (`android/app/src/main/java/com/batuexport/app/P1PrinterPlugin.java`, `src/lib/p1Printer.ts`):
```ts
interface PrinterInfo { address: string; name: string }
interface PrintLabelOptions { barcode: string; serial: string; typeName: string; calibreLabel?: string; weightKg: number; clientName: string }
interface P1PrinterPlugin {
  listPrinters(): Promise<{ printers: PrinterInfo[] }>
  selectPrinter(options: { address: string }): Promise<{ connected: boolean }>
  printLabel(options: PrintLabelOptions): Promise<{ success: boolean; reason?: PrintFailureReason }>
}
```
`calibreLabel` is optional — Barcode #1 (raw material) has no calibre yet, and the native layout just omits that line rather than leaving a dangling separator. Everything LPAPI reports asynchronously via `Callback`; every method holds its `PluginCall` open until the matching callback fires (`onStateChange` for connect, `onPrintProgress` for print), guarded by a timeout (10s connect, 18s print) that always resolves or rejects the JS side rather than leaving it hanging. A `connectionChange` event (`notifyListeners`) fires on every `onStateChange`, independent of whether JS is waiting on a call, so the UI's connection dot updates even when nothing triggered it directly (e.g. the printer going idle on its own). Persistence is entirely JS-side via `@capacitor/preferences` (`src/lib/usePrinter.ts`) — the plugin itself never touches storage, keeping the native surface to exactly three methods.

**B — 40×30mm layout, as built.** No rotation (`startJob(40, 30, 0)`) — the stock is already landscape at those dimensions. Left-aligned, top to bottom: barcode bars with LPAPI's own built-in human-readable text (~10mm) · serial (~3.5mm, medium prominence) · `typeName · calibreLabel` or just `typeName` when no calibre (~3mm) · `weightKg kg` (~4mm, prominent) · `clientName`, truncated with an ellipsis past 22 characters, no shrink-to-fit (~3mm). **The layout now genuinely exists in two places, as expected:** `P1PrinterPlugin.java`'s native drawing is authoritative for what actually prints; `barcodeLabel.ts`'s canvas/JsBarcode renderer is an explicit preview, used for the on-screen SVG, the web share/download fallback, and nothing else. They were already going to diverge (native draws its own barcode value as text under the bars; the web canvas draws a separate, larger code-value line since JsBarcode has no built-in human-readable text) — resized `barcodeLabel.ts`'s `LABEL_MM` from 50×30 to 40×30 to at least match stock dimensions, since printing the old 50×30 PNG via the web share sheet onto real 40×30 stock would have laid out wrong. Barcode #1's native label also drops the `date` field entirely (present on the web preview, not part of the raw-material fields the task specified) — another deliberate, documented difference between the two, not a bug.

**C — Bluetooth permissions**, exactly as specified: `BLUETOOTH_SCAN`+`BLUETOOTH_CONNECT` (with `neverForLocation`, since the printer is classic Bluetooth SPP and its scan results are never used for location — this avoids ALSO needing location permission on 12+) on Android 12+; `BLUETOOTH`+`BLUETOOTH_ADMIN`+`ACCESS_FINE_LOCATION`+`ACCESS_COARSE_LOCATION` (via `maxSdkVersion="30"`, a manifest-level no-op above that rather than branching the manifest itself) below. Requested through Capacitor's own `@Permission`/`@PermissionCallback` framework (two aliases, `bluetoothModern`/`bluetoothLegacy`, picked by `Build.VERSION.SDK_INT`), not hand-rolled — denial rejects with a stable `PERMISSION_DENIED` code that `src/lib/p1Printer.ts` maps to a fixed Uzbek message, never a silent no-op.

**D — printer selection and reconnection.** `PrinterStatus.tsx` (a small connection dot + tap-to-scan-and-select panel, rendered directly next to the print button in both display components, not a separate settings screen) is the "pick once" UI; `usePrinter.ts` persists the choice via `@capacitor/preferences` and re-issues one `selectPrinter` call per app session on mount so a saved printer reconnects transparently before the first print is ever attempted. Auto-reconnect-on-print lives natively, not in JS: `P1PrinterPlugin.doPrintLabel` checks `getPrinterState()` first, and if the printer's gone idle/disconnected but a printer was selected earlier this session (`currentAddress` still set), silently reconnects to that same address and only then draws — surfacing an error only if the reconnect itself fails. Ombor never sees a reconnect screen; they just tap print. The connection dot is a live `useSyncExternalStore`-backed store (not per-component state) specifically because `Barcode2Display` renders once per pallet row — many simultaneous instances all need to reflect the same connection status, not independent copies.

**E — failure reasons.** `mapFailReason` in the plugin collapses LPAPI's 25 `PrintFailReason` values to 5: `NO_PAPER` (`No_Paper`/`No_Label`/`Usedup_Label`), `COVER_OPEN` (`CoverOpened`/`TphOpened`/`LabelCanOpend`), `LOW_BATTERY` (`VolTooLow`), `NOT_CONNECTED` (`Disconnected`), `OTHER` (everything else — ribbon/temperature/rotation/timeout-adjacent states a warehouse worker can't act on any more specifically than "try again"). `src/lib/p1Printer.ts` maps each to a fixed Uzbek message shown inline under the print button.

**F — both label types, auto-print, and reprint.** Barcode #2 already had the exact shape this needed: `defaultOpen` on first appearance after a save (`OmborTayyorTab.tsx`'s `lastBarcode`), collapsed-by-default in every historical pallet row. Added the identical moment to Barcode #1, which had no `defaultOpen` concept at all before this task — `OmborIntakeTab.tsx` gained a `justAccepted` state (mirrors `lastBarcode` exactly) set right after `handleAccept` mints `barcode1`. Both components: native available → auto-print fires once per distinct barcode value (not once per component instance — both `OmborTayyorTab`/`OmborIntakeTab` reuse the same mounted instance across multiple saves in one session, so a mount-only guard would have silently stopped auto-printing after the first) via an effect keyed on the barcode string; the same "Chop etish" button is the reprint action everywhere, including older pallets/serials from prior sessions — reprint never depended on when the row was created, only on the barcode value still being on screen.

**Real regression found and fixed via the e2e suite, not assumed safe from inspection:** the first full-suite run (after an unrelated dev-server disruption — see below — was corrected) still failed `rewash-hard-gate.spec.ts` on a genuine `strict mode violation`, not a flake: unconditionally honoring `defaultOpen` in `Barcode1Display` meant its label-preview `div` (class `rounded-md border-2 …`) now rendered immediately after every Ombor accept, even on the web build with nothing to auto-print — and that div's `rounded-md` class collided with the spec's own `div.rounded-md` locator for the accepted-serial row, resolving to 2 elements instead of 1. Fixed by only honoring `defaultOpen` when `isP1PrinterAvailable()` — on web, Barcode #1's panel stays collapsed on accept exactly as it did before this task, since there's no auto-print to justify opening it. `Barcode2Display`'s equivalent pre-existing web auto-open (already shipped before this task, `OmborTayyorTab.tsx`'s own `lastBarcode`) was left untouched — it isn't causing this or any other failure, and changing already-working shipped behavior wasn't part of this task.

**Also transparently: a self-inflicted e2e disruption, corrected before trusting any result.** Stopped the dev server via `preview_stop` while a background full-suite run was still using it (the exact mistake flagged in this session's own Capacitor-wrap entry, repeated once) — 3 of 4 specs failed with `ERR_CONNECTION_REFUSED`/`ERR_CONNECTION_RESET`, and a second, redundant single-spec run accidentally started on top of it. Neither result was trusted: restarted the server, let both stray runs finish and exit fully, then re-ran the complete suite once, untouched, before drawing any conclusion — which is what surfaced the real `rewash-hard-gate.spec.ts` regression above (the disrupted run's own copy of that spec had failed too, but for the wrong, confusable reason, on a 1.0m run that got far enough to hit the real bug before the connection-refused pattern would have explained it).
