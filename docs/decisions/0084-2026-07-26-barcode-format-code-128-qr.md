## 2026-07-26 — Barcode format: CODE_128 -> QR

**Context:** the print-legibility fix above (quiet zone + module width) measurably improved density, but real printed 1D labels still failed to scan off paper at 40×30mm — bars too dense for a phone camera to resolve even with the improved numbers. On-screen scanning always worked. QR fixes the root cause (a 2D symbol with error correction fits the same data far more efficiently than 1D bars can) instead of chasing 1D density further. Also asked to restore the scan-frame overlay, "regressed again."

**Frame overlay — investigated fresh, found no regression, same as the last time this was reported.** Read `BarcodeCameraScanner.tsx` directly: byte-identical to the version from the camera-overlay-feedback task, and `git log` confirms zero commits touched that file since — the aiming frame and feedback banner were never lost. What's real and necessary regardless: requirement 4 asks for a square frame for QR (the old 280:120 rectangle was 1D-shaped), so it's being reshaped either way — reported the non-regression plainly rather than silently building "restore" work for a bug that doesn't exist in the code.

**Confirmed before coding, against the real jar, not docs:**
- `LPAPI.draw2DQRCode` exists with a `(String, double, double, double)` overload — found via `javap` on the **concrete** `LPAPI` class (the field this plugin actually holds), not just the `IAtBitmap` interface it implements, which only exposes an int-typed 4/5-arg pair this plugin never calls. `IAtBitmap`'s `ErrorCorrectionLevel`/`DrawParamName.ERROR_CORRECTION` constants exist but have zero real usage anywhere in the DothanTech demo to confirm the `setDrawParam` calling convention against — left at the library default rather than guess at an unverified native call (same judgment call as `textHeight=0` in the prior task).
- Confirmed the size parameter drives a **square** box, not width+height, by reading both real demo usages in `MainActivity.java` — one subtracts the same `qrcodeWidth` from both the label's width and height when computing x/y, which only makes sense if one parameter drives both dimensions.
- Scanner's format list was `['code_128']` only — added `'qr_code'` (kept `code_128` too, so any already-printed 1D labels still scan during the transition). Confirmed `'qr_code'` is a real, valid literal in the installed `barcode-detector` ponyfill's own type union (`utils.d.ts`), not assumed from the spec name alone.
- Current encoded value, and a drift found while checking it: the prior task made native encode `barcode2` with `PLT-` stripped, and `processBarcode` re-prepend it before lookup — but never touched `barcodeLabel.ts` (web preview), which still encoded the **full** value. Native print and web preview were encoding different strings. This task's own "same value" requirement gave a mandate to fix that now.
- **A third rendering path found that neither this task's own reading list nor the prior task caught:** `Barcode2Display.tsx`/`Barcode1Display.tsx` each have their own direct `JsBarcode(...)` call rendering CODE_128 to an on-screen `<svg>` — completely separate from `barcodeLabel.ts`'s canvas/PNG pipeline (that one only backs the web share/download fallback). This is the actual "on-screen scanning works fine" component from every prior bug report in this arc. Left unfixed, it would have kept showing 1D on-screen after this whole migration. Switched both.

**Implementation:**
- **Native (`P1PrinterPlugin.java`):** `draw2DQRCode(barcodeEncoded, 3, 1.5, 10)` — 10mm square, left-aligned at the old bars' x-position (keeps the rest of the label's own left-aligned convention, unlike the web preview which centers — the two layouts already drift by design, see the file's own long-standing comment; value-parity was the requirement, not pixel-parity). Text lines below reflowed to the QR's new (shorter) vertical footprint. Encoded value still drops `PLT-`, same as the prior fix.
- **Web preview (`barcodeLabel.ts`):** replaced `renderBars`(JsBarcode) with `renderQr`(`qrcode` npm package, `QRCode.toCanvas`), fixed 160px/10mm square — no shrink-to-fit loop needed, unlike 1D: `qrcode` auto-picks whatever version the content needs at a fixed pixel footprint, so a longer value just means smaller modules, never a wider symbol. `renderLabel` split into `encodedValue`/`displayValue` params so Barcode #2 can encode the stripped form while still displaying the full `PLT-...` text, exactly mirroring native. New exported `stripBarcode2Prefix()` helper, shared with `Barcode2Display.tsx`'s own on-screen render so the transform has exactly one definition.
- **On-screen (`Barcode2Display.tsx`/`Barcode1Display.tsx`):** swapped `<svg ref>` + `JsBarcode` for `<canvas ref>` + `QRCode.toCanvas`, same 180px/~11mm size, same encoded-value handling as the print/preview paths (stripped for #2, plain serial for #1 — no prefix to strip there).
- **`jsbarcode` removed from `package.json` entirely** — confirmed via grep it had zero remaining call sites after all three switches, not left as dead weight.
- **Scanner (`BarcodeCameraScanner.tsx`):** `formats: ['code_128', 'qr_code']`; aiming frame `aspect-[280/120]` → `aspect-square`, `w-[80%] max-w-[280px]` → `w-[65%] max-w-[220px]` (a QR target doesn't need as much width as a wide 1D rectangle did).
- **Error correction level 'Q'** (25% recovery) chosen deliberately over the library default 'M' (15%) on every web-side QR (`barcodeLabel.ts`, both Display components) — a warehouse pallet sticker exposed to handling/dust/wear reasonably warrants more tolerance than a phone-screen QR would need, and the short content stays comfortably inside Version 1 either way, so there's no density cost to choosing the higher level. Native left at the library default since `setDrawParam` couldn't be verified against the real jar (see above) — worth revisiting as a small follow-up once someone can confirm that calling convention against a real device.

**Density estimate — computed via the real installed `qrcode` library, not guessed.** `QRCode.create('210726-011-07-1', {errorCorrectionLevel:'Q'})` reports Version 1, 21×21 core modules; +4-module margin each side = 29 modules across. At the native 10mm size: **0.345mm/module**, vs. the prior 1D fix's measured 0.191mm/module — a **1.81x** improvement in raw module pitch, which likely undersells the real scannability gain since a 2D square dot is generally easier for a camera to resolve than a 1D bar-width transition at the same pitch.
