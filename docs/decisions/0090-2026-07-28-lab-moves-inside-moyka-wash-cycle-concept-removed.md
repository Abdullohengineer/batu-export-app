## 2026-07-28 — Lab moves inside Moyka, wash-cycle concept removed

**Context:** The product's real physical process has never had a re-wash *cycle* in the sense the schema modeled — SPEC's own wording (confirmed against the mockups before any code changed) is that Laborator's CHIQIM check happens once material is *in* Moyka, not after a completed processing run, and a reject just means the same batch gets re-tested, not that a second, numbered wash cycle begins. The old model (`wash_cycles` one row per cycle, `cycle_no` incrementing, Ombor's own void+resend UI to open cycle 2) was a mechanism invented to represent something that was never actually asked for, and it was the direct cause of a whole class of complexity this session removed: `activeCycles.ts`, `rewash.ts`, `usePendingRewash.ts`, the "sikl N" badges throughout Kirim/Chiqim/reports, `crossPeriodRewash` in the client report, the `qayta_yuvish_pending` WIP bucket, and — most importantly — the fact that the hard gate on Barcode #2 assignment lived at the *wrong* point (dispatch, not packing), meaning an untested serial could physically receive a pallet barcode before Laborator ever saw it.

**Decision (confirmed by the user before any code changed):**
- Keep `wash_cycles` as a real table (do not drop it) — too many FK/RLS/query references for the gain, and it still earns its keep as the one-row-per-serial home for `status`/`final_loss_pct`/`finalized_at` (the "one loss number per serial, locked at Tugallash" mechanism, unchanged in spirit from before).
- The hard gate relocating from dispatch to packing is the single most safety-critical change in this task — test it hardest, explicitly, at both the UI and RLS level.
- Delete the dead re-wash UI entirely (Ombor's void+resend flow, the amber "qayta yuvish" cards) — not disable, not hide behind a flag.
- Ship the schema+RLS+view changes as one migration rather than staging them, since the count of touched objects was small enough that splitting would only add risk of an inconsistent intermediate state.

**The model, precisely:** `wash_cycles` goes from `unique(serial, cycle_no)` to `unique(serial)` — `cycle_no` and `voided_at` dropped (the latter confirmed to have zero live writers even under the old system before removing it). `status`/`final_loss_pct`/`finalized_at` are unchanged in meaning. Critically, `lab_results.wash_cycle_id` is **untouched** — it still points at `wash_cycles.id`, still required on `scope='chiqim'` — and no unique constraint was ever forced on that relationship, so a reject-then-retest is just a second `lab_results` row against the *same* `wash_cycle_id`, with "current verdict" defined as the latest row by `created_at`. This is what makes "re-test, not re-cycle" fall out naturally from the existing shape rather than needing a new mechanism.

The `wash_cycles` row itself now gets minted at **first send to Moyka** (`OmborMoykaTab.tsx`'s `handleSend`, an `upsert(..., {onConflict: 'serial', ignoreDuplicates: true})` run alongside every `moyka_sends` insert, safe to repeat on every partial send) rather than at Tugallash — necessary because CHIQIM lab testing is now enterable from the moment material reaches Moyka, and `lab_results.wash_cycle_id` needs somewhere to point before that test can be recorded.

**The hard gate is a Postgres RLS `WITH CHECK`, not a UI convenience.** `finished_pallets`' `ombor_writes` INSERT policy now requires:
```sql
(select lr.verdict from lab_results lr join wash_cycles wc on wc.id = lr.wash_cycle_id
 where wc.serial = finished_pallets.serial and lr.scope = 'chiqim'
 order by lr.created_at desc limit 1) = 'o_tdi'
```
A scalar subquery ordered by `created_at desc limit 1`, deliberately — not `exists(...)` — because the requirement is "the *current* verdict is a pass," not "has ever passed once." A serial rejected after an earlier pass (impossible today, since nothing can un-pass through the UI, but the query is correct regardless) would not satisfy this. Matches SPEC's "hiding buttons is not security" principle: `OmborTayyorTab.tsx` also hides the pack button client-side as a convenience, but the real refusal happens here, proven directly (see Test 1 below).

**Reporting rewritten around the new model, not just patched (0035/0036):**
- `report_chiqim_rows`, `stock_on_hand_rows`, `wip_rows`, `yield_rows` (0035) — drop the `wash_cycle`/void-successor-via-`wash_cycle+1` logic that only made sense with numbered cycles. `wip_rows` loses its `qayta_yuvish_pending` CTE entirely (no more "cycle 2 hasn't started yet" state to report on). `yield_rows` drops the all\_\*/live\_\* split (nothing is voided under the new model, since a pallet cannot exist before its serial passes — there's no "voided vs current" distinction left to draw) and redefines `rewashed` as "had ≥1 reject in this serial's own lab history before its eventual pass," a boolean fact rather than a cycle count.
- `get_client_report`, `get_serial_passport`, `lab_turnaround_avg` (0036) — `get_client_report` drops `client_cycles`/`loss_period_cycles`/`cross_period_cycles`/`crossPeriodRewash` entirely (the whole concept of "raw sent in period A, a *second cycle* completing in period B" requires two cycles to exist). **Caught before applying:** an early draft of the loss arithmetic joined `finished_pallets` into the same CTE that carried `sent_actual_kg`, which would have multiplied the sent total by pallet count on any multi-pallet serial — fixed by splitting `loss_totals` (serial-level, summed once) from `loss_output` (pallet-level, joined separately), combined only in the final `loss_main` CTE. `lab_turnaround_avg` moved its anchor from `finished_pallets.received_date` to `min(moyka_sends.sent_date)`, matching the new trigger timing. `rahbar_monthly_trends`/`rahbar_client_ranking`/`rahbar_product_mix`/`rahbar_exceptions` were deliberately not touched — confirmed they only consume the preserved-name output columns of `yield_rows`/`report_*_rows`, not the removed keys.

**App-side rewrite:** `labVerdict.ts`'s `currentCycleLabStatus` became `currentLabStatus` (latest-row-per-`wash_cycle_id` resolution, sort+dedupe rather than a window function, since it's normally a handful of rows). `useMoykaSerials.ts`/`useMoykaOutput.ts` lost `activeCycle`/`isRewash` entirely — every send/pallet for a serial now belongs to the same single balance for its whole life. `useLaboratorChiqim.ts`/`LaboratorChiqimTab.tsx` rewritten for the new trigger timing (awaiting-list keyed by `wash_cycle_id`, `sentKg`/`sentDate` shown instead of a pallet count) — a rejected verdict correctly reappears in Window 1 highlighted (`rejected: boolean`, red "Rad etildi" text), not routed into the finished window (see bug below). `useLaboratorKirim.ts`/`KirimTahlilForm.tsx` gained the KIRIM-side equivalent trigger-timing change: every `kirim_lines` row is now visible from order creation, but only *enterable* once gate stage 1 (`gruzheny_kg`) exists — previously KIRIM lab testing was gated on a later confirmation step that no longer exists in this shape. `ChiqimTahlilForm.tsx` dropped its required pallet `<select>` (a pallet doesn't exist yet at test time under the new gate) for an optional free-text "Namuna manbai" field.

**Deleted outright (not disabled):** `src/lib/usePendingRewash.ts`, `src/lib/rewash.ts` + its test, `src/lib/activeCycles.ts`, `tests/e2e/rewash-hard-gate.spec.ts` (its whole premise — cycle 2 reopening dispatch via Ombor's own void+resend action — no longer exists), and every "sikl N" / "Qayta yuvish kerak" / "Qayta yuvishga yuborish" UI element across Kirim/Chiqim/reports screens (`KirimOrdersList.tsx`, `LaboratorTarixTab.tsx`, and others — confirmed via a full source grep before and after, see Test 3 below).

**Testing** (the user's own explicit follow-up task, run once the rewrite above was live).

**Test 1 — the hard gate, proven at both layers.** New spec `tests/e2e/lab-packing-hard-gate.spec.ts` (replacing the retired `rewash-hard-gate.spec.ts`): seeds two serials through KIRIM → gate → intake → Moyka send directly, then (a) confirms the pack action is *absent*, not disabled, on an untested serial, and separately attempts a **direct `finished_pallets` insert as Ombor via the dev `window.supabase` client** — proven refused by RLS, matching `/row-level security|policy/i`, not just a UI-level absence; (b) has Laborator pass one serial and reject the other; (c) confirms the rejected serial assigns no pallets, reappears in Laborator's own CHIQIM Window 1 highlighted "Rad etildi," and *still* cannot pack even after its sibling successfully did (the gate is per-serial, not per-batch). **1 passed reliably after two fixes below; see the 🚩 entries.**

**🚩 Real bug, found via this test: `useLaboratorChiqim.ts`/`useLaboratorKirim.ts` had the identical missing-guard gap as `useMoykaOutput.ts`/`useMoykaSerials.ts` above** — same one-shot mount fetch, same lack of any `cancelled`/request-id protection, both rewritten this session and both missing the convention every *other* one-shot-fetch hook in this codebase already follows. Symptom here was different and more disruptive than the empty-render case: with two overlapping `refresh()` calls in flight (StrictMode's mount double-invoke plus a manual `refresh()` from `handleTahlil` after the first of two verdicts in the same test), Laborator's CHIQIM list re-rendered repeatedly in quick succession, and a click on the second verdict button (`Qayta yuvish`) reliably hit "element was detached from the DOM, retrying" until the *test's own 180s timeout* — not a rare flake, reproduced identically on two separate isolated runs before the fix. Fixed with the same monotonic request-id guard as the Moyka hooks. Confirmed the fix, not a coincidence: before it, two consecutive isolated runs of this one spec both hung on the same click; after it, the click succeeds immediately and the spec passes cleanly on repeat runs.

**🚩 Real bug, found via this same test, after the above: `serialCard()` (the test's own locator helper) was ambiguous for longer than its one call site accounted for.** `ChiqimTahlilForm` renders its own "Seriya `<serial>`" summary in a nested `rounded-md` wrapper while open — same class of ambiguity this suite's own `serialCard()` was originally built to dodge (matching against the *closest* rounded-md ancestor of the serial's own chip, not a bare class selector), except here the form doesn't finish closing by the time a caller's very next assertion runs, since `handleTahlil`'s `setActiveTahlil(null)` + `refresh()` only commit after its async insert resolves and a click doesn't wait for that. Fixed in the test's own `testSerial()` helper: wait for `serialCard(serial)` to settle back to exactly one match (`toHaveCount(1)`, which — unlike `toBeVisible()` — doesn't require single-match to begin polling, so it's safe to call on an already-ambiguous locator) before returning control to the caller, rather than inferring "closed" from the clicked button alone (which turned out to still leave a brief window where the form's own summary block was the sole remaining match).

**Test 2 — loss computed at receipt, traced into both reports.** New spec `tests/e2e/lab-relocation-loss-verification.spec.ts`: a serial with a hand-checkable raw figure (gate 1100−100=1000kg) sent in full, passed, packed as one 850kg pallet — expected loss 150kg/15.0%. Confirms the Tugallash confirm dialog itself shows the number Ombor's own receipt produces (`150 kg · 15.0%`) before confirming, then traces the *same* number into `get_client_report` (`processedBreakdown.lossKg`/`lossPct`, JSONB, numeric) and `yield_rows` (`loss_kg`/`loss_pct`/`output_kg`, plain view, also numeric — see PostgREST note below). **1 passed, run twice back-to-back for reliability, both clean.**

**🚩 Real bug, found via this test, not hypothetical: `useMoykaOutput.ts`/`useMoykaSerials.ts` had no protection against overlapping `refresh()` calls.** Both hooks fetch once on mount via a bare `useEffect(() => { refresh() }, [refresh])`, no cancellation guard — every *other* one-shot-fetch hook in this codebase already carries a `cancelled`-on-cleanup guard (`useYieldRows.ts` and 7 others), but these two (rewritten this session) didn't. Under React StrictMode's dev-only double-invoke of the mount effect, two overlapping calls can race, and — since `refresh` is also called manually by mutation handlers (`handleSend`/`handleReceipt`/`handleTugallash`), a plain per-effect `cancelled` closure (the usual pattern here) can't cover every call site. Fixed with a monotonic request-id ref instead: only the most-recently-*started* call is ever allowed to commit state, regardless of which one resolves first. Symptom before the fix: after a fast role switch straight into a screen these hooks drive (e.g. Ombor's Tayyor Mahsulot right after a Laborator verdict), both windows could render completely empty — not a display bug, a stuck one: nothing ever re-triggers a one-shot mount fetch, so waiting longer never helped.

**🚩 Real bug, found via this test: `ClientReportTab.tsx` (and its Excel export) crashed unconditionally.** `report.raw.crossPeriodRewash.length > 0` — a leftover reference to the output key `get_client_report` (0036, above) removed entirely from its JSON shape. `report.raw.crossPeriodRewash` is `undefined` at runtime, so `.length` threw on *every* client report load and every Excel export, not a rare path. Fixed by removing the whole cross-period-rewash block from `ClientReportTab.tsx` and `clientReportExport.ts`, and the now-dead `ClientReportCrossPeriodRewash` type, `cycleNo` field, and `crossPeriodNote`/`cycle` labels from `clientReport.ts`/`clientReportLabels.ts`. This is exactly the kind of regression Test 2's own header comment already flagged this reporting layer as the highest-risk area for (this codebase has shipped one real loss-calculation bug here before) — caught by deliberately exercising the client report as part of tracing the loss figure, not by a targeted crash test.

**🚩 Real bug, found via this test: `OmborMoykaTab.tsx`'s send-to-Moyka step had no reliable success signal for a test to wait on.** The "+ Moykaga yuborish" button that opens the send form disappears the instant the form *opens* (`isActive` flips before any network call fires) — its absence proves nothing about whether the underlying `moyka_sends` insert actually completed. `lab-relocation-loss-verification.spec.ts`'s own first draft relied on this and was intermittently flaky as a result — sometimes the mutation's response hadn't landed before the test moved on to a role switch, and the write appears to have been cut short. Fixed in the test by wrapping the actual submit click in `page.waitForResponse()` for the `moyka_sends` POST and asserting it succeeded, rather than inferring success from an ambiguous button-count check.

**Test 3 — nothing wash-cycle-related left broken or orphaned.** A full source grep (`sikl |wash_cycle|cycle_no|activeCycle|isRewash|qayta_yuvish`) across `src/` surfaced ~20 files; each was checked against the *live* schema/RPC output (via direct SQL, not assumption) rather than trusted from the migration text alone, since the two bugs above were both cases of "should be safe" not holding up under a live check:

- **Genuinely dead, removed:** the `WashCycleFilter` "Yuvish sikli" dropdown in `ReportFilterBar.tsx`/`HisobotTab.tsx`/`reportQuery.ts` — the underlying `wash_cycle` column the filter compared against is always `null` now, so it could never match anything; `useReportQuery.ts` now passes `p_wash_cycle: null` directly (the RPC signature still requires the param, no default, so the wire shape is unchanged) rather than exposing a control that can't do anything. Same for `wip.ts`'s `qayta_yuvish_pending` `WipKind` — the DB view's own CTE producing it was already deleted in 0035, so the union member/label/sort-order entry were unreachable.
- **Misleading, fixed:** `SerialPassportModal.tsx`'s "Sikl {cycle.cycleNo}" heading and chiqim-lab-photo label, and `YieldTable.tsx`/`yieldExport.ts`'s "sikl {row.maxCycleNo}" badge/column — `cycleNo`/`max_cycle_no` are hardcoded to `1` server-side now (kept for JSON/row-shape compatibility with everything else still reading them), so these would have *always* displayed "Sikl 1," which reads as "there might be a cycle 2" to someone who doesn't know better. Nothing can produce a voided pallet through the UI anymore, so this code is unreachable in practice, but — like `stock_on_hand_rows`' `qayta_yuvish` bucket and `finished_pallets.status = 'bekor_qilingan'` before it — left correctly-derived rather than stripped, on the same reasoning already applied twice earlier in this session.
- **`full-chain.spec.ts` needed real restructuring, not just fixture updates** — see below.

**`full-chain.spec.ts`: sequence fix, plus a race-condition trail that took most of this task's own testing time to run down.** This pre-existing spec's own Laborator CHIQIM verdict ran *after* packing and Tugallash — valid under the old model (pack freely, test the completed cycle before Tugallash), backwards under the new hard gate. Restructured: the Laborator CHIQIM block (verdict, no more pallet `<select>`) now runs immediately after the Moyka send and before packing, with Ombor's own packing block gaining the role-switch it now needs (it used to inherit an already-logged-in Ombor session from the immediately-preceding step).

Getting this one spec green from there took far longer than expected, because the restructuring exposed a real, reproducible bug rather than a fixture mismatch: after the move, Ombor's own packing step (right after the Laborator excursion) intermittently rendered its target row absent, even though `moyka_sends`/`wash_cycles`/`lab_results` were confirmed correct via direct SQL at the moment of failure. Ruled out RLS (policy confirmed unchanged), token expiry (JWTs decoded live from the failing requests — valid, correctly scoped to Ombor), and "just needs more patience" (a flat 60s wait, 3× normal, still failed — proof nothing was ever going to retry on its own). Network capture *did* show something real along the way — `moyka_sends` occasionally queried carrying a stale JWT from the *previous* role, evidence of a pending fetch surviving past its component's own logout — but that wasn't the actual cause here, since a later, correctly-scoped request in the same trace still came back empty.

The actual cause, found by re-auditing every hook this session touched rather than the one screen that happened to be failing: `useLaboratorChiqim.ts` and `useLaboratorKirim.ts` had the identical missing-guard gap as `useMoykaOutput.ts`/`useMoykaSerials.ts` (see Test 1's own 🚩 entry above) — fixed the same way, with a monotonic request-id ref. That fix alone took this spec from failing at the packing step on every single run to passing it cleanly and consistently.

One further symptom surfaced past that point, not yet chased down: `LaboratorChiqimTab.tsx`'s own Window 3 ("Yakunlangan") sometimes shows a sulfured serial's row correctly moved out of "Sera kutilmoqda" (status genuinely `complete`) but without its verdict pill — `handleSera`'s single atomic `update({so2_mg_kg, status, verdict})` should never let one field of the same row read as committed while another doesn't, so this looks like the same general class of async-mutation/`refresh()`-ordering issue as the two bugs above, in a third location, rather than a new mechanism. Given this task's own explicit scope was Tests 1–3 on the wash-cycle relocation itself, and this is now clearly a broader, pre-existing pattern across several of this session's own rewritten hooks rather than anything specific to `full-chain.spec.ts`, it's flagged here rather than chased further: **worth a dedicated pass auditing every hook this session touched for the same missing-guard gap, and considering a shared `useOneShotFetch`-style helper so the protection is structural instead of copy-pasted per hook.** Test 1 and Test 2 above (the two specs this task actually asked for) show no trace of any of this and pass reliably on repeat runs.
