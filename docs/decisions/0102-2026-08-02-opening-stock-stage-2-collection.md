## 2026-08-02 — Opening stock, Stage 2 (collection)

**Context.** Stage 1 seeded old-washed pallets, old KN pools, and an old-raw serial, invisible to arrival/throughput reporting. This stage makes all three collectible: Menejer names the line, Ombor collects it, balances draw down correctly. `supabase/migrations/0050_opening_stock_stage2_collection.sql`, `0051_get_client_report_opening_stock_leak_fix.sql`, `0052_get_serial_passport_old_stock_badge.sql`.

**Schema.** `chiqim_lines_kind_shape` widened from `finished|raw` to five: `old_washed` mirrors `finished`'s shape (calibre + qty required — real pallets, same `chiqim_line_pallets` mechanism); `old_kn`/`old_raw` mirror `raw`'s shape (no calibre, qty optional). `old_kn_collections` (id, chiqim_line_id, pool_id, collected_kg, collected_at, created_by) is a new append-only table, structurally a twin of `raw_dispatch_lines` but anchored to `pool_id` instead of a serial — KN has no serial identity (Stage 1 design). Same RLS shape too: `read_all`, `ombor_writes` (insert-only, no update/delete — committed only at "Yuklashni yakunlash," never amended after, same precedent as `raw_dispatch_lines`). `stock_on_hand_rows`'s `old_kn_rows` CTE now subtracts real collections (`opening_kg − Σold_kn_collections`) instead of Stage 1's `opening_kg` stub.

**Old-washed and old-raw dispatch needed zero reporting-view changes.** Traced via `pg_get_viewdef` before writing anything: `report_chiqim_rows` reads `finished_pallets`/`dispatch_manifest` directly, `report_raw_dispatch_rows` reads `raw_dispatch_lines` joined through `chiqim_lines` — neither reads `line_kind` at all. Reusing the exact same tables for `old_washed`/`old_raw` means their dispatch events flow into Hisobot/the client report unfiltered, automatically, matching the established "departure/dispatch side stays unfiltered everywhere" principle for free. **Old-KN reporting visibility (a new `report_old_kn_rows` kind, `get_client_report` extension) was explicitly deferred to a later pass, per confirmation** — `old_kn_collections` exists and drains the pool correctly; the collection event itself isn't yet surfaced as a Hisobot/client-report line.

**🐛 Bug #1, found via explicit instruction to sweep proactively (not waiting for each to surface) — `wip_rows.raw_not_sent` flagged the old-raw serial with a fabricated "578 days waiting to be sent to Moyka."** Same root cause as Stage 1's `yield_rows` bug: `storage_intake.confirmed_at` was deliberately backdated to the 2025-01-01 seed anchor for `effective_qty` purposes (correct for balance math), and this WIP category reads that same column to compute "how long has this been sitting unsent" — a real, actionable question for current raw, but a nonsense number for old-raw's fabricated anchor. Fixed the same way, same narrower exclusion (`origin != 'opening_stock'`, not the `= 'delivery'` allowlist).

**🐛 Bug #2, found the same sweep, more severe — `get_client_report`'s `loss_totals`/`loss_output`/`loss_main` leaked exactly like Stage 1's `yield_rows` did, into a client-facing report this time.** The seed's synthetic `'final'` `wash_cycles` rows (old-washed, minted only to satisfy the hard gate) have `completed_date` backdated to 2025-01-01 with zero real `moyka_sends` but real `finished_pallets` weight. Any client-report query spanning 2025-01-01 picked up all 5 old-washed serials via `loss_totals`, producing `processedBreakdown.lossKg = -52210` (sent_kg=0 minus real calibreKg) — confirmed live *before* fixing it: `get_client_report(<Global Export>, '2025-01-01','2025-01-31')->'raw'->'processedBreakdown'` returned `{"lossKg":-52210,"calibreKg":52210,"konditirskiyKg":0}`, i.e. 52 tonnes materializing from nowhere in a real client's loss figure. `quality_record` had the same exposure via `arrival_date` (old-raw too, via its own `arrival_date`, even without a `wash_cycle_status='final'` to trigger the loss-side bug) — a period-spanning query would list these serials with empty/misleading lab fields under a fabricated date. Both fixed with the same `cl.origin != 'opening_stock'` exclusion; every other CTE in the function byte-identical to the live definition, confirmed via `pg_get_functiondef` before writing the replacement. Re-verified after the fix: same query now returns `{"lossKg":0,"calibreKg":0,"konditirskiyKg":0}` and `qualityRecord: []`.
