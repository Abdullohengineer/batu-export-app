# Phantom moyka_sends cleanup — 290726-068/069/072

## What happened

Serials `290726-068`, `290726-069`, `290726-072` each had their main
processing closed via Yakunlash on 2026-08-29, leaving a genuine raw
residual (92 / 29 / 36 kg respectively) unsent in Ombor. In September the
three residuals (157 kg total) were physically combined and sent to Moyka.
When the send was attempted in the app, it read as additional loss on the
closed serials, so Abdulloh backed out.

A prior read-only investigation (this session) traced the mechanism and
found the backing-out was incomplete: the send itself had already been
written to `moyka_sends` before Abdulloh backed out of the receive step.
`moyka_sends` has no status/void column and the app has no undo action for
a send — there was nothing in the UI's "cancel" to reverse, because the row
was already durable. Three rows landed, dated 2026-09-15, exactly matching
the three residual amounts:

| `moyka_sends.id` | serial | `sent_date` | `qty_kg` |
|---|---|---|---|
| `32c7e5c3-8c04-48a5-b9a6-97b922f1fd20` | `290726-068` | 2026-09-15 | 92 |
| `fc2fadfa-831d-4d96-8f22-49ee7d8376b3` | `290726-069` | 2026-09-15 | 29 |
| `f80f57f8-705f-4c9f-b88f-fdd461b28d41` | `290726-072` | 2026-09-15 | 36 |

**Root cause of the loss inflation:** `client_serial_loss_kg` (and
independently, `yield_rows`, `kirim_line_state`, `rahbar_dashboard_ledger`,
`get_client_report`) all compute a serial's "sent to Moyka" figure as an
**unconditional, all-time `sum(moyka_sends.qty_kg)`** once
`wash_cycles.closed_at` is set — no upper date bound, and no check that the
serial is still open. The three phantom rows landed directly in that sum
with no matching output, so each serial's booked `Yo'qotish` read 92/29/36
kg higher than the true, originally-closed figure:

| Serial | `client_serial_loss_kg` before | correct value |
|---|---|---|
| `068` | 142 kg | 50 kg |
| `069` | 74 kg | 45 kg |
| `072` | 89 kg | 53 kg |

No other mechanism contributed. Confirmed: no `storage_loss`-status
`finished_pallets` row exists on any of the three serials, and no
`old_stock_closeouts` row exists for this owner+type (the Yakunlash close
path — `close_wash_cycle_serial` — only ever writes `wash_cycles.closed_at`,
never touches `storage_loss`/`old_stock_closeouts`, which are a separate,
opening-stock-only mechanism). The arithmetic also closes exactly: the raw
balance formula every consumer shares
(`effective_qty − Σmoyka_sends − Σrezka_sends − Σraw_dispatch_lines`)
returned precisely 0 for all three serials with the phantom rows present,
and precisely 92/29/36 kg with them removed — matching the physically real
residual exactly, not an estimate.

## Correction

Deleted the three rows outright, via a single transaction with a paired
`audit_log` entry per row (same convention as every prior correction this
session, e.g. `docs/decisions/0187`). **This is an explicit, deliberate
exception to CLAUDE.md's never-DELETE convention**, justified narrowly:

- `moyka_sends` has **no void/status column at all** — unlike every other
  mutable table in this app (`finished_pallets.status`, `wash_cycles.
  closed_at`, `chiqim_requests.voided_at`), there is no soft-delete
  mechanism available to soften this with. This is itself a standing open
  gap, flagged in the investigation preceding this correction, not
  something this correction attempts to fix.
- The three rows never corresponded to a real, completed send event in the
  first place — the receive side was never completed, no `finished_pallets`
  rows exist from the attempt, and the send was immediately recognized as a
  mistake by the person who made it. There is no audit value in preserving
  a row that represents an abandoned attempt rather than a real business
  event — preserved via the `audit_log` insert instead, which is the
  standing convention for exactly this situation.
- The actual 157 kg combined reprocess is not lost — it will be
  re-registered as a real send event once **Path E** (multi-cycle
  `wash_cycles`, scoped in the investigation preceding this correction)
  ships. This cleanup does not consume or foreclose that work; it only
  removes three rows that were never a valid instance of it.

Pre-flight verification (read-only) confirmed all three rows present,
matching serial/`sent_date`/`qty_kg` exactly, with no extra or unexpected
rows, before the `DELETE` was applied. No `finished_pallets`,
`wash_cycles.closed_at`/`status`, or `lab_results` rows were touched.

Applied via `DELETE`, three rows, paired `audit_log` entries — archived at
`docs/data-corrections/2026-09-18_phantom_moyka_sends_cleanup.sql`.

## Out of scope, deliberately not touched

- **Path E** (multi-cycle `wash_cycles`, letting a closed serial register a
  second real Moyka cycle for a later reprocess) — a separate build, not
  started here.
- `close_wash_cycle_serial`, `wash_cycles` schema, `get_serial_passport`,
  `yield_rows`' grain — none modified.
- The 92/29/36 kg raw remainder is not re-sent or re-registered here — it
  now correctly sits as `raw_not_washed` stock again, exactly where it
  should, awaiting Path E.
