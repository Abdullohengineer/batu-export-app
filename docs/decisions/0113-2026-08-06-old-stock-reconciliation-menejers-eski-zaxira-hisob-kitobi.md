## 2026-08-06 — Old-stock reconciliation: Menejer's "Eski zaxira hisob-kitobi"

**Context.** Opening stock was seeded with approximate weights and has lost mass to dehydration over a year — a fully collected type still shows a remaining book balance that physically doesn't exist. This gives Menejer a screen to close a type out and book the shortfall as storage loss, isolated from processing loss so yield figures stay clean. `supabase/migrations/0064_pallet_status_storage_loss_value.sql`, `0065_old_stock_closeout.sql`, `0066_old_stock_closeout_dispatch_fix.sql`.

**(a) Leftover rows — three genuinely different mechanisms, not one forced-uniform one, confirmed before building anything.** Old washed flips `finished_pallets.status` to a new `storage_loss` enum value (`voided_at` reused, same column, same "when did this stop being real" meaning as the existing `bekor_qilindi` use, just a second reason now) — every consumer (`useAvailableFinishedStock.ts`, `stock_on_hand_rows`) already filters `status='in_stock'`, so this alone suppresses it everywhere for free. Old KN gets a `closed_at` timestamp directly on `old_kn_pools` (same "lifecycle flag on the entity" pattern as `wash_cycles.finalized_at`) — both Ombor's collection screen and Menejer's own pool-balance hint read exclusively through `stock_on_hand_rows`, confirmed by tracing the code, so one predicate there covers both. Old raw has no single entity to flag — the two-sided fix below.

**Bug caught before testing, not during it.** The first pass of `close_out_old_stock`'s `old_washed` branch and `old_stock_closeout_lines`' view both treated `finished_pallets.status='in_stock'` alone as "still remaining." That's wrong in this codebase specifically: nothing ever writes `status='dispatched'` (confirmed via `useAvailableFinishedStock.ts`'s own comment) — a genuinely departed pallet keeps `status='in_stock'` forever, with departure tracked entirely through `dispatch_manifest` + `gate_weighings.completed_at`. Left as-is, closing out a type would have swept up already-collected pallets into storage loss and corrupted their status. Fixed (`0066`) to match `stock_on_hand_rows`' own definition of "genuinely still on hand" exactly: `in_stock` AND not (`dispatch_manifest` exists AND gate completed).

**(b) The ledger: one new table, `old_stock_closeouts` (`kind, owner_id, type_id, book_remaining_kg, closed_at, closed_by`, `unique(kind, owner_id, type_id)`).** Read by nothing on the processing side — isolation from `yield_rows`/loss percentages is structural (no query exists to union it in), not a filter to remember. `yield_rows` itself already hard-excludes `origin <> 'opening_stock'` at its own source, so old-raw closeouts couldn't reach it even by accident.

**The old-raw two-sided fix, and the standing hazard it's built on.** Raw balance already has two independent implementations in this codebase — `stock_on_hand_rows`' `raw_rows` CTE (SQL) and `useMoykaSerials.ts`'s `available` (frontend, reads `storage_intake`/`moyka_sends`/`raw_dispatch_lines` directly, never touches `stock_on_hand_rows`). This predates this task and isn't fixed by it. Closing out an old-raw line therefore needed patching both, or the frontend picker (`ChiqimForm.tsx`'s old-raw sub-picker, via `useMoykaSerials`) would keep offering a line that `stock_on_hand_rows`/qoldig'i already hides. 🚩 **Standing hazard, not resolved here:** any future change to how raw balance is computed has to be made in both places by hand, or they will silently disagree. `stock_on_hand_rows`' `raw_rows` gets a full exclusion (`not exists` against the closeout table) rather than a partial subtraction — correct because close-out is all-or-nothing per scope ("close-out only for now, no partial recounts"). `useMoykaSerials.ts` fetches the same closeout ledger and zeroes `available` for any `isOldStock` serial matching a closed owner+type, guarded so a closed old-raw line can never zero out an unrelated regular serial for the same owner+type.

**`get_client_report`: a new top-level `storageLoss` section, sibling to `raw`/`oldKn`/`finished` — not nested, and not touching the raw reconciliation formula for two of the three kinds.**
- **Old raw** is the only kind needing a reconciliation change. `client_lines` gains two as-of-gated closure flags — `closed_before_from`/`closed_as_of_to` — because opening and closing balances need *different* date gates (a closure landing mid-period must still show the pre-closure balance at period start), the same shape as the existing `dispatched_before_from_kg`/`dispatched_as_of_to_kg` pair. `raw_opening_total`/`raw_closing_total` (and their by-type variants) exclude closed lines; a new `cumulativeStorageLossKg` reconciliation term keeps `balancesKg` at 0 — `xomKg` drops by the booked amount and `cumulativeStorageLossKg` rises by the identical amount, the same cancellation shape `cumulativeRawDispatchedKg` already uses.
- **Old washed** needs no reconciliation term at all — excluding `storage_loss` pallets from `client_pallets` (mirroring the existing `bekor_qilindi` exclusion exactly, same as-of gating) already removes it from `finished.closingKg` uniformly, and there is no separate finished-side reconciliation formula in this codebase to keep balanced.
- **Old KN** needs nothing here — its balance was never part of `get_client_report` to begin with (the prior task's own `oldKn` section is a flat events list, not a balance).

**The screen.** New `old_stock_closeout_lines` view (a UNION of three per-kind SELECTs, each using that kind's own natural opening/collected/remaining formula, LEFT JOINed to the closeout table so a closed line renders as a badge instead of vanishing) feeds `/menejer/eski-zaxira` ("Eski zaxira hisob-kitobi", `OldStockCloseoutTab.tsx`), added to `MenejerHome.tsx`'s nav and `App.tsx`. Per-line "Yakunlash" is a two-step confirm mirroring `OmborTayyorTab.tsx`'s Tugallash pattern exactly — shows the precise remaining-kg figure before committing. The close-out itself runs through one `security definer` RPC, `close_out_old_stock`, rather than granting Menejer new direct-write RLS policies on `finished_pallets`/`old_kn_pools` (neither of which Menejer otherwise writes — that's Ombor's domain) — same precedent as `mint_serial_from_sources`, and per CLAUDE.md's own rule that a status flip a writing role isn't permitted to make directly goes through a security-definer function, not app code. `old_stock_closeouts` itself has no direct write policy — written exclusively by the RPC, same precedent as `serial_mint_sources`.

**Verification — real fixtures, real Menejer auth (not the service role), all three kinds, live.** A raw `execute_sql` call can't exercise `close_out_old_stock`'s own `my_role() = 'menejer'` check (no `auth.uid()` in that context) — the close-out itself was run through the actual dev-server UI, logged in as the real `TEST Menejer` account, which also doubled as verifying the screen.
