## 2026-08-04 — Client reports stopped mutating retroactively (as-of-date reconstruction, raw side)

**Context.** The raw-side twin of the 2026-08-02 finished-side fix, queued explicitly in that entry and in the connectivity audit. `client_lines.has_intake` and `effective_qty` (sourced from `report_kirim_rows.qty_kg`) both read current state, so a serial ordered inside a closed period but accepted into storage after that period ends retroactively joins the closed period's raw balance. Unlike the finished-side defect, this one fires on every ordinary Ombor intake accept — not only on re-wash — so closed-period raw figures were never actually stable. `supabase/migrations/0061_get_client_report_raw_as_of_date_stability.sql`.

**Mechanism.** `report_kirim_rows_as_of(p_to date)` is a faithful clone of `report_kirim_rows`'s own ladder logic — the CASE expressions are copied verbatim, not reimplemented, avoiding a third parallel implementation alongside `effectiveQty.ts` and the live view. Exactly three joins are date-gated:
1. The outer `storage_intake` join (`has_intake` / `qty_kg` / `provisional`): the join predicate itself carries `confirmed_at is not null and (confirmed_at at time zone 'utc')::date <= p_to`, so acceptance after `p_to` makes `si.actual_qty` read NULL and the existing "not yet accepted" branch fires unchanged.
2. The `box_mass` CTE's per-line `storage_intake` join (the `bool_and` "were ALL lines on this order accepted" gate) — same predicate, applied per line before the aggregate runs, so a line accepted after `p_to` correctly makes the whole order's `total_box_mass_kg` read NULL as of that date, not just as of now.
3. The `gate_weighings` lateral nulls out `completed_at` itself (rather than editing every CASE branch) when its date is after `p_to` — every branch already null-checks `completed_at` before reading `net_kg`, so this one change cascades through `qty_kg`, `provisional`, both `truck_variance_diff_*` fields, and `provisional_variance_flag` for free.

`es` (earliest Moyka send) and `lr` (latest lab reading) are deliberately **not** gated — not part of `has_intake`/`effective_qty`, not read by `client_lines` at all, and not named in the bug's own two culprits.

`get_client_report.client_lines` changes on exactly two lines: `join report_kirim_rows rkr` → `join report_kirim_rows_as_of(p_to) rkr`, and its own separate `left join storage_intake si` (which drives `has_intake` — a boolean `client_lines` computes itself, not a column the view exposes) gains the identical join-predicate gate. Every downstream CTE (`raw_opening/closing/received_total` and `_by_type` variants, `moykada_total`, all four `cumulative_*_total`) inherits the fix automatically since they all read through `client_lines` — no other CTE needed touching.

**Scope, held deliberately narrow.** Only `get_client_report` switches to the as-of view. `wip_rows`, `stock_on_hand_rows`, `yield_rows`, `report_rows`, and the three Rahbar functions (`rahbar_monthly_trends`, `rahbar_client_ranking`, `rahbar_product_mix`) all correctly want live current state — "what does the warehouse look like right now" — and are untouched.

**Two deliberate semantic changes, both changing previously-reported historical output:**
- **A serial ordered in one period but accepted in a later one now leaves the earlier period's raw balance entirely.** It wasn't physically in the warehouse yet, so this is correct, not a bug — but it means a previously-printed closed-period statement won't match a re-run after this fix ships. Falls out automatically from gating `has_intake`; no separate branch needed.
- **`raw_received_total` also stabilizes, not just the opening/closing balance.** It isn't gated by `has_intake` — it sums `effective_qty` by `arrival_date` alone, which is correct (a truck that arrived in June was received in June regardless of when Ombor gets around to accepting it). But it read the *live* `effective_qty`, so a closed period's `receivedKg` used to drift from `declared_qty` to whatever the actual turned out to be once accepted, even in a re-run months later. Now frozen to what was known as of `p_to` — `declared_qty` until acceptance is on the books as of that date. In scope because the bug description names `effective_qty` directly, not only `has_intake`.

**Verification — real before/after numbers, byte-identical stability test, current-period agreement, full cleanup.**

Dedicated TEST owner ("TEST — as-of verification (safe to delete)") with two disposable kirim orders or­dered inside 2026-06 (`ASOF-VERIFY-01`/`-02`, serials `TEST-ASOF-01`/`-02`, 1,000 kg / 500 kg declared) — not `TEST-`-plated, since `report_kirim_rows`'s own `plate !~~ 'TEST-%'` filter would have excluded them from the report entirely and made the mechanism untestable; isolated instead under a dedicated owner so no real client's report is touched.

- **A0 (pre-fix, pre-accept):** `get_client_report(TEST owner, 2026-06-01→2026-06-30)` → `raw.closingKg 0`, `reconciliation.totalReceivedKg 0`, `receivedKg 1500` (arrival-date-only, correct and unaffected by intake status).
- **A1 (pre-fix, after accepting `TEST-ASOF-01` on 2026-08-04, unchanged as an August event):** same closed period → `closingKg` moved **0 → 1000**, `totalReceivedKg` moved **0 → 1000**. Real numbers, real function, the bug reproduced live: an August acceptance retroactively changed a June report.
- **Migration applied.**
- **B1 (post-fix, identical data to A1):** re-run → `closingKg 0`, `totalReceivedKg 0` — back to **A0**, byte-identical. The fix restores correctness even with the acceptance already on the books.
- **B2 (post-fix, after accepting the second fixture `TEST-ASOF-02` on 2026-08-04 — the literal "accept an intake dated inside the window, re-run" test, done post-fix with a genuinely fresh mutation rather than a no-op):** re-run → identical to **B1** in every field, byte-for-byte.
- **Current-period agreement with Ombor qoldig'i:** `get_client_report(Global Export, 2020-01-01→today)` → `raw.closingKg 40,993.4`. `stock_on_hand_rows` `raw_not_washed` bucket for the same owner → **40,993.4** across 7 rows. Exact match. `reconciliation.balancesKg` = **0**.
- **Cleanup:** both `storage_intake` rows, both `kirim_orders` (cascading their `kirim_lines`), and the TEST owner deleted; confirmed 0 leftover `TEST-ASOF%` rows anywhere.
