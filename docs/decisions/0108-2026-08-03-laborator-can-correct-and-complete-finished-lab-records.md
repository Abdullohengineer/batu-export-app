## 2026-08-03 — Laborator can correct and complete finished lab records

**Context.** Several recent KIRIM loads were entered without an SO₂ target, so the sulfur field was hidden (§5.5.1: no target = natural product) and the records completed straight to Yakunlangan with moisture only. Those loads do need sulfur, and there was no way to add it after the fact — the Sera step never existed for them, and nothing on either Laborator tab could revisit a completed record at all.

**Investigation, before any code.** Of the six real (non-opening-stock) `kirim_lines` with a null SO₂ target, four already had a `complete`-status `lab_results` row (moisture only, SO₂ null) and two had never been sampled at all. For the two untested ones, setting the target alone is sufficient — `KirimTahlilForm`'s `isSulfured` check reads the target live at Tahlil time. For the four already-complete ones, setting the target alone does nothing: routing to the amber Sera window is driven entirely by `lab_results.status`, set once at save time and never re-evaluated — a `complete` row stays `complete` forever regardless of a later target change. The edit action was genuinely required, not a simpler no-code fix.

**Two things found during investigation that corrected the task's own framing:**
- **`useLaboratorKirim.ts` had no latest-wins resolution at all** — the one hook in this family never given it. `get_client_report`'s `intake_lab` CTE and `get_serial_passport`'s `kirim_lab` CTE both already correctly do `order by created_at desc limit 1`, and `useLaboratorChiqim.ts`/`labVerdict.ts`'s `currentLabStatus` already implement the identical newest-first, first-kept-per-key pattern — but `useLaboratorKirim.ts`'s own `resultBySerial` map was built from an unordered fetch with a plain last-in-array-wins `Map` construction. Inserting a superseding row without fixing this would have made the Laborator KIRIM tab itself resolve non-deterministically between the original and the correction. Fixed to match the established pattern exactly (`.order('created_at', {ascending:false})` + first-kept-per-serial loop, same shape as `labVerdict.ts`).
- **"Sera kiritish" is an UPDATE, not an insert**, on both tabs — not itself an example of the superseding-row pattern. The real precedent is the CHIQIM re-test case (`labVerdict.ts`: "a reject followed by a re-test is a NEW lab_results row against the SAME wash_cycle_id").

**Target values.** Set `target_so2_mg_kg = 2000` on all six affected `kirim_lines` (280726-029, 290726-068, 290726-069, 290726-070, 290726-071, 290726-072) — confirmed with the user first, applied via direct SQL (production data). 2000 mg/kg is a ceiling: any reading under it is acceptable, only readings above it should warn. Added the identical soft-warn treatment (informational, never blocking, same shape as `ChiqimTahlilForm`'s existing moisture warn) to every SO₂ entry point that now uses this target: both tabs' existing Sera kiritish step, and both new edit forms' SO₂ fields — not just the new code, since Sera kiritish uses the same target and would have been inconsistent otherwise.

**The edit action, built for both KIRIM and CHIQIM.** Scoped to this session's own "unless it genuinely doubles the work" test: `useLaboratorChiqim.ts` already had the correct ordering (zero extra fix needed there), and the CHIQIM form only adds two fields (sampled-pallet text, verdict) over the KIRIM one — estimated 30-40% more work, not a doubling, so both shipped together.

- `KirimTahlilEditForm.tsx` / `ChiqimTahlilEditForm.tsx` (new) — every field on the record is editable: sample date, moisture, SO₂ (shown whenever a target now exists, unconditionally enterable unlike the original form's "wait a day" gate, since this save IS the result), the defect note, and — CHIQIM only — sampled-pallet and verdict. A left-blank photo keeps the previous sample photo rather than dropping it.
- **Inserts a superseding row, never updates in place** — these are quality records feeding client reports; a changed value must stay traceable, and the original row is never touched. `status` is always `'complete'` (editing only ever applies to Window 3; Window 2's moisture-in rows already have Sera kiritish as their own entry point).
- **Verdict on the CHIQIM edit form is never silently carried forward.** Per §5.5.3's own invariant ("the verdict is an explicit click — never auto-derived, even when the reading obviously misses target"), that extends to editing: the current verdict is shown as context, but saving still requires clicking one of the two buttons — it may reaffirm the same verdict or deliberately change it, but there is no neutral "Saqlash" that could read as verdict-preserving. Changing it does **not** retroactively unmake pallets already packed under the prior verdict — the hard gate (SPEC §5.5.3) is checked only at Barcode #2 assignment, at that instant, never re-checked retroactively; it only changes what CURRENT lab status reads from that point on.
- **Inline-toggle UI**, matching `KirimOrdersList.tsx`'s existing "Tahrirlash" pattern rather than a new three-dot menu, per explicit instruction.
- No schema change: INSERT is already granted to Laborator via the existing `laborator_writes` RLS policy, the same one the original Tahlil insert uses.

**Verification — live, with a disposable `TEST-` fixture, not the real records.** The mechanism itself (insert a superseding row) is reversible, but writing a fabricated SO₂ reading onto a real, already-completed client-facing quality record — even briefly — is not something to do just to prove the UI works; the four real records are left for Laborator's own actual lab correction using the new UI. Built one `TEST-LABEDIT-01` KIRIM fixture (mirroring the exact broken shape: `complete` status, moisture only, SO₂ null) and one `TEST-LABEDIT-02` CHIQIM fixture (same shape plus `verdict='o_tdi'`), both `origin='delivery'` so they exercise the same code path real serials do.

- **Requirement 4 confirmed live**: with the target set, the SO₂ field appeared on the edit form immediately, no special-casing needed.
- **Ceiling warning confirmed live**: entering 2500 (above the 2000 target) showed "Talabdan yuqori (2000 mg/kg) — baribir saqlash mumkin."; correcting to 1500/1800 cleared it; both saved successfully either way.
- **Superseding confirmed on both tabs**: after edit, exactly two `lab_results` rows exist per fixture — the original untouched (SO₂ null, original note) and a new row (SO₂ set, new note, later `created_at`). The Laborator screen itself immediately showed the corrected value (proving the `useLaboratorKirim.ts` ordering fix).
- **Resolution confirmed everywhere it matters**: `get_serial_passport`'s `kirimLab`/`cycles[0].lab` returned the corrected row for both fixtures. `get_client_report`'s `intake_lab`/`delivered_lab` CTEs, isolated and run directly against each fixture's `lab_results` rows (the fixtures' `TEST-` plates make them invisible to the outer arrival-date filter by the same pre-existing convention every other `TEST-` fixture this session relies on — expected, not a defect, and orthogonal to the resolution logic being tested), also returned the corrected row. Both CTEs already used the correct `order by created_at desc limit 1` pattern before this task; nothing needed to change there.
- Both fixtures fully deleted afterward — zero `TEST-LABEDIT%` rows remain.

**Verification.** `npx tsc -b --noEmit` clean. Unit suite 82/82. Playwright 4/5 — the same long-standing `full-chain.spec.ts` flake, unrelated to this change (fails at the identical locator).

**Out of scope:** Menejer-side target editing (separate follow-up, per the original task).
