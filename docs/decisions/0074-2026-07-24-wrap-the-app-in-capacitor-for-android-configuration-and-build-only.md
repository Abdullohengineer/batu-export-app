**Bundled locally, not pointed at Netlify.** `capacitor.config.ts` has no `server` block at all — Capacitor's default behavior with `server` unset is to serve `webDir` from the bundled local assets via its own local server (`https://localhost`, not a real network request), which is what makes the shell load with zero signal. `webDir` points at `dist-native/` (see below), and Capacitor's default `https` scheme is what allows `getUserMedia` (a secure-context API) to work fully offline in the WebView — nothing extra needed for that.

**PWA service worker — separated by build mode, not by touching the plugin's own config.** `vite.config.ts` now takes the `mode` Vite already passes to `defineConfig`'s function form: when `mode === 'capacitor'`, the `VitePWA` plugin is skipped entirely (`.filter(Boolean)` over the plugins array) and `build.outDir` becomes `dist-native` instead of `dist`. Every other mode (`npm run dev`, plain `npm run build`) is byte-for-byte unchanged — same plugin, same Workbox config, same `dist/`. A new `build:native` script (`tsc -b && vite build --mode capacitor`) is the only thing that ever passes that mode. Verified, not assumed: built both outputs back to back — `dist/` still contains `sw.js`, `workbox-*.js`, `manifest.webmanifest`, `registerSW.js`; `dist-native/` contains none of them, just `index.html` + hashed JS/CSS/wasm. `npm run cap:sync` (`build:native` then `npx cap sync android`) is the one command that gets a fresh build into the native shell.

**Android permissions.** Capacitor's default template already declares `INTERNET`; added `CAMERA` (`AndroidManifest.xml`) since barcode scanning feeds `getUserMedia` frames to `BarcodeDetector` in-page, no native camera plugin involved — Capacitor's stock `BridgeActivity`/`WebChromeClient` forwards the WebView's `getUserMedia` permission prompt to Android's runtime permission system automatically once the manifest declares it, so no custom native code was needed. Also added `<uses-feature android:name="android.hardware.camera" android:required="false">` so a camera-less device isn't filtered out of installability — manual barcode entry is a fully supported fallback already. Checked the final **merged** manifest from the Gradle build (not just the source one) to confirm nothing extra got pulled in by a dependency: `INTERNET`, `CAMERA`, the `uses-feature`, and one auto-injected `…DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` signature permission that AndroidX Core adds unconditionally on target SDK 33+ (Android 13's dynamic-broadcast-receiver export rule) — boilerplate every modern Capacitor app carries, not a real user-facing permission and not something this task added. Nothing Bluetooth-related, as instructed.

**Env vars — no new mechanism, reused what already exists.** Vite loads plain `.env` for *every* mode, including a custom one (`.env.[mode]` files are additive on top, not a replacement) — so the same gitignored `.env` a developer already has for `npm run dev` also feeds `build:native` with zero extra configuration. **Flagged, not fixed (out of scope — no UI/routing change made):** `BrowserRouter` uses the History API; Capacitor's local WebView server does not automatically fall back to `index.html` for an arbitrary sub-path the way Netlify's SPA redirect does. In the ordinary case this is a non-issue — the app always cold-starts at `/` and every in-app navigation is client-side `pushState`, exactly like a fresh browser tab hitting the Netlify root today. The one scenario worth testing on-device: if Android reclaims the app's process while it's backgrounded on a sub-route (e.g. `/menejer/chiqim`) and the WebView's navigation state is restored to that URL on relaunch rather than the app cold-starting at `/`, the local server has no file at that path. Not reproduced or fixed here — App.tsx routing was explicitly read-only per the task's scope. If it does turn up on-device, the fix is small (either a WebView-state-restore opt-out so the app always cold-starts at `/`, or a local server fallback rule) and shouldn't need a router change.
