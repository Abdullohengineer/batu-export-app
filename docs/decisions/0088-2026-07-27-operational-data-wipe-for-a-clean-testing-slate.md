## 2026-07-27 — Operational data wipe for a clean testing slate

Requested directly (not code-driven): clear every operational row so the app is a fresh slate for end-to-end testing, keeping master data intact. `supabase/seed/wipe-all-operational-data.sql` (2026-07-21) was the obvious starting point but turned out stale in two ways once checked against the live schema rather than trusted as-is: it has no statement for `chiqim_line_pallets` (didn't exist yet when it was written — this session's own CHIQIM Option B table, see above), and it deletes `owners`, which this task explicitly wants treated as master/config data, not operational. Delete order was re-derived from the **live** FK graph (`list_tables` verbose, not the migration files — those turned out stale too: `lab_results.request_id` doesn't exist anymore, it's `parent_serial`/`wash_cycle_id` since the v1.9 reshape).

**Order used** (children before parents, verified against every live FK, not assumed): `chiqim_line_pallets` → `dispatch_manifest` → `chiqim_lines` → `gate_weighings` → `chiqim_requests` → `lab_results` → `finished_pallets` → `wash_cycles` → `moyka_sends` → `storage_intake` → `kirim_lines` → `kirim_orders` → `notes` → `serial_counter` → `audit_log`. `serial_counter` included deliberately — leaving a day's counter row behind would make the next serial minted that day continue from the old count instead of starting fresh at `-001`. Run via the Supabase MCP's direct Postgres connection (same path `apply_migration` uses), not the app's RLS-constrained client — most of these tables have zero delete policies for any role by design (§2.15 "never delete, only void" — see `teardown.ts`'s own comment), so this was the only path capable of clearing them at all.

**Master data confirmed untouched:** `profiles` (10), `settings_limits` (9), `calibres` (9), `product_types` (5), `owners` (6), `product_categories` (1). One judgment call flagged and left as-is per the user's own choice: `owners` contains one inactive row, `"Sinov Mijozi QA"` ("Test Client QA") — textbook test debris but not literally `TEST-`-prefixed, and `owners` is explicitly master data / out of scope for this task, so it was surfaced rather than deleted unilaterally.

**Result, verified live:** all 15 operational tables (461 `audit_log`, 58 `finished_pallets`, 38 `lab_results`, 32 `gate_weighings`, 28 `moyka_sends`, 24 `wash_cycles`, 23 `kirim_lines`, 21 `storage_intake`, 21 `kirim_orders`, 15 `dispatch_manifest`, 14 `chiqim_requests`, 7 `chiqim_lines`, 7 `serial_counter`, 2 `chiqim_line_pallets`, 0 `notes`) read **0** after. No app code, schema, or master data touched.

**Flagged, not fixed here (out of scope for this task):** `supabase/seed/wipe-all-operational-data.sql` itself is now stale for the reasons above — running it as-is today would error on the missing `chiqim_line_pallets` statement and would delete `owners` against this task's own policy. Left as found; worth a follow-up pass whenever it's next needed.
