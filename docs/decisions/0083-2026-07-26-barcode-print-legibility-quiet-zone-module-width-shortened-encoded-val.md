## 2026-07-26 — Barcode print legibility: quiet zone, module width, shortened encoded value

**Context:** printed 40×30mm labels don't scan (dense bars, near-zero quiet zone); the same code scans fine off a screen, confirming this is print geometry, not the decoder — real photo evidence provided.

**Inspected and reported before coding, per the task's gate.** Decompiled the real LPAPI jar (`javap` against `LPAPI-2026-01-08-R.jar`, cross-checked against the PDF and demo source — same discipline the original P1 printer task used, since that task already found one real PDF/jar divergence) to get `draw1DBarcode`'s exact signature: `(text, type, x, y, width, height, textHeight)`, `width` documented as "the overall display width of a 1D barcode" — LPAPI auto-derives module width from content length + this target. Current call: `x=2, y=1.5, width=36, height=10, textHeight=2.5` on a 40mm label → **2mm quiet zone per side** (real, not zero, but thin).

**Measured module density with the app's own `jsbarcode` dependency, not estimated.** `PLT-210726-011-07-1` is 19 characters (the task text said 20 — minor miscount) and encodes to **233 CODE_128 modules** → `36/233 ≈ 0.155mm/module` at the current width, well under commonly-cited reliable minimums (~0.25mm+) for phone-camera 1D scanning.

**Minimum safe encodable value — investigated, not assumed.** Traced the sole mint point (`FinishedReceiptForm.tsx:59`, `` `PLT-${serial.serial}-${code}-${existing + 1}` ``, inserted verbatim at `OmborTayyorTab.tsx:158`) and confirmed only the constant `PLT-` prefix is safe to drop from the *encoded* value (19→15 chars, 233→**178 modules**, measured):
- The trailing pallet-sequence digit is unbounded/unpadded (`existing + 1`, no `padStart`) — de-hyphenating it would make pallet #10+ for a serial+calibre ambiguous to parse back.
- Calibre codes aren't uniformly numeric — `useCalibres.ts` documents `code: '04' | '06' | 'KN' …` — a digits-only encoding (the task's own stretch proposal) silently breaks for Konditirskiy.

**The real constraint that shaped the fix: on a fixed 40mm label, growing the quiet zone and thickening bars pull in opposite directions unless content shrinks first** — with 19 chars fixed, there's no room to both widen margins and thicken bars; one comes at the other's expense. This is why the prefix-drop isn't cosmetic — it's what makes the other two levers compatible. Reported this explicitly and got confirmation before implementing, along with two other open questions:
- **Text-suppression risk**, confirmed and flagged rather than assumed: `draw1DBarcode` ties its own auto-rendered readable text to the same `text` argument that drives the bars — there's no separate "encode this, show that" option. Shortening the bars would also shorten LPAPI's own text line unless suppressed. Chose to attempt `textHeight=0` and draw the full value explicitly in its place — confirmed this is genuinely unverified (LPAPI's own docs use `0` for `drawText`'s width/height to mean "auto-size," not "hide," so there's no basis to assume the same convention holds for `textHeight`) rather than presenting it as certain.
- **QR as a follow-up**: assessed, not pursued blind. Even the best safe geometry fix (below) lands around 0.19mm/module — a real, verified improvement but still short of a comfortable phone-camera margin. Confirmed to defer until after this fix gets a real print/scan test, rather than build QR speculatively.

**Implementation, `P1PrinterPlugin.java` (`drawAndCommit`):**
- `barcodeEncoded = barcode.startsWith("PLT-") ? barcode.substring(4) : barcode` — encoding-only, `barcode` itself untouched everywhere else.
- `draw1DBarcode(barcodeEncoded, CODE128, 3, 1.5, 34, 7.5, 0)` — x/width tightened from `2/36` to `3/34`: quiet zone grows 2mm→3mm per side (+50%) while module width still improves to `34/178 ≈ 0.191mm/module` (+24% over today) — both gains land simultaneously specifically because content shrank first. `textHeight=0` attempts auto-text suppression (see risk above).
- `drawText(barcode, 3, 9, 34, 3, 2.3)` — new, explicit — the full `PLT-...` value, in the space LPAPI's own auto-text used to occupy. Every other line (`serial`/`typeLine`/`weightLine`/`clientLine`) untouched, exact same position/size as before.

**Implementation, `OmborChiqimTab.tsx` (`processBarcode`):** one-line normalization right after the empty-input guard — `if (!barcode2.startsWith('PLT-')) barcode2 = \`PLT-${barcode2}\`` — reassigns the parameter itself so every downstream use (both `finished_pallets`/`dispatch_manifest` lookups, `resolveScan`'s own `barcode2` field) picks up the normalized value with no other code change. Backward-compatible by construction: a full-value scan/manual entry (older labels, or the prefix typed by hand) matches as-is since the check is a no-op when the prefix is already present. `barcodeLabel.ts` (web preview) deliberately left untouched — it's explicitly a preview only, already documented as free to drift from native (DECISIONS.md "P1 printer integration" — native prints, web previews), and scanning always reads the real printed sticker's actual encoded bars regardless of which build is doing the scanning, so the shared `processBarcode` normalization is what makes scanning work everywhere, not anything in the preview renderer.

**Verified live — the lookup/normalization specifically, not just reasoned.** Camera hardware unavailable in this sandbox (standing limitation, every camera task this session), so verified via manual entry, which shares the identical `processBarcode` code path as a camera decode. Queried a real, available pallet (`PLT-210726-002-06-2`, Isfara/Kalibr 6), typed the prefix-stripped form (`210726-002-06-2`) into the manual field on an open request wanting a *different* calibre (Isfara/Kalibr 7). Result: **"Bu tur/kalibr ushbu so'rovda yo'q."** — the `no_matching_line` outcome, only reachable if the pallet lookup already succeeded (a failed lookup would have produced "Bunday barcode topilmadi." instead). This conclusively proves the normalization correctly reconstructs the full `barcode2` and finds the real row. No state was written (a rejection is a no-op), so nothing needed cleanup.
