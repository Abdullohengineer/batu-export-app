## 2026-08-03 — Opening-stock connectivity audit (the checklist that should have existed upfront)

**Context.** Seven separate origin/timestamp leaks had been found reactively across the Stage 1-3 build, each caught only after it was already live. This task was the audit that should have preceded all of it: 26 explicit checklist items (5 Ombor screens, 2 Qorovul, 3 Menejer, 2 Laborator, 2 Rahbar, 12 report/view SQL objects) plus an open-ended sweep for anything reading `origin`/`confirmed_at`/`finalized_at`/`received_date`/`completed_at` not on the list, plus a dedicated cross-consumer check that the 2026-08-02 Qand→Qand Qizil correction actually held everywhere. Verification only — query or click each item, don't assume from code; fix only confirmed defects.

**Method.** The 14 role-scoped UI items were driven live in the browser, one role at a time (session storage is shared per browser profile, so role logins can't run concurrently) — actually clicking through Ombor, Qorovul, Menejer, Laborator, Rahbar as the real test accounts, including submitting a real CHIQIM request spanning all three old-stock line kinds (`Eski (yuvilgan)`/`Eski KN`/`Eski xom`) to watch it render at each downstream stage. The 12 SQL view/function items plus the sweep plus the Qand Qizil cross-check ran as a 15-agent background workflow in parallel with the UI pass, each agent required to fetch the *live* `pg_get_viewdef`/`pg_get_functiondef` (never trust a migration file in isolation) and run real queries as evidence.

**Result: 22 of 26 items pass as designed. Four confirmed defects, all four fixed and verified live** (the fourth edits `get_client_report`, a live migration on the shared project, and per this file's own standing workflow rule was shown and confirmed before applying — the confirmation and the fix landed in a separate follow-up turn from the three frontend-only fixes below, which shipped directly).

**🐛 Defect 1 — Laborator's KIRIM tab showed all six opening-stock lines.** `useLaboratorKirim.ts` had zero origin filtering (the one hook in this family that was never touched by the 2026-08-02 hotfix). Live: five washed master serials sat forever behind "⏳ Darvoza (1-bosqich) kutilmoqda" (a gate event that will never happen), and the sixth — old raw stock (`020826-039`) — had a *synthetic* `gate_weighings` row (deliberately added by the Stage 1 seed, migration 0048, so `effective_qty` would resolve final instead of stuck provisional) that made it fully actionable with a live "Tahlil" button on fabricated stock. Fixed with the same positive allowlist (`.eq('origin', 'delivery')`) already used by `useKirimTrips`/`useIntakeLines`. Verified live: reload dropped the count from 12 to 6, all six remaining rows real deliveries.

**🐛 Defect 2 — Ombor's own Hisobotlar (intake history) had the same hole.** `useIntakeHistory.ts` fetched `kirim_orders` with no origin filter at all. Confirmed live: widening "Sanadan" back to 2024-01-01 does nothing today only because the UI's default 30-day window happens to hide it — the fabricated `020826-039` intake (2,880 kg, confirmed 2025-01-01) was one date-filter click away from rendering as a real receipt. Same fix, same allowlist. Verified live post-fix: date range widened to 2024-01-01, still exactly 6 real rows.

**🐛 Defect 3 — Qorovul's own Hisobotlar (gate history) had the same hole again.** `useGateHistory.ts` embeds `kirim_orders` via PostgREST with no origin filter, and per its own header comment fetches the *entire* `gate_weighings` table client-side (a pre-existing, separately-flagged scaling limitation, not part of this fix) — meaning the fabricated gate row for `020826-039` was already downloaded to every Qorovul session, just hidden by the date filter. Fixed the same way (embed now includes `origin`, filtered to `'delivery'`; CHIQIM-direction rows pass through unfiltered since dispatch is origin-agnostic by design). Verified live post-fix: date range widened to 2024-01-01, still exactly 5 real completed trips.

**All three defects share one root cause.** `origin='delivery'` filtering was added to the *few* hooks directly implicated in the 2026-08-02 phantom-truck hotfix (`useKirimTrips`, `useIntakeLines`) but never propagated to the sibling "history" hooks for the same two roles, nor to Laborator's KIRIM hook — three more places reading the identical `kirim_orders`/`storage_intake`/`gate_weighings` join with the identical missing filter. This is exactly the class of gap the audit's own sweep phase was built to catch (see workflow findings below) rather than a new, unrelated bug.

**🐛 Defect 4 — `get_client_report`'s `finished.producedKg` counts the entire opening-stock seed as "produced" whenever a report period includes 2025-01-01. Fixed and applied** (`supabase/migrations/0060_get_client_report_exclude_opening_stock_produced.sql`). Confirmed live before the fix: `get_client_report(Global Export, '2025-01-01','2025-01-01')` → `finished.producedKg = 52,210`, i.e. the whole fabricated seed reported as if produced on a single day. `client_pallets` (migration 0058) carried no origin filter at all, unlike `loss_totals`/`quality_record` in the same function which already exclude `origin != 'opening_stock'`. The fix is *not* a blanket exclusion on `client_pallets` — that would also drop opening stock from `openingKg`/`closingKg`, understating a real client's real physical inventory by 52,210 kg for any period that doesn't straddle the fabricated date. `finished_produced_total`/`finished_produced_by_calibre` gained `and origin != 'opening_stock'` (production events exclude the fabrication); `finished_opening_total`/`finished_opening_by_calibre` gained `or origin = 'opening_stock'` alongside the existing `received_date < p_from` test (opening stock always counts as pre-existing balance, regardless of where `p_from` falls relative to 2025-01-01). `dispatchedKg` is untouched: a real dispatch of old stock today is a real event, matching the existing origin-agnostic precedent in `report_raw_dispatch_rows`/`rahbar_client_ranking`'s dispatch CTE.

**Boundary case caught during verification, before this ever shipped.** The first version of the fix applied only the `producedKg` guard. Testing the straddling case the user specifically asked about (`p_from='2025-01-01'`, either as a single day or as the start of the full lifetime range) revealed `finished.closingKg` dropping to **0**, not 52,210: `finished_opening_total`'s own `received_date < p_from` is a *strict* inequality, so opening stock (dated exactly 2025-01-01) failed that test too whenever `p_from <= 2025-01-01` — with `producedKg` now correctly excluding it, the 52,210 kg fell into neither bucket and vanished, trading an overcount for an undercount. Per explicit instruction ("must always count as opening regardless of whether the period straddles 2025-01-01"), added the `or origin = 'opening_stock'` arm described above and re-applied before reporting success. Safe unconditionally, not just for realistic periods: `client_pallets`' own `WHERE` already requires `fp.received_date <= p_to` for a row to exist there at all, so an opening_stock row is structurally unreachable for any `p_to` earlier than 2025-01-01 — there is no query shape where the added `or` could misfire on a genuinely out-of-range period.

**Verified live, all four period shapes give the identical, correct result** (`openingKg: 52,210, producedKg: 0, closingKg: 52,210`, `byCalibre` summing to the same 52,210): a single day exactly on the seed date (`2025-01-01..2025-01-01`), the full lifetime from the seed date (`2025-01-01..today`), a genuine straddling range (`2024-06-01..2026-06-01`), and a non-straddling range (`2026-01-01..today`). `raw.reconciliation.balancesKg` stayed **0** for the straddling range (the raw side is untouched by this fix and was already correct).

**22 items confirmed passing, with notable design findings (not defects):**
- **Item 1 (Qoldig'i)** is scoped to Menejer/Rahbar only — SPEC.md §3.2.6 says so explicitly, and there is no `/ombor/qoldiq` route. The checklist's own "Ombor screens" framing was a scoping mismatch, not a bug; verified the underlying behavior via Menejer instead (all three old-stock kinds present, correctly labelled "Eski zaxira 2025-2026", Qand Qizil correction holding).
- **Item 9 (KIRIM order list)**: neither `opening_stock` (created_by is `NULL`) nor `internal_reprocess` (created_by is always an Ombor actor, per `mint_serial_from_sources`) can ever match any Menejer's own `profile.id`, so both are structurally invisible on `KirimOrdersList` — correct in effect, but as a side-effect of an ownership filter ("my own submissions"), not a deliberate origin filter.
- **Item 10 (Hisobot search)**: contradicts its own stated expectation. `report_rows` hard-filters `origin = 'delivery'` on the KIRIM branch, so opening stock is unreachable by search, not merely excluded from totals — confirmed live (searching `020826-037` with the date range widened to 2020 still returns "Natija topilmadi"). Reported as ambiguous rather than fixed: this matches the exclusion pattern used everywhere else by design, and a serial's full history stays reachable via the passport drill-down; whether Hisobot search specifically should reach opening stock was never a decided requirement, just this checklist's own assumption.
- **`get_client_report`'s raw-side origin handling** (`raw_received_total`/`raw_received_by_type` positive-allowlist, others unfiltered) was observed only, per instruction not to re-litigate the already-known, separately-queued raw-side as-of-date defect.
- Every processing/production aggregate (`yield_rows`, `rahbar_monthly_trends`'s yield-derived columns, `wip_rows`' non-`raw_not_sent` branches, `lab_turnaround_avg`) correctly admits `internal_reprocess` while excluding `opening_stock` — confirmed via a live `internal_reprocess` order (`030826-017`) that existed transiently during the audit (a hand-verification fixture from earlier in this same session, since reverted) and was independently observed passing the relevant filters before it was cleaned up.
- `lab_turnaround_avg`'s opening-stock exclusion is emergent, not an explicit filter — it works because opening stock's fabricated wash/lab rows have no `moyka_sends` counterpart (0 rows system-wide), so the turnaround subtraction evaluates to `NULL` and SQL's `avg()` silently drops it. Flagged as latent fragility (would silently re-admit opening stock with a fake zero-day reading if anyone ever backfilled a `moyka_sends` row for consistency), not a live defect.
