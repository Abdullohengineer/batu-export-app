## 2026-07-25 — Capgo upload blocker: `notifyAppReady()` wasn't missing from the code, it was missing from `main`

**Context:** `npx @capgo/cli bundle upload` refused with "notifyAppReady() is missing in the build folder." `findstr notifyAppReady src\main.tsx` found nothing — but the "Capgo live updates" entry earlier in this file (chronologically task 2 of this session) describes adding exactly that call. Investigated why a documented, described-as-done change was absent from the actual tree.

**1. Searched the whole `src/` tree — genuinely absent, not misplaced.** Zero matches for `notifyAppReady` anywhere under `src/`, confirming the user's own `findstr` finding rather than assuming it was just in a different file.

**2/3. Root cause, confirmed via git history, not assumed: the whole Capgo integration was never merged to `main` — it wasn't removed by a later merge, it never arrived.** `git log --oneline --all -- src/main.tsx` shows exactly two commits ever touching that file: the original scaffold, and `092ab13` ("Add Capgo live updates for OTA web-layer pushes") — and `git show 092ab13 -- src/main.tsx` confirms that commit genuinely added the exact `notifyAppReady()` call described. But `git merge-base --is-ancestor 092ab13 main` returned false: that commit only ever existed on its own branch, `capgo-live-updates`, which was pushed at the end of task 2 but whose PR was never merged (task 43 in the session's own tracker — "Set up production channel on Capgo" — was left `pending` for a related, separate reason: the Capgo backend's own account inconsistency, see below, blocked the channel-creation step that would have prompted closing the loop). Confirmed the gap was total, not partial: `grep -i capgo package.json` on `main` before this fix found nothing at all — no dependency, no `capacitor.config.ts` plugin block, nothing. Every task since (camera-scanner-webview, photo-compression, ombor-printing-gaps, menejer-chiqim-widen, camera-overlay-feedback) branched from `main` and so never had any of it either.

**Fix: cherry-picked `092ab13` onto a fresh branch off current `main`**, rather than re-deriving the integration from scratch — it was a single, clean, purely-additive commit (7 files, all `+`), already fully designed and verified in task 2 (env-var survival across `build:native`, `autoUpdate: 'atBackground'`, the hosted-service config, the intentionally-unset `defaultChannel`). Applied cleanly with one expected conflict: `docs/DECISIONS.md`, since every task appends to it and this commit's own 40-line entry was written against an earlier point in the file. Resolved by placing the Capgo entry at its real chronological position (right after the P1-printer entry, where `capgo-live-updates` actually branched) rather than at the file's current tail, with a short note explaining why a task-2 entry is landing now, during what's chronologically a much later task — so the log still reads as an accurate timeline instead of one entry appearing mysteriously out of order. `npm install` confirmed `node_modules` was already in sync with the restored `package-lock.json` (0 changes, same 20 pre-existing `npm audit` findings already flagged as unrelated in the original entry).

**4. Confirmed the call survives the real production build, not assumed from source.** `npm run build:native`, then searched the actual minified `dist-native/assets/index-*.js` (not the source) for the string: found exactly once, `...re.notifyAppReady();export{...}` — right after the React root's `render()` call, exactly the intended placement. It survives because minifiers (Vite's default, esbuild) rename local variable/import bindings (`CapacitorUpdater` here became the local alias `re`) but do not mangle property/method names accessed via dot-notation on an external object by default — `notifyAppReady` is such a property, not a renameable local identifier, so there was never a real risk of minification hiding it from Capgo's own source-string check. Answers the task's own alternate hypothesis directly: minification is not why the original check failed; the code simply wasn't in the tree being checked.

**Confirmation the bundle now uploads — partial, and the remaining blocker is a separate, already-known issue, not this one.** `npx @capgo/cli@latest bundle upload com.batuexport.app --channel production` no longer raises the `notifyAppReady()` code-check error at all — it passes straight through that check to the actual upload step, which is itself proof the fix works (that check is what produced the user's original symptom verbatim). It then fails with a different, later-stage error: `Cannot get organization id for app id com.batuexport.app`. Checked further with a read-only command, `npx @capgo/cli@latest app list` → `No apps found` — the exact same write-path-exists/read-path-invisible inconsistency already flagged (unresolved) in the "Capgo live updates" entry above, not a new problem and not something fixable from this codebase. This is Capgo's own account/backend state, dashboard-side per the original task-2 split of responsibilities, not touched further here.
