## 2026-08-02 — Raw dispatch serial pool

**Context.** The one-serial-per-raw-line model (`chiqim_lines.raw_serial`, 2026-07-31) forced Menejer to pin one exact serial with an implied quantity before the truck ever arrived. Reworked to mirror the finished side structurally: `chiqim_line_pallets` is a reservation pool, `dispatch_manifest` is what actually loaded — raw becomes the same shape, a Menejer-selected POOL of candidate serials (`chiqim_line_raw_serials`, new) with Ombor recording actual per-serial draws on the floor (`raw_dispatch_lines`, unchanged). The pool's total available has no relationship to what gets drawn — "these are your sources," not an allocation.

**Schema.** New junction table `chiqim_line_raw_serials(line_id, serial)`, deliberately NOT copying `chiqim_line_pallets`' reservation machinery (`released_at`, active-unique-index) — raw is bulk and divisible, so two requests may legitimately draw from the same serial; there is nothing to reserve or release, only pool membership. `chiqim_lines` gained `line_kind` ('finished'|'raw'), backfilled from the old `calibre_id`/`raw_serial` XOR shape before `raw_serial` was dropped; every existing raw line's single serial migrated into the pool as a one-row pool (by construction, every historical `raw_dispatch_lines` draw already matched it exactly, so nothing became retroactively "out of pool"). `qty_kg` became nullable for raw lines (Menejer may not know how much will be drawn) via one folded check constraint (`chiqim_lines_kind_shape`) replacing the XOR. `0047_raw_dispatch_serial_pool.sql`.

**App-level guard (2026-08-02 feedback).** The DB can't enforce "a raw line has ≥1 pooled serial" across two tables — `ChiqimForm.tsx` gained an explicit pre-submit check (mirroring the existing `missingPicks` check for finished lines) that blocks with a specific error message rather than letting an empty-pool raw row silently vanish from submission if another row on the same form happened to be valid.

**What needed zero changes, confirmed before touching anything.** `get_client_report`, `get_serial_passport`, `stock_on_hand_rows`, `wip_rows`, and `useMoykaSerials.ts` all read `raw_dispatch_lines` directly by `serial` — none ever touched `chiqim_lines.raw_serial` or branched on `calibre_id`'s null-ness. Requirement 9 (passport shows partial raw collection) was already satisfied by existing code (`get_serial_passport`'s `rawDispatches` CTE joins through `chiqim_lines` but filters by the *draw's own* serial) — confirmed by hand-verification below, not just by inspection.

**The 8-file `calibre_id`/`raw_serial` ripple, now keyed on `line_kind`:**
- **`ChiqimForm.tsx` (major).** `rawSerial: string` → multi-select `Set<string>`; qty no longer required or auto-filled for raw rows (relabeled "Taxminiy miqdor (ixtiyoriy)"); submit inserts `line_kind`/nullable `qty_kg`, then batch-inserts the pool into `chiqim_line_raw_serials` — symmetric with the existing `chiqim_line_pallets` insert for finished rows, no 23505 race handling needed (line_id is freshly minted per submission). New local oldest-first sort for the picker (requirement 5, "aged raw moves before fresh") — `useMoykaSerials`'s own newest-first default is untouched, it stays load-bearing for §5.2 Window 1 elsewhere.
- **`OmborChiqimTab.tsx` (major).** State reshaped from one draft per line to an array of committed draws per line plus a per-line in-progress composer. Ombor picks a pooled serial (or types any other real serial — out-of-pool, warned, blocked from being *added* to the draft without a note, never blocking the overall finish) then weight+box mass, and adds it; a line can hold several draws, even against the same serial twice (requirement 6, confirmed the DB already allowed N `raw_dispatch_lines` rows per `chiqim_line_id` — no unique constraint ever existed there). `handleFinish` now inserts sequentially, not batched — mirrors `ChiqimForm.tsx`'s own established discipline against trusting batch-insert RETURNING order — because each draw's own returned id is what ties an out-of-pool note to the right row via the existing generic `notes` table (`entity_type='raw_dispatch_lines'`), reused as instructed rather than building a new note feature. A raw line's now-optional `qty_kg` also meant `lineStatus`/progress-bar/shortfall/aggregate-tone logic needed a "no target" path throughout this file and `chiqimScan.ts`'s `shortfallLines` — an un-estimated raw line shows its running total with no bar or shortfall claim, since there's nothing to fall short of.
- **`useOmborChiqimRequests.ts` (moderate).** `ChiqimLine` gained `line_kind` (kept snake_case, unlike this interface's other derived fields, to stay structurally compatible with `chiqimScan.ts`'s `ChiqimLineLike` which `request.lines` is passed into as-is) and `rawSerialPool: string[]` via a new `chiqim_line_raw_serials(serial)` join.
- **`FinishedChiqimList.tsx` (minor, extended per explicit confirmation).** `lineLabel` switches to `line_kind`; also fetches and shows the full pool (`Xom · A, B`) rather than degrading to a bare "Xom" — this is a receipt/history view, and a finished line's `reservedPallets` are already shown here in full, so showing less detail for raw would have been a regression in visibility, not a neutral simplification.
- **`useFinishedChiqimRequests.ts`, `useChiqimTrips.ts`, `chiqimScan.ts`, `chiqimScan.test.ts` (minor/mechanical).** Field swap throughout; `resolveScan`'s actual matching logic needed no change — a raw line's `calibre_id` is still always null either way, so it's still naturally never a scan candidate, exactly as that function's own pre-existing comment already explained.
